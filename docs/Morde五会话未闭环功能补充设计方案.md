## 2. 全局设计规则

1. **服务端是唯一事实来源。** 客户端只展示服务端确认的主会话、Task 状态、Workspace revision、Host 状态、项目授权和费用；读取历史不能创建 Task 或触发执行。
2. **能力声明与对象授权分开。** `/api/capabilities` 只说明服务端已经装配并支持某项合同，不授予账号对具体资源的权限。每个请求仍须校验 actor、账号、项目角色、Host/Workspace 关系及当前授权。
3. **把身份与权限分开。** Task ID 只定位 Task；Host cookie 只证明 Gateway 客户端身份；操作租约只授权特定时间内控制 Host；Workspace 访问须由账号/项目资源权限另行授权。
4. **写操作使用版本与幂等。** 任何会改变会话、Task、Workspace、项目预算或所有权的操作都携带期望版本和幂等键。冲突返回当前版本供用户核对；超时结果标为 `unknown` 并先对账，不自动重放副作用。
5. **未知状态 fail-closed。** 服务不可达、授权过期、迁移或物化未确认时保留最后一次已确认状态并标出时间；未知不等于成功、失败或可继续写入。
6. **个人和项目数据隔离。** 个人主会话、记忆、凭据和安装状态默认私有。项目成员只能访问明确关联且已授权的项目资源；加入项目、看到 Host 或知道 Workspace ID 都不自动获得文件权限。
7. **迁移不丢唯一副本。** 不因服务重启、Host 重建、Workspace 迁移或代码删除清理旧卷、历史和凭据。验证新副本可读、完整且可回滚前，旧数据保持原位或只读保留。

## 3. P0 闭环设计

### 3.1 会话、消息与 Task 恢复

- 主会话在服务端按服务实例和账号唯一确定；初始化、切换使用版本比较写入。客户端首次启动跟随服务端主会话，用户明确选择普通会话后才暂时离开主会话。
- 同一会话的消息按服务端顺序构造后续 Task 上下文。每条消息携带幂等键；服务端返回 `pending`、`applied` 或 `unknown`。只有确认进入执行上下文后才显示为已应用。
- 一个 Task 的 Host、Workspace、revision 和模型目标在创建时固定。切换会话、账号或目标不能默默改写现有 Task；继续执行须通过当前 Task 和 lease 校验。
- 应用重启或断线后先读会话消息及 Task 快照，再按最后确认的事件序号续读 SSE。快照版本较新时以快照为准；事件过期时重新拉取快照，不重新提交原消息、不重新启动 Task。
- 批准/拒绝、澄清、暂停/继续/取消都绑定当前请求 ID、版本和幂等键。冲突时刷新后要求用户核对。停止或取消结果未知时保留“待确认”，不得显示已停止。
- 项目 Task 的发起人、会话创建者和项目负责人是不同角色。当前合同下只有会话创建者控制共享会话 Task；其他成员按项目权限查看摘要。若将来允许成员审批或停止，必须由服务端单独签发可撤销授权，不能用成员身份推导。

### 3.2 个人资料、记忆、目标与例程

- 个人对象以账号为边界，沿用现有 personal object 类型与 revision；云端读写都传对象类型、稳定 ID、期望 revision 和幂等键。
- 客户端保留未同步草稿；发现服务端 revision 前进时显示冲突，不做字段级静默覆盖。用户确认解决后生成新 revision，历史值仍可追溯。
- 例程和提醒使用服务端时区、触发记录及幂等键；同一触发窗口最多创建一个 Task。撤权、停用、错过执行和服务重启都写出可查询状态，不重复补跑。
- 记忆供 Agent 使用时按会话/项目授权选择上下文；项目会话不自动读取个人记忆。不同账号缓存必须按 service instance、account 和 installation scope 隔离，切换身份即清理内存内容。

### 3.3 Workspace 文件、版本和过程视图

- 将粗粒度 `workspace_sync` 拆成明确能力：`workspace_read`、`workspace_write`、`workspace_restore`、`workspace_copy`、`workspace_transfer`。旧客户端只认识聚合能力时，服务端仅在整套旧合同确实完成后才公布旧 `workspace_sync`；新客户端按最小权限逐项显示入口。无能力声明时所有相应入口保持关闭。
- 文件列表、预览、下载与修改各自做授权。写入、重命名、移动和删除传入 Workspace revision、规范化相对路径、期望版本及幂等键；拒绝越界、敏感路径和未支持的文件类型。符号链接只操作链接本身，不跟随目标读取内容。删除云端文件与清理本机副本必须是不同操作。
- 版本历史以已确认的不可变 revision 为依据。手机和 Workbench 的 diff 展示路径、变化类型和安全元数据；敏感内容不进入事件摘要。回滚总是追加一个新 revision，不覆盖旧历史。
- Workspace 变更时间线用分页 revision 查询；不为 P0 新造第二套事件持久化。Task 的运行过程继续用 Task SSE。Host 在线/状态沿用授权后的 Host 查询：页面可见时每 5 秒刷新，超过 15 秒未获新确认标为旧，应用进入后台后停止轮询；不能把 HTTP 请求成功当作状态已变化。
- 文件操作、差异、回滚、同步和 Task 过程均关联 actor、Workspace、Task（如适用）、revision 与结果状态，便于复查写入来自谁、作用于哪个已确认版本。

### 3.4 一 Host 一 Workspace、控制权、复制与移交

- 创建/恢复 Host 前验证恰好一个 ready Workspace，且它没有被其他 Host 占用；数据库唯一约束和事务锁是最终防线，客户端检查仅用于提示。无绑定的旧 Host 保持停止/不可运行状态，直到用户明确选择可用 Workspace。
- 多人可以观察 Host；单个 Host 同时只有一个带过期时间的操作租约。接管、释放、续租均带 lease version。AI 与人工操作也通过同一个 Host fence；观察票据不能转成控制权。
- 恢复顺序固定为：停止 Host 写入、排空 Task/同步/连接、确认最后 revision、解除绑定、按期望 revision 执行 restore、核对新 revision 及物化结果、由用户选择是否重绑。任何停止/解绑结果未知或仍有活动写入时保持冻结并先对账。
- Workspace 复制使用停写后的 checkpoint，先只读预检文件类型和元数据、再预留容量、复制、读回逐项比对源/目标、最后创建新的 Workspace/Host 绑定。P0 不要求 COW。预检发现硬链接、ACL/xattr 或其他无法无损表达的数据时，在目标卷创建和源冻结前拒绝并返回原因；不得悄悄丢元数据后标记完整。
- 移交申请持久冻结源 Workspace。接收方有独立的待接收列表，只能查看发给当前账号的申请；接受与取消按版本串行化，成功接受后旧 owner 权限立即撤销。复制/移交/同步/恢复互斥；崩溃后按持久 operation ledger 对账后才能解冻。
- 建议补充两个最小列表合同：负责人可按项目列出其待处理成员邀请（建议 `GET /api/projects/{project_id}/invitations?state=pending`）；接收人可列出发给自己的待处理 Workspace 移交（建议 `GET /api/me/workspace-transfers?direction=incoming&state=pending`）。二者都要分页、按当前 actor 过滤并在每次读取时复核权限，客户端不得枚举 ID。

### 3.5 项目工作、交付和账本

- 项目角色固定为 owner/member/viewer；路由按操作校验角色与资源关系。邀请列表、撤销、接受、转移负责人都使用 invitation version 和幂等操作。
- 项目共享会话中的 Task 必须归属项目、会话和实际发起人。工作项关联 Task 时服务端验证成员资格和 Task 归属；交付登记引用已确认的 Workspace revision 与服务端验证过的产物证明，不接受客户端自报的成功状态或文件内容。
- 项目连接器页面只组合当前账号私有连接器元数据与项目已有 active grants；credential 和 endpoint 不返回给项目成员。当前项目列表只返回 active grants，而重新授权被撤销 grant 需要当前 grant version。建议增加 `GET /api/projects/{project_id}/mcp-connectors/{connector_id}` 返回无秘密的状态/version，仅连接器 owner 或项目 owner 可读；客户端收到 409 后刷新状态再让用户确认，不能拿 `expected_version=0` 覆盖撤销状态。
- 内置技能是只读指引，不授予新工具或文件权限；它们沿用 Task 当前授权，默认不做项目级开关。`skill_setting` 个人对象目前不等同于 Runtime skill grant，客户端不应把它当作项目执行开关。以后若产品要控制某项内置技能是否可用，应先由服务端提供版本化 catalog/grant API 并在每次执行时复核。
- `project_budget_execution` 只有在项目授权、账号预算预留、项目预算预留、版本化费率快照、幂等结算与超额/unknown 对账全部可用时才开启。金额未知时仍可展示用量，但不能表示已结算或允许无预算执行。
- Host CPU/内存采样和模型费用分开。每个采样点快照记录归属和代次，归属不唯一、counter reset、容器变化或缺样即标 `unknown`。账本 API 只返回有权限的汇总，不泄露容器 ID、原始快照或其他项目归属。
- Host 资源费用策略尚未确定前只记录用量，`price_status=unknown`，不扣账号或项目预算。原始样本必须有有限保留期并汇总为有界周期数据；保留期和计费主体列为产品决策，不由实现自行推断。

### 3.6 受控外部 AI 与旧电脑数据迁移

- Codex/Claude 等外部 AI 在单次 Task grant 到位前保持不可启动。grant 绑定 actor、项目、Task、Host、Workspace/revision、允许的文件/网络范围和有效期，可撤销并可审计；撤权必须阻止新操作并停止可终止的在途进程。
- cgroup/容器身份本身不足以证明文件和网络隔离。W11 需证明工具进程不能读取其他 Workspace、宿主机路径或未授权网络；无法证明时 capability 继续关闭，不把 WeChat allowlist 或状态探测当作通用 AI 执行。
- W22 先盘点旧 `workspace-root`、`profile-data`、`runtime-data`、`host-apps` 卷与 Host/Workspace/账号映射。歧义卷不自动归属；凭据不得复制到新共享范围。每批迁移先形成可恢复副本、校验文件树及权限、演练回滚，再切换新 Host；旧卷只读保留至回退窗口结束。
- 数据路径、默认镜像、Linux 权限、空间限制和真实目标卷只能在本地目标 Ubuntu 上验收。Docker Desktop 和 macOS 临时目录结果不能替代 Linux 固定镜像证据。

## 4. P1/P2 接入规则

- **P1：**通知分级、设备接力、项目技能/连接器、文档模板。复用当前 Hub、MCP grant、Task artifact 与 Workspace revision；设备是获准目标，不是第二个 Agent；个人连接器凭据不复制给项目。客户端可查看服务端固定技能 allowlist 的安全说明和项目有效连接器；未取得可读的 grant version 前不提供撤销后的重新授权。通知默认脱敏，只有明确 actionable 的事件才可导航。
- **P2：**行级批注、跨项目搜索、语音与图像/视频/语音处理。先按项目/Workspace 权限过滤再做检索或摘要；批注锚定不可变 revision 和精确行/范围；媒体输入输出使用平台管理的模型连接，生成物写入授权 Workspace 并取得 artifact proof。真实媒体服务没有就显示未就绪，不使用本地 Agent 或占位结果伪装完成。
- Feed、Ideas、Library 和简报等 Muse 入口继续保留；按各自的数据合同逐步迁移，不因 P0 关闭本机 Agent 而删除用户数据。

## 5. 分阶段交付与依赖

1. **合同冻结：**服务端、OpenAPI/生成客户端和 Portal schema 对齐 capability、权限主体、版本/幂等、unknown 与迁移状态；会话 1/4/5 将公共合同写入各自交接记录，PC/iOS 只消费已发布合同。
2. **个人 P0：**主会话、多轮上下文、消息投递、审批/澄清/停止恢复；个人数据 revision 与计划幂等；Workspace 只读/写操作、版本 diff/restore、Host 绑定和租约。
3. **团队 P0：**成员/邀请待办列表、项目会话和 work-item、Task 与交付证明、预算/费用 unknown 语义；完成 PC05/PC07/iOS I08/I09 的正式 API 接线。
4. **Workspace P0：**完整复制、迁移预检和旧卷映射、接受式移交及失败对账；完成 W10/W20/W22 与 iOS I14–I16，随后安全退役已被替代的入口。
5. **受控执行与清理：**W11 安全隔离经证实后再开放 R09；PC10/I10 及 R11 等旧入口按调用方证据和可回退迁移分步收敛。无替代合同的旧数据读取保留。
6. **P1/P2：**按第 4 节逐项启用，任何新功能不得绕开 P0 的权限、预算、Workspace 和 artifact proof。
7. **W14 最终集成：**收齐各会话的迁移、API/OpenAPI、客户端和本机数据库证据；逐项给出“实现、本机验证、目标环境待验证”，不把 mock、跳过或仅编译成功写成端到端通过。

## 6. 验收条件

### P0 必须通过

- 同一账号在两个 PC/iOS 客户端读到同一主会话；多轮消息、重复提交、事件断线、重开和审批版本冲突均不重复执行，另一账号的数据保持隔离。
- 同一账号的个人记忆/例程在授权范围内读取和更新；冲突保留两边内容，项目成员无法读取个人私有数据。
- 文件只在 capability 和资源授权同时满足时开放；上传、重命名、移动、删除、diff、restore 均处理并发 revision；未知结果先对账，不覆盖确认外数据。
- Host/Workspace 一对一约束在并发创建/恢复时仍成立；两个逻辑用户可验证观察只读、租约抢占/到期/撤权；复制和移交期间写入/启动按合同冻结。
- 项目邀请、成员权限、Task、工作项、交付证明、预算预留与 ledger 在 owner/member/viewer 和跨项目边界下均有允许/拒绝用例。
- 外部 AI 未通过授权与文件/网络围栏之前保持 fail-closed；旧卷迁移可中断重试、可读回并可回滚；旧数据不会因清理代码消失。

### P1/P2 必须通过

- Hub/MCP/模板调用均能撤权；通知不泄露正文；搜索、批注和媒体结果按项目与 Workspace 授权过滤，并关联可验证 revision。
- 模型和 Host 用量可以与费用区分；只有在费率、付款主体和预算策略明确且账本记账测试通过时才报告金额。

### 本机验证边界

- 使用本地替身、内存响应、两个逻辑账号、临时目录和临时 PostgreSQL；浏览器验收仅用内存数据。iOS 运行使用现有模拟器，不要求真机或真实文件传输。
- 服务端按入口要求执行可离线运行的测试、race、覆盖率、lint、生成文件检查及所需 PostgreSQL 集成；任何自动下载、远程访问或文件外发在运行前都必须排除。
- Minis simulator 现有预编译 `libish_emu.a` 为 device-only；在取得本机可用的 simulator 版本前，记录该限制，使用 generic iOS build 验证共享 Swift 源码，不更换仓库外依赖。
- 测试服务器、真实 Ubuntu、真实外部 AI、真机和跨设备文件传输均不在本方案可声称已验收的范围内。若将来要做这些验证，须先满足仓库本地规则并准备独立授权的本地环境。

## 7. 需保留的产品决策

唯一会阻止“Host 用量变成实际扣费”的业务决策是：共享 Host 的费用由 Host owner 账号承担，还是由发起项目 Task 的项目预算承担；同时需要确认费率和账本保留期。**默认建议先只计量、不扣款、不把 `unknown` 转成估算金额**。这不阻塞其余 P0/P1/P2 开发；进入实际收费前再请产品负责人确认。

文件系统遇到不能无损复制的 ACL/xattr/硬链接时，本文默认在预检阶段拒绝复制并保留源数据，不做降级复制。若产品要求兼容这些文件系统特性，应先补齐 manifest、revision、同步、diff、restore 与复制全链路的表示和测试，再宣称完整复制。
