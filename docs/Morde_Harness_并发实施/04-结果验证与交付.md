## 目标与任务来源

核实 H05 现有 Task validation/review、结果快照和原会话发布事务是否满足合同；只有当前 Task 修订、产物版本、来源与实际环境证据满足规则时才能通过。Task completed、模型自述或 ResultReview 摘要不能替代验收状态。结果先持久化，再回到正确的原会话，恢复/重连不能重复发布。已有测试覆盖的部分不重写。

具体合同直接引用[最终规格](../Morde_Harness_最终流程与实现规格.md) §2 的第 9–10 步、§4 和[主 TODO](../Morde_Harness_实施任务_TODO.md) H05。

## 实施步骤

1. 审查验证 Worker 与正式发布事务的先后关系，画清当前实际调用链；不把异步 review “存在”当成 final response 已被阻断的证明。若现有实现和故障测试已经证明门禁正确，只将实际入口验收留给 S07，不增加重复机制。
2. 核实当前修订、来源、产物、环境和校验结果的持久绑定；旧证据、旧修订和迟到结果必须被拒绝或 supersede。
3. 对照 Hermes `turn_stop_gates.py` 和 `turn_final_response.py` 的调用链与测试；兼容时移植最小 stop-gate 控制逻辑及配对测试。最终状态、发布事务和回执仍使用 Morde 现有机制。
4. 若新增 Schema，先向协调会话申请迁移号；S07 合并后验证真实客户端投递。

## 验收

按 H05 覆盖只有模型自述、证据缺失、错误环境、旧修订、重启/重连和晚到结果。必要证据缺失时不能标 PASS；Task completed 和 ResultReview 与 validation 状态分开展示；同一最终回执只发布一次。包括一个工程证据和一个非工程证据场景，实际客户端展示由 S05/S06 完成，端到端证据由 S07 记录。

## 本轮 S04 结果（2026-11-22）

- 正式回执仍在原 `publishConversationResultReviewInTx` 事务中持久化；回执将主助手内容标成“结果摘要，不代表独立验收”，另写 `Task 执行状态：completed` 和按 Task ID/修订列出的服务端验收状态。
- 只有 `task_validation_reviews.state='reviewed'`，且 Task 当前完成修订、`task.result` 事件序号/修订/结果摘要与回执来源完全相符时，才显示持久化 verdict。缺行、待审、旧修订、错误事件或摘要不匹配均回退为 `pending`；`PASS`/`FAIL` 不由路由模型回复推导。原会话、单条消息 ID、批次状态与重放事务未另建路径。
- 当前执行证据没有服务端可信的目标环境 ID；Shell 证据只有退出码/超时和输出字节计数，产物复核目前只读标签、路径、媒体类型、大小。S04 verdict loader 对工具执行将审批、纠正与回放事实保留为 unknown，因此模型建议或模型填写的 environment 字符串不能产生 PASS。未添加或推测环境标识。
- 最小跨 owner 提案：S02 在受控执行尝试中产生不可由模型填写的目标环境身份；S03 将其与 Task 修订/尝试及实际结果事件绑定，并为 Artifact 暴露服务端内容摘要和版本。S04 再按结果所引用的执行环境和产物版本验证相等关系。接口补齐前，此类执行保持 pending。
- 本地 `go test ./internal/app -run 'TaskValidationVerdict|EvaluateTaskValidationReview' -count=1` 通过；`conversation_result_review.go` 的 PostgreSQL 门禁集成回归已写入，但因 `CH_TEST_DATABASE_URL` 未配置而未执行。纯回执格式/上限测试、`git diff --check` 通过。精确 PASS 回执测试通过合成的持久 verdict 行验证“可发布既有 PASS”，不代表当前生产事实收集器已能为执行型 Task 生成 PASS。
