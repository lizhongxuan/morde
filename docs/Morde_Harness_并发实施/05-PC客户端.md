# S05｜morde-pc 客户端

**状态：** 未开始（H 项状态见[主 TODO](../Morde_Harness_实施任务_TODO.md)）。

**共同开发门禁：** 缺陷必须按[并发总控](00-并发实施总控.md)追到机制根因；复杂方案、取舍和模块/函数边界要留档。不得只绕过失败状态或缩短测试输入。

## 目标与任务来源

完成 H06 中 PC 端需要的消息受理/失败说明、任务进度、运行中追问、恢复后状态与结果入口，让用户从实际 `morde-pc` 完成相关操作。普通用户功能不得只交付为独立 Web 页面。

具体验收直接引用[根 AGENTS.md](../../AGENTS.md)、“PC 端优先”和第一里程碑，以及[最终规格](../Morde_Harness_最终流程与实现规格.md) §2.4、[主 TODO](../Morde_Harness_实施任务_TODO.md) H03/H06。既有 API 可用时只接 UI，不顺手改服务端合同。

## 文件所有权

独占 `clients/desktop/harness/desktop/**`、`clients/desktop/harness/dsh-nanomuse/src/client/**`。如果现有 Portal 组件由 morde-pc 内嵌使用，才允许修改对应的 `web/portal/src/routes/Assistant.*`、直接配套样式和测试，并须在回报中说明它的 PC 内嵌入口；不得把 Portal 浏览器验收写成 PC 验收。

不修改 iOS、服务端、Runtime、共享 API DTO 或主 TODO。需要接口变化时先向对应服务端 owner 提案。UI 遵循仓库 ice-cream-blue 规范。

## 实施步骤

1. 先审计当前 PC 代码与未提交基线；已有失败原因显示修复及本地运行中普通问答夹具记录在主 TODO。区分已经实现的行为与缺口，保留普通问答、任务卡及文件夹同步功能，不重复写同一修复。
2. 对已受理但路由/模型失败的消息显示安全且可操作的原因；保留原文和幂等重试语义，不能隐藏为无说明的重试图标。
3. 接收 S03 确认的审批/额度展示数据合同，在需要时展示本次预估、已累计、限额和未知项；复用现有会话、任务、进度和消息投递合同，不实现第二套意图路由或客户端自行判定权限。
4. 逐项用真实 `morde-pc` 操作受影响入口；必要时以本机服务和合成文本构造测试数据，所有数据与产物只留本地。

## 验收

除组件测试、类型检查和 PC 构建外，必须启动并操作当前工作树构建的实际 `morde-pc`。验收至少覆盖普通回复、后台任务期间普通提问、定向追问状态、消息失败原因、断线/刷新恢复和现有文件夹同步回归（若改动触及相关 UI/入口）。真实 Provider 或服务端不可用时如实记录，不用独立浏览器、截图或构建结果宣称 PC 端到端通过。

## 会话完成回报

按[总控交接格式](00-并发实施总控.md#5-会话交接格式与合并规则)回报实际 PC 版本/入口、操作步骤、截图或本地证据位置、服务端/API 基线、运行结果和未测范围。不要编辑共享 TODO/验证记录。
