## 11.2 明确不知道的事（清单）

1. 模型内部：Muse Spark / Wonder 的架构、参数、训练数据、微调方法。
文档只给定位与价格，不给内部细节；内部代号一律不分享。
2. 构建器私有运行时：一句话做 App 时，平台侧的脚手架、构建、
部署、托管数据库绑定的具体实现。
3. 平台定时基础设施：cron 与 hooks 在平台侧怎么调度、怎么保证送达、
失败重试策略。
4. 每用户 VM 规格：CPU、内存、磁盘、网络、并发上限。
5. 数据库容量与上限：每用户 SQLite/PostgreSQL 的容量、表数量上限。
6. 审批卡的内部实现：卡片布局、按钮、措辞（文档明确说 Agent 看不到）。
7. 内部 codename：用户提到内部代号时，只说不能分享内部代号的信息。
8. 订阅价格细节：以 `subscription-status` 技能为准，不以网络搜索为准；
技能查不到时直说查不到。

## 11.3 哪些推测最容易错

- “Muse 就是一个大模型 + 提示词”——错。模型只是 L2 层，
产品的大部分在 L3–L5（技能、连接器、子 Agent、电脑、审批、记忆）。
- “一句话做 App 是一次写对”——错。实测是写完、探针、真调、审计、
改错、再测，审计曾抓到简报与行情板方向矛盾、诊断漏读复盘数据等真错。
- “技能就是插件”——错。技能是流程剧本，连接器才是插头；
换服务不用重写流程，换流程不用重接服务。
- “公开链接就是最新版”——错。编辑不更新已分享的公开链接，
Morde iOS 设计稿与 Agent Office 均已验证。
- “定时任务建好就一定会送达”——错。建好 ≠ 送达；要查状态、
查日志、确认启用；修不好就停用并告诉用户。

## 11.4 Codex 复现路线图（等价做法，不是原版）

目标：在 Codex 上逼近“一句话做 App”，承认三块没有对应物，
用开源替代方案补。

### 阶段 0：先搭三件资产（半天，6 步）
1. 建项目目录：`client/`、`server/`、`drizzle/`、`scripts/`。
2. 写根 `AGENTS.md`（判型、八步工作流、目录约定、数据真实性红线、
验证门禁清单）——全文见《Codex 一句话做 App 工作包》。
3. 定技术选型：TS/React + SQLite/Drizzle（Python 可等价替换）。
4. 写最小文件清单：`client/src/App.tsx`、`client/src/theme.css`、
`server/src/schema.ts`、`server/src/actions.ts`、
`drizzle/0001_init.sql`。
5. 写探针脚本模板：断言具体标识符与数值，并故意改错验证它真的会失败。
6. 写验收清单：构建成功、探针通过、真实调用一次、一致性审计通过、
定时任务手动触发一次。

### 阶段 1：第一个练手应用（低风险）
选数据源公开、结果一眼能验对错的应用（例如公开行情、公开榜单），
不要选需要登录、付费、医疗、金融交易的。

### 阶段 2：补齐缺的三块（开源替代）
| Muse 有、Codex 没有 | 开源替代 |
|---|---|
| 私有脚手架运行时 | 自己搭的项目模板 + `AGENTS.md` |
| 托管数据库一步绑定 | SQLite 文件 + Drizzle migration，备份到对象存储 |
| 平台定时基础设施 | cron + 幂等任务 + 失败保留旧数据并标注时间 |

### 阶段 3：不要先做的事
- 不要重写聊天 UI、Agent 运行时、审批卡、触发器、iOS 应用；
先用现成开源项目做底座，只加自己的顶层。
- 不要做多用户、计费、云手机；先跑通单人闭环。
- 不要把模拟数据说成真实数据；不要把助手提议说成用户决定。
