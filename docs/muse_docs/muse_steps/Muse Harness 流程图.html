Muse Harness 流程图：每个步骤、每个函数

没有 Muse 源码。这张图是逆向工程的产物——从真实对话、工具调用记录、数据库表（muse.db 只读查询）和产品文档反推出的 harness 全流程，细到每一步的判定条件、每个关键函数的输入输出与实测数字。

一句话概括：Muse 的 harness 是「1 个 root agent + 树形 subagent（实测最深 2 层）+ 有序事件账本 + 卡片制审批 + Markdown 与数据库双轨记忆」。主对话极短（回复中位约 150 字），约 75% 的事件用户看不到；过程噪音全部收进任务详情，任务是四层结构：消息 → 任务 → 主 agent + 子 agent → 每人一串工作项 → 每条点开是完整命令、退出码、耗时、输出原文。

01

收件与入口：消息先落盘，再谈处理

入口面很宽，但全部是一对一：消息只在用户与自己的 agent 之间流动，没有群聊。收件只是 harness 的一个入口——内部调度、自我改进、监控产生的请求量是用户聊天的上百倍。

用户入口
多端主对话已证实

Web / iOS / Android / Mac 应用 + Chrome 扩展侧边栏（复用用户自己 Chrome 的登录态）；每会话一个 chat UUID，transport 不产生第二份 transcript。

其他入口
侧边通道与语音已证实

WhatsApp 是当前唯一有指南的侧边 provider；语音对话、语音备忘录转写、多声部音频生成；无环境监听，麦克风不能由 agent 打开。电话仅能打给美国商家（付费计划 + 用户确认）。

落盘为任务行已证实

一行 = activity.activity_monitor_threads 的一条记录：name（标题）/ subtitle（一句话副标题）/ status / finish_status / created_at / finished_at。副标题随进展改写：进行中是当前进展，完成后变成交付物描述。442 个任务全部 finished：success 398、waiting_for_user 30、failed 14。

请求打标已证实

每条运行时请求带三个分类字段：request_origin（来源）、transcript_surface（界面）、root_work_class（internal / user_facing）。实测 61,557 条请求：internal 60,050 vs user_facing 1,507；来源 Top 是 internal.runtime_storage 31,048、internal.self_improvement 14,624、external.hatch_chat 仅 597。

标题现场生成合理推断

同一动作（点赞）两次标题写法不同（「对用户消息点赞 👍」vs「标记用户消息：👍🏻」），说明标题是现场生成的、不是固定词表。Morde 照抄时宜用「动词 + 对象」固定规则，别学这种随意。

幂等 / 去重 / 定序 未知

Muse 侧收件的幂等与定序机制无证据。Morde 自己的 AcceptConversationMessage + client_message_id 幂等 + 服务端 sequence 定序是 Morde 的设计，比 hermes 更严，不是从 Muse 抄的。

意图识别与任务拆分：路由有机制，分类算法是黑箱

skill、connector、偏好、记忆四条路由线都有明确文档机制；唯独「一条消息判成什么任务、几条消息合并成一个任务」的核心算法，文档与数据库都没有——这是整张图最大的未知。

muse.skill_search → SKILL.md已证实

按任务描述找 skill（全库 58 个），每个 SKILL.md 写明触发条件；无 skill 时走 custom-connector-setup：查官方 API / MCP，Zapier / Composio 兜底。

connector 路由（143 个）已证实

边界写死：只有文档里列出的命令才存在，未列出的命令答复为「该 connector 不提供」，不许发明端点。

偏好文件路由已证实

路由线 D · 记忆
muse.memory_search 先行已证实

回答「你记得什么」之前必须先搜记忆；返回相关 claim 与聊天摘录，但不是全部消息。

判定：这条消息归哪个任务？归并存在 规则未知
  • 新开任务——一条消息多半开一个 activity thread。
  • 归并进已有任务——链接表 829 条消息→任务链接 / 352 个任务，平均每任务 2.36 条；109 个任务（31%）链了 ≥2 条，18 个链了 ≥6 条。但归并了哪些消息、按什么规则，无法确认（链接表与消息表的 ID 命名空间不同，只有 29/829 能 join 上）。
判定：任务复杂度需要拆分吗？
  • 简单 → 主 agent 直接做（见分图 03）。
  • 大文档审阅（>10 页 / 多文件 / 法律财务技术审阅）→ coordinator 模式：一个 coordinator 定页码章节分工 + 若干 extraction worker + 一个 checking worker；每个 worker 给定唯一输出路径，互不覆盖；coordinator 保留最终判断权。
  • 宽研究（wide research）→ 一句话 operation_brief + 独立输入列表 + 输出 schema + worker 模板；先去重归一化输入再派 manager；manager 输出合同固定六项：total / success_count / failure_count / results / failures / notes。
  • 用户待办层拆分规则：项目与任务分开、周期性与一次性分开；只在「可分别完成或可解阻塞」时才拆；标题写下一步具体动作；建前先搜是否已有相同任务。

03

并发与后台 Agent：派发不排队，监视不打扰

主 agent 只做简单对话；复杂与并发工作派后台 subagent。派发之后主 agent 继续干自己的事，子 agent 的每个事件都过一次协调员决策——但 99% 的决策不需要惊动主 agent。

主 agent 接任务已证实

实测样本：主 agent 17:03:40 派发两个子 agent 的同时，自己在 17:03:33–17:03:42 做 git 检查——时间戳重叠，不是排队。单日最多建 63 个任务（2026-11-09）；采样时仍有 5 个派生处于 running。

判定：自己做，还是派发？合理推断
  • 简单对话 / 小事 → 主 agent 直接做完回复（连 👍 回执都只给大活儿，小事不点）。
  • 复杂 / 并发 / 长耗时 → 派 subagent 到后台。
  • 判断的具体阈值（复杂度、耗时预估）无直接证据 未知；官方推荐「一个 coordinator per objective」，明确反对从 root 直接扇出多个平级 worker。
派生 subagent（agent.subagent_spawns）已证实

230 次派生：child_depth=1 159 次、child_depth=2 71 次（31%）——嵌套到 2 层，推翻了旧说法「子 agent 不再派子 agent」（那只是单任务样本）。类型分布：通用（agent_type 为空）124 次（54%）、artifact_builder 27、spaces_builder_lite_edit 24、spaces_builder_lite 22、browser_task 12、deep_research 11 等。没有内置的架构师 / 程序员 / 测试队伍，默认就是「1 主 + 按需派生的通用子」。

派生本身也是一条工作项
action_id 前缀 = 身份已证实

工具执行：每次调用都是一条可钻取的工作项

任务记录的最小单位是工作项（action）。活儿主要在子 agent 里干：16,182 条工作项中子 agent 占 13,302 条，是主 agent 的 4.6 倍。每条点开都是同一副骨架——在哪执行、完整命令、退出码、耗时、工作目录、输出原文。

发起一次工具调用已证实

执行通道按类型分：shell（muse.exec + process.* 后台进程）/ 浏览器（browser.browse 派 live 任务，search / open / find 只取文本）/ 设备（只用 device.describe 广告的命令调 device.invoke，绝不发明端点）/ 工作流（workflow_runs 分阶段、可重放）。CAPTCHA 与 bot 检查由浏览器自行解决，不问用户。

先出占位行（running）已证实

运行中的调用先以占位行出现在清单里（标题如「正在运行：正在检查保存的记录」，状态 running），跑完才换正式标题与终态。Web 上悬停运行中条目出现 Stop，可取消——cancelled 是常规终态（96 项）。

落盘 report（固定七要素）已证实

执行位置 + 完整命令原文 + 退出码 + 耗时（毫秒） + 工作目录 + 输出原文（长输出截断并注明截了多少行）+ 一句人话结论。例：git fetch，exit code 0，2275 ms，cwd /home/hatch。连点赞这种一秒钟的动作也记工具名、返回值和结论——没有「太小不记」的例外。

执行结果？
  • success——15,968 条（98.7%）：继续下一步。
  • failed——214 条（1.3%）：留在清单里，不删不改写，任务不因此停下（例：同任务里 ls 返回 exit code 2，后面的构建照常完成）。timed_out 是真实终态（7 项）。
  • 写操作超时或结果不确定时：先读当前状态再决定重试——第一次可能已经成功；「已接受 / 已排队」≠「已确认的物理变化」。
存储层：三张表 + 事件账本已证实

runtime.tool_calls（调用名、输入、状态）+ runtime.tool_outputs（结果与调用引用）+ runtime.events（带 request 归属的有序账本，event_seq 单调递增）。注意：只读角色两次查 tool_calls 都是 0 行，用户能看到的工具记录唯一事实来源是 actions 的 report；0 行的原因（权限过滤还是另有写入路径）未知 未知。

进程重启 / 中断后
恢复四步已证实

05

审批：只卡不可逆点，卡对 agent 不可见

审批是卡片制 + 作用域制。最特别的一点：agent 看不到审批卡的布局、按钮和措辞，也不能承诺哪种选择能停掉后续提示——决定存在独立的 Sentinel store，agent 的权限工具只读。

agent 发起一个动作已证实

普通任务、普通浏览器表单提交默认免批直接执行。

判定：动作属于哪一类？
  • 普通 / 只读 → 直接执行。GitHub 读操作走 call-read-tool（仅限评审过的只读工具清单）。
  • 敏感 / 改状态（登录、发帖、写操作）→ 出审批卡。GitHub 写操作与一切未评审工具走 call-tool，每次调用都要新审批。
  • 购买 → 每次都要新审批，永无 lasting 默认；选卡、看购物车、登录完成都不等于授权花钱。（例外：scheduled task 的一次付款批准覆盖该任务后续「同一商店 + 同一支付方式」，直到任务删除。）
  • 发送（邮件 / 消息） → 每次批准，除非有 scoped allow：可在卡上选「以后对该收件人 / 对话都允许」；欧盟用户没有任何 send allowance；Threads 发帖、Facebook 发帖等永远每次问。
  • 发布 / 上传 / 擦除 → artifact 每次发布与更新、每次文件上传、每次健康数据擦除，都要一次新批准，无 standing 模式。

失败、限流与降级：失败先是记录，其次才是状态

Muse 侧的失败哲学：失败留在任务详情里，不污染主对话、不改写历史；限流是硬停而不是硬撑。对照之下，Morde 路由「直接失败、无降级」是明确的反面教材——这一节两边都画。

失败属于哪一类？
  • 限流 → 每 connector 每分钟配额 + connector_rate_limited + retry_after_seconds（Google 系最紧：Calendar 60/min + burst 20，Gmail 6000 units/min，GitHub 50/min）。带 terminal_for_attempt: true 时当次 connector 工作立即终止：禁 sleep、禁重试、禁委派、禁排替代任务。
  • durable 阻塞（connector 需重连、只有用户能做的动作、bot 检查过不去、配对设备离线、浏览器正忙）→ 任务自己暂停，下一轮再试。
  • 普通执行失败 → 留痕，任务继续（见分图 04）；后台只有 cron / hook / systemd 三种机制，所谓 watch 与事件触发实际都是轮询，两次检查之间发生又反转的变化会漏掉，定时只约不准（前后数分钟）。

一次辅助 LLM 总结hermes 补齐

每 attempt 仅一次辅助调用；输入上限 160K 字符（约 40K token）；产出摘要 2,000–10,000 token。关键细节：总结读的是原始工具结果（summary_view 把窗口内的 stub 还原回原文）；提交时先存后裁，原文以 stub 归档到磁盘，模型之后仍可 read_file 打开。

压缩失败 / 溢出时？
  • 通用失败 → 冷却 600s（DB 持久化）；超时阶梯 (60, 300, 900)。
  • 5 类 terminal failure（认证 / 网络 / 截断 / 空内容 / 过载）→ 必须 abort、原样保留会话、不 rotate。
  • 连续 3 次过载 abort → 降级为确定性 fallback 摘要；连续 2 次 provider 证实的无效压缩 → 触发 breaker。
  • anti-growth 护栏：压缩后 token 反而涨了（实测见过 427K → 598K）→ 拒绝采用。
  • provider 报 context_length_exceeded → 先压缩再重试一次，而不是直接失败（agent/turn_overflow.py）；实在压不动才 fail_turn(compression_exhausted=True)，transcript 保持完整。

Bug 的发现与处理：五步法与两个真实案例

Muse 自身的 bug 处理没有源码可看；能提炼成规范的，是 2026-11-22/23 两次 Morde 服务端真实排查——每一步都有日志、数据库与实测支撑。这套五步法就是建议 Morde harness 照抄的调试流程。

第 1 步 · 发现：先拿数字定性已证实

失败率、失败分类 Top N、用户原话，三样先摆出来再动手。例：路由失败 20/73（总体）、11/53（近 2 天约 21%）；近 7 天路由结果 48 routed、9 routing_context_unavailable、6 routing_action_unavailable、4 message_too_long、3 model_unavailable、5 waiting_user。

第 2 步 · 定位：分层排除已证实

四个动作：① 先证伪最显眼的假设（模型窗口查实是 1,048,576 token，不是瓶颈）；② 沿代码路径找真正的上限（文件 : 行号级）；③ 查「本应工作但没跑的系统」（摘要三张表全是 0 行）；④ 查失败是否走到了关键调用（conversation_route_model_calls 0 行——4 条失败消息根本没走到模型调用）。

第 3 步 · 验证根因：单变量对照实测已证实

复现成功才定根因，不靠日志推测：只改一个变量（环境变量有 / 无、小会话 + 大历史的组合）看输出原文。同时区分有机故障与合成测试——其余上下文失败是合成的长上下文回归测试，不是真实使用，别混进根因。

第 4 步 · 防止复发已证实

回归测试（新测试 PASS 才算修完）；失败诊断开始记真实尺寸（字节数），不再靠重读 DB 猜；流程图与规格文档同步更新；误诊写进长期记忆并标 supersedes，防止旧说法复活。

第 5 步 · 收尾纪律已证实

修完 ≠ 生效 ≠ 合并：写明还要重建镜像 + 更新摘要 + 重启才生效；dev 分支先行，合并等用户点头；SKIP 的测试写明待 CI 跑，不谎称全过。

案例一 · Bug 3：DSH 任务派生失败（根因两次反转）

初始判断（错）2026-11-21/22

「配置的 node 路径 /usr/local/bin/node 在服务器上不存在，bin.mjs 也没装」——把容器内路径当成了宿主机路径，这是误诊的根源。

专用 Docker engine 与 Guardian 服务 active，socket / key 存在；镜像 morde-cloud-runtime:local 里 node 与 bin.mjs（及 bin-account.mjs）都在。模板配置没错，不得「修复」成宿主机路径。

纠正写进记忆2026-11-22

纠正条目标 [correction|high] 并带 supersedes: 指向旧说法，防止复活。

supervisor 用 env -i 起容器并传入 MORDE_WORKSPACE_DIR，而 bin.mjs 的环境白名单只有 PATH / LANG / LC_ALL / TZ / NODE_ENV。对照实测：带该变量 → {"type":"failed","code":"runtime_unavailable"}；不带 → {"type":"ready",...}。邻文件 bin-account.mjs 的白名单里早就有这个变量。

案例二 · 主会话「上下文太多」报错（2026-11-23 00:32）
