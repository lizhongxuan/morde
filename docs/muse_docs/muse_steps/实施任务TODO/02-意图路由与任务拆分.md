## 目标与边界

本步骤负责根据已受理消息选择会话处理方式，并在确有必要时建立新 Task 和计划。上下文装配归第 10 步；工具授权和执行归第 5、4 步；复杂任务的子 Agent 分工和执行归第 3 步；结果回到原会话归第 7 步。

Muse 已观察到的目标体验是：普通问答直接回复原会话；简单工具按需使用，不必因此创建可见的长期 Task；复杂工作进入 Task；进度查询、明确修改或停止只作用于对应任务；关联不清时澄清。以上路由算法和消息归并规则在 Muse 资料中未知。本设计不预设独立 Planner 文件、固定 60 秒归并窗口，也不因缺少验收标准就一律追问。

## Morde 现状与实现依据

Morde 已有分类、非法输出修复/兜底、消息聚合和 Task 创建链路。当前聚合常量为 350 毫秒收集窗口、最长等待为 30 秒；这是 Morde 当前实现，不能推断成 Muse 的规则。先验证现有行为、误归并与遗漏，再决定是否需要改动。测试用例 TC-2.12 记载“无窗口”，和当前源码不一致；开发验收前应按源码更新该探查记录，不能以它作为本步骤实现依据。

代码入口：[ConversationRouteWorker.RunOnce / safeConversationRouteDecision / conversationRouteClassifyFallback](../../../../server/internal/worker/conversation_route_worker.go)、[ClassifyConversationRoute](../../../../server/internal/worker/cloud_dsh_coordinator.go)、[路由动作与上下文判定](../../../../server/internal/app/conversation_route_decision.go)、[ApplyConversationRoute / createConversationRouteTask](../../../../server/internal/store/postgres/conversation_route_actions.go)、[executeTaskPlan](../../../../server/internal/app/cloud_dsh_task_plan.go)。动作只能绑定已受理消息、所属会话和当前任务快照；存储事务重新校验快照、用户范围及任务修订后才应用。

## 路由合同

下表是流程图中的六类产品行为，与 Morde 内部动作的对应关系。`steer` 和 `join` 是现有合同的细分路径，不新增第七种用户意图。

| 流程图行为 | Morde 动作及处理规则 | 不满足条件时 |
|---|---|---|
| 回复 | `reply`；普通问答、问候和表达偏好直接回复原会话，不创建长期 Task、不启动云电脑。 | 缺少必要历史时说明无法确认，不编造。 |
| 查询 | `status`；只读取用户有权查看且明确指向的任务，不启动工具副作用。 | 目标不明、不可访问或候选不完整时询问用户指定任务。 |
| 明确修改 / 停止 | `update` 用于实质修改并发起同一 Task 的修订；`steer` 仅用于对唯一运行中 Task 的低风险补充；`stop` 对指定 Task 发起取消请求，停止完成状态以服务端为准。 | 目标、权限或快照变化时不作用到别的 Task，转为澄清或重新分类。 |
| 简单工具 | 路由到受控工具入口；简单操作可不创建可见的长期 Task。权限、审批、账本由第 4、5 步执行。 | 工具不支持、无权限或需要实质规划时，说明限制或建立 Task；不得编造执行结果。 |
| 新 Task | `new`；用于独立工作或复杂任务，绑定原会话并记录可执行目标、范围、验收条件及预算来源。仅当确实无法安全推定时提问。 | 目标/范围不明且影响执行、安全、成本或不可逆结果时，询问最少缺失信息。 |
| 澄清 / 关联已有请求 | `clarify` 请求最少必要信息；`join` 将同一执行范围内明确重复或补充同一交付物的消息关联到既有请求，保留每条原始消息且不重复执行。 | 仅主题相似不构成合并依据；范围、附件、项目或操作目标不同则独立路由，关系不明则澄清。 |

关键安全边界：`steer` 不能变更计划、执行目标、权限、审批、附件或外部副作用；执行期间可以收到新消息，但修改/停止只影响命中的 Task。任务候选、引用或授权不完整时，先澄清；消息内容只有截断预览时，不据此操作已有 Task。

## Task 计划和依赖

- Task 的执行范围、用户权限和预算由服务端当前 Task/授权确定；模型不能通过计划扩大权限或预算。预算必须标明实际来源，无法确认的费用保持未知。
- `executeTaskPlan` 记录复杂多步骤 Task 的建议计划，并不派发子 Agent，也不替代工具授权。沿用已有 `goal` 与 `steps` 字段（步骤含 `description`、`depends_on`、`outputs`、`completion_criteria`、`status`）；仅在现有合同确实不能表达验收要求时才提出接口改动。计划步骤最多 32 项，每步最多 8 个依赖；实现沿用当前校验和依赖环检查。
- 路由的 `dependency_task_ids` 表示当前新 Task 等待哪些已有 Task；计划步骤的 `depends_on` 表示同一计划内的先后关系。第 3 步的 DSH 子 Agent 派发才开始实际执行；独立工作可并行，共享或互斥资源依赖应串行或隔离。

- [ ] **M02-01（未开始，依赖 M01-01）路由合同与动作规则**：核对并补齐 `conversation_route_decision.go`、route worker 和 `ApplyConversationRoute` 对上表六类行为及 `reply / status / update / steer / stop / new / join / clarify` 的输入、目标、状态和回执映射。模型只给出分类建议；应用侧在事务内校验消息/会话、权限、任务修订和快照。验收：分别覆盖普通问答、查询、修改、停止、简单工具、新 Task、重复/补充请求及澄清；非法动作或陈旧快照不产生任务变更或工具副作用。
- [ ] **M02-02（未开始，依赖 M02-01）目标消歧与执行中接续**：使用现有任务引用、候选集和执行/控制范围校验。`update` 与 `stop` 仅操作明确目标；`steer` 仅附加到同用户、同控制范围/授权/模型和会话条件下的唯一运行任务；`join` 仅关联可合并的同范围请求。候选不全、引用失效、附件/项目/电脑目标不一致或并发修订时不得猜测。验收：两个相似活动任务并行时修改/停止其中一个，另一个继续；陈旧版本、错误账号、范围不同和歧义指代均不误操作。
- [ ] **M02-03（未开始，依赖 M02-01）新 Task 简报与计划衔接**：为复杂任务沿用现有 Task/计划合同记录目标、范围、验收、预算来源和原会话；仅在必要时澄清。计划内依赖交给 Task Plan 表达，已有 Task 依赖使用 `dependency_task_ids`，实际子 Agent 派发交给第 3 步 DSH 协调。验收：复杂多步工作有可核对计划并按依赖执行；简单问答不建 Task、不启动云电脑；简单工具走授权入口；计划不会直接派发或提升权限。
- [ ] **M02-04（未开始，依赖 M02-02、M02-03）聚合及失败路径基线**：按源码验证现有 350 毫秒窗口、最长等待和同执行范围候选的效果，记录重复、补充、独立任务、异范围以及有附件消息的结果；比较错误归并与遗漏后再提改动。分类输出修复失败或模型不可用时沿用当前兜底；无法判定目标必须澄清。验收：不照搬未经证实的 Muse 秒数；不新加相似度算法或合并窗口；无重复任务，歧义消息不静默执行，模型失败不猜目标。若引用 Muse 测试记录，先更正 TC-2.12 与源码的差异。

## 已知缺陷

- 2026-11-23：问“上面那条信息说了什么”时分类四次全败——模型输出非法，四次调用各烧满 512 token 输出上限；兜底又把未解决的前序当成上下文缺失，让用户重发内容，失败传到下一条消息。修复：构造器仍发 512 token 最小窗口预算，DSH 协调器在已解析窗口容纳时按同一拟合校验抬到 2048；可存输出上限 4096 字节提到 16384 字节；非法输出留 1024 字预览进日志与落库行；兜底只在前序记录确实缺失时问“无法确认上下文”。

## 端到端验收

在实际 `morde-pc` 与原生 iOS 各覆盖：普通问答直接回复原会话且不启动云电脑；查询只读；简单工具经受控入口；复杂请求形成 Task 和计划；同一 Task 的追问、明确修改及停止不串线；同话题但不同范围的请求不合并；目标不清或历史不可用时只问必要问题。注入非法分类输出、服务端快照变化和模型失败，核对最终动作、任务/消息归属及服务端状态一致。只使用本地受控测试环境。
