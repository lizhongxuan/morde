## 目标与边界

本步骤负责根据已受理消息选择会话处理方式，并在确有必要时建立新 Task 和计划。上下文装配归第 10 步；工具授权和执行归第 5、4 步；复杂任务的子 Agent 分工和执行归第 3 步；结果回到原会话归第 7 步。

Muse 已观察到的目标体验是：普通问答直接回复原会话；简单工具按需使用，不必因此创建可见的长期 Task；复杂工作进入 Task；进度查询、明确修改或停止只作用于对应任务；用户明确要求停止全部时，只作用于其发起的全部活动任务；关联不清时澄清。以上路由算法和消息归并规则在 Muse 资料中未知。本设计不预设独立 Planner 文件、固定 60 秒归并窗口，也不因缺少验收标准就一律追问。

## Morde 现状与实现依据

Morde 已有结构化分类、非法输出的一次有界修复、安全澄清、消息聚合和 Task 创建链路。模型结构化 `action` 决定自然语言语义；服务端不使用动作/文件关键词清单改写模型的 `new`、`update`、`stop`、`stop_all`、`tool` 或 `reply`。分类失败时 `conversationRouteClassifyFallback` 仅返回上下文缺失/不完整或目标未明的澄清，不执行 Task 动作。当前聚合常量为 350 毫秒收集窗口，最长等待 30 秒；这是 Morde 当前实现，不能推断成 Muse 的规则。TC-2.12 已按源码更新。简单工具首切片仅对明确的只读网页搜索/读取走路由动作 → 短命内部 Task → 现有 Broker，跳过 DSH；内部 Task 保留授权、执行租约和 Broker 账本，但从用户 Task 列表、会话任务面板、任务候选及公开详情/事件入口隐藏，原消息和结果留在会话中且不挂 `task_id`。Workspace、MCP、写入和电脑操作等其他工具仍使用 Task → DSH → Broker，不纳入本次直达实现。此路径是流程图“简单工具直达 Broker”的 Morde 执行实现，不据此断言 Muse 内部实现相同。

## 路由合同

下表是流程图中的六类产品行为，与 Morde 内部动作的对应关系。`steer` 和 `join` 是现有合同的细分路径，不新增第七种用户意图。

| 流程图行为 | Morde 动作及处理规则 | 不满足条件时 |
|---|---|---|
| 回复 | `reply`；普通问答、问候和表达偏好直接回复原会话，不创建长期 Task、不启动云电脑。 | 缺少必要历史时说明无法确认，不编造。 |
| 查询 | `status`；只读取用户有权查看且明确指向的任务，不启动工具副作用。 | 目标不明、不可访问或候选不完整时询问用户指定任务。 |
| 明确修改 / 停止 | `update` 用于实质修改并发起同一 Task 的修订；`steer` 仅用于对唯一运行中 Task 的低风险补充；`stop` 只对明确匹配的单个 Task 发起取消请求；`stop_all` 只接受用户直接、肯定要求停止全部活动任务的请求，并限于当前用户发起的任务。两者都通过 AI 对话自然语言触发，客户端不显示任务停止按钮，最终状态以服务端为准。 | 目标、权限或快照变化时不作用到别的 Task；候选不完整、语义含混、问题/引用文本/否定表达或混合请求时转为澄清。 |
| 简单工具 | 明确的只读网页搜索/读取按需经短命内部 Task 调用现有 Broker，不启动 DSH；内部 Task 只承载调用身份、授权/审批、执行租约和账本，对用户隐藏，结果作为普通助手消息回到原会话。其他工具仍走 Task → DSH → Broker。 | 仅允许 `morde_web_search`、`morde_web_read` 且参数通过服务端白名单校验；无权限、未授权、工具失败或结果未知时如实反馈，不编造结果、不自动重放未知副作用。 |
| 新 Task | `new`；用于独立工作或复杂任务，绑定原会话并记录可执行目标、范围、验收条件及有效预算。仅当确实无法安全推定时提问。 | 目标/范围不明且影响执行、安全、成本或不可逆结果时，询问最少缺失信息。 |
| 澄清 / 关联已有请求 | `clarify` 请求最少必要信息；`join` 将同一执行范围内明确重复或补充同一交付物的消息关联到既有请求，保留每条原始消息且不重复执行。 | 仅主题相似不构成合并依据；范围、附件、项目或操作目标不同则独立路由，关系不明则澄清。 |

关键安全边界：`steer` 不能变更计划、执行目标、权限、审批、附件或外部副作用；执行期间可以收到新消息，但修改/停止只影响命中的 Task。任务候选、引用或授权不完整时，先澄清；消息内容只有截断预览时，不据此操作已有 Task。若预览开头清楚表达了“总结/分析/解释这篇文章”等独立内容处理请求，应建立新 Task，并由 Task Agent 通过授权的当前消息搜索或分段读取工具取回原文；不应要求用户重发已保存的长消息。存在其他 Task 时仅放行无控制或续接意图的明确内容分析；若相同请求的旧 Task 尚在等待或恢复，先说明状态，只有用户明确要求重新开始才绕过重复请求关联。该意图只从用户请求开头判断，不将粘贴原文里的指令当成 Task 控制命令。

## Task 计划和依赖

- Task 的执行范围、用户权限和预算由服务端当前 Task/授权确定；模型不能通过计划扩大权限或预算。路由收件把预算归一后写入 Task；空值使用服务端默认上限。Task 当前不保存“用户指定 / 服务端默认”的来源标记，费用估算保持未知。
- `executeTaskPlan` 保存复杂多步骤 Task 的建议计划，不直接派发子 Agent，也不替代工具授权。沿用已有 `goal` 与 `steps` 字段（步骤含 `description`、`depends_on`、`outputs`、`completion_criteria`、`status`）；仅在现有合同确实不能表达验收要求时才提出接口改动。计划最多 32 步、每步最多 8 个依赖，当前校验引用、重复项及依赖环。Host operation、MCP operation、child spawn、direct-read 与 Hub command 的计划绑定均已有本地 admission/readiness 路径；Hub command 的约束回归曾发现迁移重建丢失 `hub_operation` 分支，已由未部署迁移 `00254` 修复并经隔离 PostgreSQL 复验。模型提交的 `PlanStep.Status=completed` 仍不是结算证据；跨场景/重启及真实 DSH 验收仍待完成。
- 路由的 `dependency_task_ids` 表示当前新 Task 等待哪些已有 Task；计划步骤的 `depends_on` 表示同一计划内的先后关系。M02-03 仅验收计划及两类依赖数据被正确保存；本步骤 M02-14 已接入 Host/MCP/child 与 direct-read 计划门，真实 DSH plan execution 和重启/跨场景验收仍待完成。
