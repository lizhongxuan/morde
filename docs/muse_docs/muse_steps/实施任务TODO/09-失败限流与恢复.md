## Muse 效果与 Morde 现状

Muse 的失败动作保留在任务详情中，后续成功动作与失败并存；失败原因进入任务事件，主对话不展示原始错误。限流响应包含 `retry_after`；只有标明 `terminal_for_attempt` 的连接器动作才结束本次尝试，不能在该次工作里睡眠重试、委派或换动作绕过。需要连接器重连、审批或用户操作时任务暂停等待，之后再继续。Muse 的一般自动重试、降级阈值及失败提示原文未知，不能据此照搬固定次数或等待时间。

Morde 已有 [conversationRouteRateLimitDelay / failRoute](../../../../server/internal/worker/conversation_route_worker.go)、[HandleConversationRouteRateLimit](../../../../server/internal/store/postgres/conversation_route_causality.go)、[cloudDSHModelErrorCategory](../../../../server/internal/worker/cloud_dsh_executor.go)、[Broker.Reconcile](../../../../server/internal/app/cloud_dsh_tool_broker.go)、[模型用量对账](../../../../server/internal/store/postgres/model_usage_admin.go)、任务步骤失败原因及 `retryable` 字段、助手消息的 `interrupted` 状态；[PC Assistant](../../../../web/portal/src/routes/Assistant.tsx)、[iOS MordeApp](../../../../clients/nanoMuse/android/src/ios/Morde/MordeApp.swift) 和 [iOS 任务视图](../../../../clients/nanoMuse/android/src/ios/NanoMuse/MIFTaskViews.swift) 已有对应状态展示。代码存在不等于端到端通过：PostgreSQL 持久化、服务重启和实际 PC/iOS 故障链路仍待验证。

## 接口与参考

- 已有模型/工具错误、工作项及任务状态：将失败阶段、原因码、用户/任务/调用身份、尝试及结果状态写入对应账本或任务事件；耗时沿用实际开始/结束时间。原失败步骤不可被重试覆盖，后续尝试需关联原步骤。原始工具输出只在授权的任务详情中展示；主对话只给简短状态或必要的用户操作提示，不透出原始 Provider 错误、堆栈或凭据。
- 已有 `conversationRouteRateLimitDelay` 与 `HandleConversationRouteRateLimit`：确认的 Provider 429 由路由层现有有限重试负责（最多记录三次被拒调用）。短 `Retry-After` 向上取整；24 小时内的等待写入 `available_after`。超过 24 小时或无法表示的等待会被标为超出持久队列期限，结束当前路由尝试并留失败状态，不截短后自动重派或转成短退避。MCP 连接器只在结构化错误同时满足 `isError`、`code=connector_rate_limited`、`terminal_for_attempt=true` 和整数 `retry_after_seconds`（1–86400）时触发终止；1–86400 秒是 Morde 的输入安全上限，不是 Muse 配额。普通 `isError` 不触发。标记及原始结果保存在现有操作账本，重放时从账本重新判定；Broker 先持久化失败步骤，Worker 校验结果接纳并清理 DSH 请求后将 Task 置失败，在写回 `tool_result` 前停止会话，因此该次尝试不睡眠重试、不委派或换动作绕过，也不按 connector 的 `retry_after_seconds` 自动重排。Muse 资料只证实当次 connector 工作立即终止，没有证据说明后续何时、由谁恢复；Morde 当前 Task 失败后的用户重试入口和恢复节律仍待双端验收，不能宣称已与 Muse 完全一致。没有新增数据库字段或第二层自动重试。
- **路由失败的显式恢复入口：** PC Assistant 与 iOS MordeApp 对本人发起、尚未关联 Task 的失败消息提供“重新处理”操作。服务端复用原消息；同一幂等键重放不创建第二次尝试，新幂等键才递增 `route_attempt`。此入口仅重试消息路由，不适用于已经创建 Task 的连接器失败，也不能绕过未知模型用量或未知工具副作用的对账栅栏。长 `Retry-After` 终止后显示的具体等待提示和 PC/iOS 实际点击链路仍待验收。
- 已有 `Broker.Reconcile`：对已派发的副作用用原调用身份查询；若结果或模型用量未知，先核对工具操作账本或模型用量账本。不能确认时保留 `unknown`、用量预留和等待状态；不能释放预算或盲目重放。只有确认未执行或收到可验证结果，才能决定后续动作。
- 已有流式助手消息和审批等待状态：已展示的部分回复在断流/取消后保留并标为 `interrupted`；任务详情保留失败步骤及后续重试记录。`waiting_user` 的审批、澄清和用户操作等待不应归成失败。
- **本次接口变化：** [AgentToolResult.TerminalForAttempt](../../../../server/internal/app/agent_tools.go) 传递经过严格解析的终止信号；[CloudDSHToolBroker.FailTerminalToolAttempt](../../../../server/internal/app/cloud_dsh_mcp.go) 在 Worker 清理 DSH 请求后提交最终失败状态。普通 MCP 错误仍走原工具结果流程。
- **可适配局部逻辑：**[Hermes `parse_retry_after_seconds / jittered_backoff`](../../../../project/hermes-agent/agent/retry_utils.py) 可改写解析服务端退避提示和带抖动的有限退避；限额、最大次数和时钟以 Morde 自己的策略及实测确定。
- **只参考设计：**[Hermes `classify_api_error`](../../../../project/hermes-agent/agent/error_classifier.py) 参考错误分类；不复制其自动恢复次数、Provider 配额、等待梯子或单机状态。Morde 继续使用 DSH、现有任务事件和账本。

## 端到端验收

使用本地可控的假模型和假工具模拟短/长 `Retry-After`、连接中断、授权失效、执行后丢回执、模型用量未知、对账失败、取消及审批等待；PC 必须从实际 `morde-pc` 客户端入口检查简短提示、失败详情、已显示文本和真实任务状态，React/浏览器测试只能作为组件证据，不能替代客户端验收；iOS 从原生客户端验收。使用隔离的本地服务、测试账号和客户端数据目录，不操作已有用户会话。重启后核对原失败事件、调用次数、持久等待时间、预算保留及账本对账结果。不要用真实外发连接器测试；环境或账本无法观测时将对应验收标为待验证。
