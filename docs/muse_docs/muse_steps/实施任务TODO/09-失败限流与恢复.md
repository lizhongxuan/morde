## Muse 效果与 Morde 现状

Muse 的失败动作保留在任务详情中，后续成功动作与失败并存；失败原因进入任务事件，主对话不展示原始错误。限流响应包含 `retry_after`；只有标明 `terminal_for_attempt` 的连接器动作才结束本次尝试，不能在该次工作里睡眠重试、委派或换动作绕过。需要连接器重连、审批或用户操作时任务暂停等待，之后再继续。Muse 的一般自动重试、降级阈值及失败提示原文未知，不能据此照搬固定次数或等待时间。

Morde 已有 [conversationRouteRateLimitDelay / failRoute](../../../../server/internal/worker/conversation_route_worker.go)、[HandleConversationRouteRateLimit](../../../../server/internal/store/postgres/conversation_route_causality.go)、[cloudDSHModelErrorCategory](../../../../server/internal/worker/cloud_dsh_executor.go)、[Broker.Reconcile](../../../../server/internal/app/cloud_dsh_tool_broker.go)、[模型用量对账](../../../../server/internal/store/postgres/model_usage_admin.go)、任务步骤失败原因及 `retryable` 字段、助手消息的 `interrupted` 状态；[PC Assistant](../../../../web/portal/src/routes/Assistant.tsx)、[iOS MordeApp](../../../../clients/nanoMuse/android/src/ios/Morde/MordeApp.swift) 和 [iOS 任务视图](../../../../clients/nanoMuse/android/src/ios/NanoMuse/MIFTaskViews.swift) 已有对应状态展示。仍需验证错误事件、模型/工具账本、服务重启及双端真实故障链路是否一致。

## 接口与参考

- 已有模型/工具错误、工作项及任务状态：将失败阶段、原因码、用户/任务/调用身份、尝试及结果状态写入对应账本或任务事件；耗时沿用实际开始/结束时间。原失败步骤不可被重试覆盖，后续尝试需关联原步骤。原始工具输出只在授权的任务详情中展示；主对话只给简短状态或必要的用户操作提示，不透出原始 Provider 错误、堆栈或凭据。
- 已有 `conversationRouteRateLimitDelay` 与 `HandleConversationRouteRateLimit`：确认的 Provider 429 由路由层现有有限重试负责（当前最多记录三次被拒调用）。调用前必须尊重 `Retry-After`；若等待超过该路径可接受的两分钟，当前实现会把等待归零，而存储层仍可能重排重试，需在 M09-02 明确改为持久等待或结束本次尝试，不能立即重试。连接器显式给出 `terminal_for_attempt` 时只终止当前工作项；不得在同一次尝试内睡眠、重试、委派或切换替代动作。Muse connector 的每分钟配额不复制到 Morde。
- 已有 `Broker.Reconcile`：对已派发的副作用用原调用身份查询；若结果或模型用量未知，先核对工具操作账本或模型用量账本。不能确认时保留 `unknown`、用量预留和等待状态；不能释放预算或盲目重放。只有确认未执行或收到可验证结果，才能决定后续动作。
- 已有流式助手消息和审批等待状态：已展示的部分回复在断流/取消后保留并标为 `interrupted`；任务详情保留失败步骤及后续重试记录。`waiting_user` 的审批、澄清和用户操作等待不应归成失败。
- **可适配局部逻辑：**[Hermes `parse_retry_after_seconds / jittered_backoff`](../../../../project/hermes-agent/agent/retry_utils.py) 可改写解析服务端退避提示和带抖动的有限退避；限额、最大次数和时钟以 Morde 自己的策略及实测确定。
- **只参考设计：**[Hermes `classify_api_error`](../../../../project/hermes-agent/agent/error_classifier.py) 参考错误分类；不复制其自动恢复次数、Provider 配额、等待梯子或单机状态。Morde 继续使用 DSH、现有任务事件和账本。

## 任务

- [ ] **M09-01（未开始，依赖 M04-01）失败事实与记录归属**：核对 route worker、执行器、Broker、`task.step`/`task.operation` 事件和错误投影，持久记录失败阶段、稳定原因码、任务/调用身份、尝试及真实结果；不覆盖原失败项。PC/iOS 的任务详情显示失败步骤和后续成功步骤，主对话不暴露原始错误或凭据。验收：同一任务先失败再成功，两步及各自证据均保留；不同账号/任务不能读到事件；普通用户能看到简短状态和必要操作提示。
- [ ] **M09-02（未开始，依赖 M09-01）限流与安全重试**：保留 Provider 429 的路由层有限重试和现有调用账本；符合范围时尊重 `Retry-After`，超过两分钟时改为持久等待或结束本次尝试，修复“delay 归零后仍重排”的路径；连接器若返回 `terminal_for_attempt`，当次工作立即终止，不睡眠、不重试、不委派、不换动作。不得叠加多个自动重试层。验收：模拟短 `Retry-After` 按时间再试；模拟五分钟等待不立即重试；明确终止标记只执行一次；取消、撤权和预算耗尽均不再派发；重启后遵守原调用身份和等待时间。
- [ ] **M09-03（未开始，依赖 M04-04、M09-01）操作与用量未知先对账**：通过 `Broker.Reconcile` 和现有模型调用账本查明已派发操作、结果及用量；核对 `unknown` 用量的预算保留与管理员对账入口。对无法查询的副作用或 Provider 结果保留未知状态和预算预留，不自动重放或错误释放。验收：模拟操作已成功但回执丢失、模型用量未知、对账失败三种情况；前两者经账本确认后只结算一次，无法确认时明确等待且不产生第二次副作用/模型请求。
- [ ] **M09-04（未开始，依赖 M09-02、M09-03）中断、等待与双端呈现**：核对 PC Assistant 与 iOS MordeApp 对断流、用户取消、授权失效、`waiting_user`、任务失败和结果未知的展示及恢复行为。已展示文本保留并标中断；审批/澄清等待不是失败；有安全恢复条件时按持久状态继续，需用户操作时等待用户。验收：故障注入后 PC/iOS 状态一致；审批任务不显示失败，用户批准后只执行一次；中断回复可见已生成部分且不会冒充完整回复；失败细节保留在任务详情。

## 端到端验收

使用本地可控的假模型和假工具模拟短/长 `Retry-After`、连接中断、授权失效、执行后丢回执、模型用量未知、对账失败、取消及审批等待；在实际 PC 和原生 iOS 检查简短提示、失败详情、已显示文本和真实任务状态。重启后核对原失败事件、调用次数、持久等待时间、预算保留及账本对账结果。不要用真实外发连接器测试；环境或账本无法观测时将对应验收标为待验证。
