## Muse 效果与 Morde 现状

Muse 的失败动作保留在任务详情中，后续成功动作与失败并存；失败原因进入任务事件，主对话不展示原始错误。逆向资料还确认两类不同恢复：`terminal_for_attempt` 限流立即结束当次尝试，不能在该次工作里睡眠重试、委派或换动作绕过；durable 外部阻塞（如连接器需重连、设备离线）会暂停，并在下一轮检查时再试，只有用户能完成的操作仍等待用户（TC-9.3–9.5）。这不代表限流终态也会自动重排；Muse 的一般错误重试次数、固定轮询间隔、降级阈值及失败提示原文未知，不能据此照搬。

## 接口与参考

- 已有模型/工具错误、工作项及任务状态：将失败阶段、原因码、租户/账号范围、用户/任务/调用身份、尝试及结果状态写入对应账本或任务事件；耗时沿用实际开始/结束时间。这里要求能按租户/账号归属安全查询，不要求新增字段（先复用现有 owner/tenant 身份及授权边界，若字段不足再单独评估）。工具调用在模型响应校验阶段被拒时，结构化记录阶段、类别、原因码、工具名、有效调用 ID 和 `tool_dispatched=false`，方便从 Task ID 定位；工具执行异常导致执行结果无法确认时，日志记录工具名、调用 ID、派发状态、稳定失败原因码和底层错误类型，Task 操作账本保留操作状态供对账。不得将工具参数、原始模型内容、原始错误文本或凭据写入通用日志。原失败步骤不可被重试覆盖，后续尝试需关联原步骤。原始工具输出只在授权的任务详情中展示；主对话只给简短状态或必要的用户操作提示，不透出原始 Provider 错误、堆栈或凭据。
- 已有 `conversationRouteRateLimitDelay` 与 `HandleConversationRouteRateLimit`：确认的 Provider 429 由路由层现有有限重试负责（最多记录三次被拒调用）。短 `Retry-After` 向上取整；24 小时内的等待写入 `available_after`。超过 24 小时或无法表示的等待会被标为超出持久队列期限，结束当前路由尝试并留失败状态，不截短后自动重派或转成短退避。MCP 连接器只在结构化错误同时满足 `isError`、`code=connector_rate_limited`、`terminal_for_attempt=true` 和整数 `retry_after_seconds`（1–86400）时触发终止；1–86400 秒是 Morde 的输入安全上限，不是 Muse 配额。普通 `isError` 不触发。标记及原始结果保存在现有操作账本，重放时从账本重新判定；Broker 先持久化失败步骤，Worker 校验结果接纳并清理 DSH 请求后将 Task 置失败，在写回 `tool_result` 前停止会话，因此该次尝试不睡眠重试、不委派或换动作绕过，也不按 connector 的 `retry_after_seconds` 自动重排。针对这种 `terminal_for_attempt` 限流，Muse 资料只证实当次 connector 工作立即终止，未证实该限流终态后续由谁或何时恢复；TC-9.5 的 durable 外部阻塞“下一轮再试”是另一种状态，按 M09-02.1 单独映射。Morde 的 Task/MCP 用户重试入口已分别从 PC、iOS 原生客户端闭环到本地 Morde 服务/PostgreSQL（见 S09-4、S09-6），但使用的是合成连接器，不等于真实连接器或跨端一致性验收。没有新增数据库字段或第二层自动重试。
- **路由失败的显式恢复入口：** PC Assistant 与 iOS MordeApp 对本人发起、尚未关联 Task 的失败消息提供“重新处理”操作。服务端复用原消息；同一幂等键重放不创建第二次尝试，新幂等键才递增 `route_attempt`。此入口仅重试消息路由，不适用于已经创建 Task 的连接器失败，也不能绕过未知模型用量或未知工具副作用的对账栅栏。本轮已在隔离本地服务上从 `morde-pc` 实际点击验证长限流失败后重试；iOS 原消息路由失败显式重试已通过本地 Morde 服务/PostgreSQL 闭环（见 S09-7）；Task/MCP 原生 UI 已从点击重试闭环到本地 Morde 服务与 PostgreSQL（合成连接器 fixture，见 S09-6）。
- **Task 步骤重试接口：** 已有 `POST /api/tasks/{task_id}/steps/{step_id}/retries`，请求带 `expected_task_revision`、`expected_attempt` 和 `Idempotency-Key`；当前接纳已完成 Task 中确认未派发的 Host 工具步骤，以及失败 Task 中由唯一、精确的 MCP 操作账本证明已终止限流的步骤。账本中的 `call_id`、工具名、请求摘要、Task revision 和结构化限流标记必须全部匹配；重试时间取账本结果的 `updated_at + retry_after_seconds`。MCP 限流终态先于 Agent 进程树停止确认，因此只有匹配的 Agent 停止收据/Guardian 停止证明已落库后，详情才开放重试且 API 才接受重试，避免新一代 Agent 与旧进程树重叠。MCP 连接器重试本身不依赖 Host；无 Host 仅在精确终止限流账本、无 Workspace 目标等约束全部满足时允许，Host 工具和 Workspace 操作仍须经过原 Host fence。重试使用新的尝试步骤和调用身份，重新检查授权/审批，并永久保留来源失败步骤。未知副作用、未结算模型调用、其它待派发操作、撤权或待审批均拒绝新重试。已消费的重试 intent 在审批恢复或进程重启后只允许按相同 immutable intent、调用身份和操作账本继续；MCP Broker 仅在来源/调用/参数摘要完全匹配时复用预留的重试步骤行，账本负责防止重复副作用。此合同不扩大消息路由重试入口的适用范围。
- 已有 `Broker.Reconcile`：对已派发的副作用用原调用身份查询；若结果或模型用量未知，先核对工具操作账本或模型用量账本。不能确认时保留 `unknown`、用量预留和等待状态；不能释放预算或盲目重放。只有确认未执行或收到可验证结果，才能决定后续动作。
- 已有流式助手消息和审批等待状态：已展示的部分回复在断流/取消后保留并标为 `interrupted`；任务详情保留失败步骤及后续重试记录。`waiting_user` 的审批、澄清和用户操作等待不应归成失败。端到端双端验收须核对 PC 与 iOS 读取同一 Task、同一 assistant message ID、相同已显示前缀和 `interrupted` 状态；若中断时另有已派发操作，仍须按原操作身份对账，未确认前保持 `unknown`、预算预留和无重派。
- **本次接口变化：** [AgentToolResult.TerminalForAttempt](../../../../server/internal/app/agent_tools.go) 传递经过严格解析的终止信号；[CloudDSHToolBroker.FailTerminalToolAttempt](../../../../server/internal/app/cloud_dsh_mcp.go) 在 Worker 清理 DSH 请求后提交最终失败状态。普通 MCP 错误仍走原工具结果流程。任务级安全恢复沿用并收紧现有 `TaskStepRetry` 接口，不新建第二套恢复 API。
- **可适配局部逻辑：**[Hermes `parse_retry_after_seconds / jittered_backoff`](../../../../project/hermes-agent/agent/retry_utils.py) 可改写解析服务端退避提示和带抖动的有限退避；限额、最大次数和时钟以 Morde 自己的策略及实测确定。
- **M09-02.1 DSH checkpoint 参考边界：**本地 [DSH `session-checkpoint-policy.apply`](../../../../project/deepseek-harness/packages/session/session-checkpoint-policy/src/index.ts) 在模型请求、顶层工具副作用和 `agent/pre-step` 前调用 session flush；[DSH `SessionPersistence.open/read/flush`](../../../../project/deepseek-harness/packages/session/session-persistence/src/index.ts) 提供既有事件日志的恢复接口。Morde 的 [runtime `engine.mjs`](../../../../runtime/morde-cloud-runtime/src/engine.mjs) 已接入这两个 DSH 插件及自有 `WorkerSessionPersistence`；Task/checkpoint fence 和 blocker claim 条件仍由 Morde Store 管理。可复用的是同一 DSH session/checkpoint 语义，不移植或推断自动 blocker retry；上游插件没有 connector/device health classification。
- **只参考设计：**[Hermes `classify_api_error`](../../../../project/hermes-agent/agent/error_classifier.py) 参考错误分类；不复制其自动恢复次数、Provider 配额、等待梯子或单机状态。Morde 继续使用 DSH、现有任务事件和账本。

## 对最终流程图的恢复决策补充

以下是 Morde 的实现与验收合同，用于把第 09 步的状态边界统一起来；Muse 未披露的自动恢复时机、次数和降级阈值仍不作推断。

| 场景 | 持久状态与用户呈现 | 允许的恢复动作 |
| --- | --- | --- |
| 模型返回未授权工具或不合法调用，且能确认尚未派发 | 记录阶段、原因码、工具名及 `tool_dispatched=false`；主对话给简短安全提示，Task 详情保留失败步骤 | 不执行被拒调用；只允许现有路由/响应校验合同内有界恢复，不得把失败调用伪装成已执行 |
| Provider 路由返回 429 | 在路由账本保留被拒调用；24 小时内持久化 `available_after`，超限则结束当前路由尝试并在原消息显示失败 | 仅由现有路由 Worker 在持久期限后继续，最多记录三次被拒调用；超期限后由用户从原消息显式重新处理，复用原消息及幂等规则 |
| MCP 连接器返回精确的终止限流标记 | 操作账本和失败 Task 步骤保留原调用身份、结构化结果及 `retry_after_seconds`；Task 详情显示等待期限，主对话不暴露原始错误 | 本次 Agent 尝试立即停止；不睡眠重试、不委派、不换工具绕过、不后台重排。用户重试须等期限到达且账本、Agent 停止凭据、Task revision、授权/审批和预算全部复核通过 |
| 工具已派发或模型调用已发出，但结果/用量无法确认 | 保持 `unknown` 与必要的预算预留；原对话如实说明结果未确认及最后确认的工作，不使用已移除的机械状态行 | 先按原调用身份对账；没有可验证结论时继续等待，不释放预留、不创建新调用、不开放重试 |
| 审批、授权恢复或其他必须由用户完成的前置条件未满足 | Task 为 `waiting_user`，不记作执行失败；界面说明所需用户操作 | 条件满足后从同一 Task/检查点继续，并重新核验当前授权、审批和预算；不创建重复尝试或重放已确认副作用 |
| 流式回复断开或用户取消 | 保留已展示文本并标记 `interrupted`；若期间有已派发操作，另按 `unknown` 对账 | 不把部分文字标成最终答案；恢复前先核对取消结果和已派发操作，不因客户端重连而重复执行 |

验收时逐类核对“持久状态 → 用户可见状态 → 可执行恢复动作”一致；错误详情只在授权的任务详情内展示，主对话不得泄漏 Provider 原始错误、堆栈、工具参数或凭据。
