## Muse 效果与 Morde 现状

完成任务后用真实检查、读回或 checking worker 对照目标确认结果，用户能区分已执行、验证通过、失败与证据不足。模型自述、文件存在、文件哈希或“执行完成”本身不证明内容正确。

现有 [reviewInput](../../../../server/internal/worker/task_validation_review_worker.go) 的审核输入是 `artifact_metadata_only`，不能单凭它验证产物实际内容；[EvaluateTaskValidationReview](../../../../server/internal/app/task_validation_verdict.go) 和 [验证存储](../../../../server/internal/store/postgres/task_validation_review.go) 已有判定与记录基础，需补可核查内容和事实。

## 接口与参考

- 已有 `GetTaskValidationReviewStepDetail`、`OpenTaskArtifactContent`：前者供受控验证读取步骤证据，后者有用户可见/已验证产物约束，不能简单复用于验证前读取。**拟新增或扩展内部受控读取合同**：仅验证 worker 按当前 claim 获取授权范围内的证据/产物，绑定用户、任务修订、尝试、来源调用、环境/工作区版本与内容哈希；失权、过期或版本不一致拒绝，不能泄漏给其他任务。具体入口以实现时核对现有代码后确定。
- 已有 `EvaluateTaskValidationReview`：输入应包含可核验的实际检查与来源，输出通过、失败或待验证；存储和结果发布消费同一状态，不能把执行完成自动当验证通过。
- **可适配局部逻辑：**[Magentic-UI `decide_verifier_class`、`parse_stat_output`、`diff_states`](../../../../project/magentic-ui/src/magentic_ui/teams/omniagent/_verifier.py) 的操作前后检查和差异计算可按 Morde 的工具/文件证据格式改写；不以此替代业务内容检查。
- checking worker 可以用 DSH 子会话完成独立核对，但“必须使用另一模型”并无 Muse 证据，也不能替代可复现的检查。

## 端到端验收

使用本地合成任务分别制造正确文件、错误内容、运行失败、无权限读取和产物变更；通过实际 PC/iOS 查看任务的执行与验证状态及证据来源。不得为了验证向外发送文件。
