# 五会话复杂链路设计与交接

本文补充[并发总览](<00-并发实施总览.md>)及 A–E 任务中跨层链路的设计；目标仍以[最终流程](<../Morde 复刻 Muse 最终流程与开发设计.md>)、[一体化方案](<../Morde 复刻 Muse 一体化实施与验收 TODO.md>)和 `AGENTS.md` 为准。**下面的接口字段、事件与状态流是待定稿的 Morde 设计，不是已经实现的能力，也不声称是 Muse 内部算法。**现有代码与提案冲突时先记录问题，由 A 统一调整合同、调用方与测试；不能把本文当作缺失的服务端权威合同直接改库。

## 0. 实施次序与交接

A–E 的第一批可同时进行基线审查及不依赖新合同的工作；跨层实现按以下最小交接推进，接到一项即可继续，不必等待整份任务文档完成。

| 顺序 | A 的交付及接收方 | 可并行工作 |
|---|---|---|
| 1 | A 确认消息/Task/授权/预算现状与各文件所有者；B、C、D 核查自身消费端。 | E 验现有 PC 交互；B/C/D 做本地复现与回归。 |
| 2 | A 与 B 定稿路由和计划依赖身份；与 C 定稿长消息投递及 checkpoint；与 D 定稿验证来源、终态投递及预算身份。每项单独发布。 | C 实现可独立验证的读取和压缩；D 处理确定失败回送；E 接现有审批和工作项事实。 |
| 3 | B/C/D 分别接入各自合同，A 补公共 Store/API/迁移；C 与 E 对接同步快照和真实 Host 回执。 | B-02 协作、C-02 记忆和同步、E-01 UI 可随相应合同稳定推进。 |
| 4 | A 和 E 联验 T01–T59；D 把失败与验证事实交回原对话；C、B 处理联调缺陷。 | A-02 可提前将有效中间结果给 D-02，不等待全部工作关闭。 |

交接最小内容：**版本/文件、输入输出、持久身份、权限与失效条件、失败/unknown 行为、调用方及可重放测试**。公共类型、迁移、状态或 API 由 A 按 `server/AGENTS.md` 同步权威合同、实现和测试；本设计不是权威合同的替代品。未能确定的条款记录阻塞，相关会话继续独立项。

## 1. 会话路由与计划依赖：A-01 / B-01

**现状：**[`task.Plan.Validate`](<../../../../server/internal/domain/task/plan.go>) 校验计划结构和无环；[`executeTaskPlan`](<../../../../server/internal/app/cloud_dsh_task_plan.go>) 保存 Agent 提交的计划及其修订，`completed` 仍只是模型给出的计划状态。A-01 的迁移 `00244_task_plan_step_execution_bindings.sql` 与 Store adapter 将 plan step 绑定到现有 tool/MCP/child 执行 ledger，并从真实结算状态读取 readiness；CloudDSH tool schema 携带 plan step ID/revision，Broker 校验后，Host operation、MCP operation dispatch 与 child spawn 在对应持久化事务内检查 readiness。跨 Task 的 `dependency_task_ids` 与计划内 `depends_on` 是两类不同依赖。该 gate 证明的是计划前置步骤结算，不能替代 H07 对适用检查、覆盖范围和不可变 Workspace 版本的验证。

**拟定设计：**

1. 会话语义由路由 Agent 给出结构化 `reply/new/update/stop/tool/clarify` 等动作；应用层重新校验 owner、会话、目标 Task、当前授权、Task 修订和幂等。关联不明确只问缺失的最少信息；同话题不自动合并，纯文字问答不建 Task 或启动电脑。
2. 对**有执行依赖的计划步骤**，绑定 `(task_id, task_revision, plan_revision, plan_step_id)`，并将其本次实际工具调用或子 Agent 身份与现有 operation/child ledger 关联。绑定和派发准入须在同一版本及授权栅栏下生效；不可只在 UI 上标记或信任模型填的 `completed`。没有依赖的简单工作不强制创建计划。
3. 依赖步骤仅在所需前置结果有真实成功/结算证据时放行；前置失败、取消、unknown、授权失效或证据不完整时保持阻塞并记录原因，独立步骤可继续。跨 Task 依赖仍检查同一用户、会话、项目及前置修订，不能用计划步骤结算代替。
4. 保存新计划会增加 `plan_revision`。已派发操作继续按原身份对账，不因修订重放；新计划不得直接消费旧修订的成功状态。若仅状态更新而需复用证据，A/B 须定义基于目标、参数、范围和原始结算事实的显式重绑规则，无法证明一致就重新验证，不靠步骤标题猜测。

**交接与验收：**B 提出决策字段、依赖绑定点及失败返回；A 定稿公共字段和持久化，B 接入路由/计划，C 接入 Runtime 会话树的子 Agent 调用。T05–T08、T45–T46 分别覆盖同名不同任务、前置失败/unknown、两个独立步骤并行、新修订、重放和撤权；本地证据、实际 PC 和真实模型分开记录。

**合同状态：**公共 R25/H07 语义已在 [`docs/实施/00-总览与公共约定.md`](../../../实施/00-总览与公共约定.md) §6.1 定为 v1；本节目标流程与之对齐。M02-14 的计划修订身份及依赖 gate 已接入。A/B/D 仍需接通 H07 专属的计划检查身份、覆盖范围、不可变 Workspace 版本与 review facts；在这些字段绑定并通过修订失效测试前，修复验证保持 pending。

1. 用户已选择按需验证。B 的计划记录目标、授权范围和适用检查；用户或项目明确要求的检查不得省略。若没有此类要求，红测与全量套件是按具体风险和可行性选择的手段，不是所有修复的固定写入/完成条件。复现不可得、检查不可运行或失败时，原对话说明实际修改、原因和未满足项，不能声称已通过或把必需检查标为完成。
2. A 统一审查 E03/E06/E07 所用 Broker、`cloud_dsh_failing_test_gate.go`、`cloud_dsh_minimal_diff_gate.go` 和 `cloud_dsh_test_gate.go`；B 负责计划语义及其专属接口，D 负责验证事实与 H07。改动必须同步写入/完成/复核及调用方，而不是删除某个门就让未经检查的结果通过。计划需新增必要文件时，由 Agent 更新当前计划并重新校验授权与版本；计划名单或影响图不能扩大用户授权。已派发 unknown 先对账。

4. R26 的来源引用复用工具的真实读取结果、当前用户权限和现有产物 proof；保留可获得的来源版本与位置，未读、不能定位或撤权时说明限制。B/C 分别核对工具与 Runtime 对外部内容的信任边界；A 保持 Broker 的实际授权/审批/账本，D 输出报告要点与依据，E 展示。仓库/网页/附件伪称的授权不成为新权限；用户明确要求按文档执行时，在请求和既有授权范围内执行相关内容，正常分析不能被一律拒绝。

**交接与验收：**A 持有三处门禁和公共合同，B 持有计划/工具专属代码，C 持有 Runtime，D 持有独立验证/交付，E 独占实际 PC 操作；公共状态、迁移、跨层接口若受 `server/AGENTS.md` 约束先同步权威合同，缺项标阻塞。T58 覆盖按需检查、明确要求、失败/不可运行和修订失效；T57/T59 覆盖正常资料分析、不可信指令夹具、来源定位及撤权。各层均未运行，不能以本文设计宣称已实现。

## 2. 长消息、追问与恢复：A-01 / B-01 / C-01

**现状：**迁移 `00241_task_agent_message_delivery_receipts.sql` 为逐条消息保存 source/manifest/attachment/representation 摘要、Task revision、Agent generation 与 applied checkpoint。Postgres Store 为每个 pending message 构造 receipt，并提供绑定当前 Task/授权/消息与 source SHA 的分页读取；Worker 对超 128 KiB inline 上限的初始消息、followup、steer 和恢复批次生成有界 reference，Runtime 验证 reference envelope 与 outer fence 并从 checkpoint 恢复。Store、Worker 和 Runtime 的局部测试已运行；`applied` 只证明 checkpoint 接受该 envelope，不证明模型读完正文。见 [`cloud_dsh_session_tree.go`](<../../../../server/internal/worker/cloud_dsh_session_tree.go>)、[`engine.mjs`](<../../../../runtime/morde-cloud-runtime/src/engine.mjs>) 与 [`agent_message_sources.go`](<../../../../server/internal/store/postgres/agent_message_sources.go>)。真实 DSH/模型语义和实际 PC 长消息/恢复仍未验收。

**拟定设计：**

1. 收件与分块仍保留原始 `message_id`、原文、字节长度、SHA-256、顺序和附件；大消息可投递时，服务端为**每条需要外置的消息**生成并验证来源/分页 manifest，绑定 owner、会话、Task、消息、授权和相应修订。不能把首条消息的 manifest 当作后续 steer 的正文。
2. 在 Worker ↔ Runtime ↔ checkpoint 的合同中引入版本化、有界的原文引用表示：原文身份/哈希与投递表示指纹分开，连同附件、`followup/steer`、消息次序、Agent generation 及修订共同校验。短指针或提示词不可替换原正文后仍沿用旧的精确正文匹配；短消息及已有 checkpoint 的可恢复性由 A/C 先验证，再定兼容策略。
3. 首条、运行中 followup、superseding steer 和 `revision_messages` 批次使用同一来源身份与授权规则；批次按原顺序提交，不能因总体超帧上限丢失任一条，也不能使新 steer 错绑到先前任务或调用。受影响读取工具须明确请求的 message ID/哈希与版本，跨消息不能复用前一条的已读进度。
4. checkpoint 与 delivery ledger 共同证明消息已被接收/应用；**已投递不等于全文已处理**。需要全文分析时，按来源页和完整顺序记录实际读取覆盖及摘要，结合模型窗口和预算分段处理；检索型问题可返回有限匹配，但不能冒称读完全篇。损坏、缺页、撤权或预算不足时说明已处理/未处理范围，保留原始记录。
5. 投递前、发送后但 checkpoint 前、checkpoint 已提交但 Worker 崩溃等情况下，以相同身份恢复并核对已投递证据；状态或副作用未知先对账，不重复追加消息、不重放已确认动作。

**交接与验收：**A 持有身份/存储及预算合同，C 改 Worker、Runtime、读取工具和 checkpoint，B 确保长补充正确路由，E 操作实际 PC。T49/T50 除首条外须覆盖 **128 KiB+1 / 1 MiB 的 followup、steer、恢复批次**、多条批次总量超限、特殊 Unicode、重连、缺页和撤权。实际模型正例要验证首/中/尾及全文覆盖；固定回复只证明投递链路。

## 3. 验证失败、终态和原对话交付：A-01 / D-01 / D-02 / E-01

**现状：**[`CommitTaskProgress`](<../../../../server/internal/store/postgres/task_execution.go>) 和 [`CompleteTaskStop`](<../../../../server/internal/store/postgres/task_stop.go>) 是终态事实的现有事务边界；[`publishConversationResultReviewInTx`](<../../../../server/internal/store/postgres/conversation_result_review.go>) 只处理当前 `completed` 结果。[`CompleteTaskValidationReview`](<../../../../server/internal/store/postgres/task_validation_review.go>) 更新验证记录且不另写验证结果 Task 事件；D-01 现会在同一事务为已发布结果写入独立 `late_validation` outbox source，绑定原 `task.result` 序号/摘要、claim generation 和 verdict 摘要。晚到 FAIL 不应假定已有新的 Task `event_sequence`；首次结果尚未发布时由既有结果整理路径读取当前验证状态。

**当前实现切片（2026-11-25）：**迁移 [`00240_task_terminal_delivery_outbox.sql`](<../../../../server/migrations/00240_task_terminal_delivery_outbox.sql>) 建立独立持久 outbox；[`task_terminal_delivery_outbox.go`](<../../../../server/internal/store/postgres/task_terminal_delivery_outbox.go>) 在 server Task 的 `CommitTaskProgress` 失败、`CompleteTaskStop` 确认取消以及无审批/澄清卡片承载的选定持久等待事务内写入 source。D-01 在已发布结果的验证复核事务中写入 `late_validation` source，并让未发布首回执读取当前验证结论。A 已提供 claim/lease、current source 失效、unknown、加密 `reply_ready`、budgeted ModelGateway 调用接口；D 已接入受摘要校验的 source facts、消费 Worker 和原会话发布。当前 App/Worker 与隔离 PostgreSQL 定向组通过；真实 PC/DSH 请求尚未显示回复，端到端验收未通过。

**实施状态与设计：**

1. 已确定且能安全处理的工具失败，先以脱敏的真实结果交回原 DSH Session；保留失败工作项。授权等待、取消中、确定失败和已派发 unknown 分开处理，unknown 先按原调用对账，合并到另一任务本身不是失败。
2. 对不可恢复失败，A 在 `CommitTaskProgress` 的终态事件/中断快照事务中写入独立终态投递 outbox；取消仅在 `CompleteTaskStop` 确认 Agent 已停、操作已对账并提交取消终态后入队。source row 以 `(task_id, source_event_sequence, source_event_type)` 去重并绑定 owner、会话、Task 修订、授权版本和事件摘要。claim/lease、稳定 source identity、authorized reply fence 与 published message identity 已接入；不能将失败伪装成 `completed`，也不能将状态通知伪装成用户消息送入普通路由。
   对结果 unknown、额度不足等**需要告知用户且没有现成审批/澄清卡承载的持久等待**，复用同一投递机制并绑定该 `task.waiting_user` 事件，明确称“等待核对/处理”，不能写成终态失败；恢复、用户新指令或授权变化后旧等待说明须失效。同一等待事件重启不重复通知，审批和澄清仍走既有卡片，短暂可自动恢复的等待不制造消息噪音。已选定的持久等待 writer 与 source consumer 已接入。
3. 晚到 FAIL 使用当前验证 claim、结果事件序号/哈希及修订核对来源。**不新增 Task 事件；在验证结论事务中写入独立的 `late_validation` outbox source**，键包含原结果事件序号、结果哈希、claim generation 和 verdict 摘要，避免冒造事件序号。该 source writer 已由 D-01 接入已发布结果的验证事务，source consumer 也已接入；若结论在首次结果交付前已进入该结果，不再发第二条通知，首次结果整理路径读取已持久化的验证状态。PostgreSQL 回归验证了验证先完成时 FAIL 进入首回执，以及发布事务持锁时验证 completion 等待后生成一条晚到 source。
4. Worker 使用租约/generation 领取条目，读取限长、摘要校验且不含原始工具输出的 facts，并在 ModelGateway 与预算账本内以稳定 `terminal_delivery_<delivery_id>` 调用生成自然语言说明。流程为：持久领取 → 绑定稳定模型调用 ID / 预算预留 → 派发并记录结果或 unknown → 加密持久化 `reply_ready` → 重核来源/授权/修订/steer 后发布或失效。已结算响应在发布前崩溃时恢复持久候选，不重新派发；派发或用量 unknown 时先按原账本对账。模型/额度不可用时可发布明确标为系统事实的回退，不冒称 AI 生成；不在日志中记录模型原文、敏感事实或凭据。
5. 原对话写入前再次核对事件、授权、当前修订与后续 steer；过期条目标记失效而不覆盖新结果。发布回退须使同一条目的晚到模型结果无法再次发布，未知用量仍按原账本对账。重复 claim、崩溃、重连或晚到模型结果都不能造成多条同源通知；事实不明明确写“尚未确认”，已完成内容和可安全继续的方式如实呈现。

**交接与验收：**A 负责终态事务、事件/outbox 的事务内接口、网关预算及权威合同；`task_validation_review.go` 仍由 D 独占，D 在已有验证完成事务中调用 A 交付的接口，不由 A 另开事务写验证结果。D 负责验证事实、生成/恢复和交付编排；E 展示同一会话的持久消息。T47/T48/T55/T56 增加“发布前后到达 FAIL”、两条路径并发、claim 崩溃、重复事件、撤权、模型用量 unknown 和用户补充后失效。一次成功执行不等于验证通过，合成回复不等于真实 Agent 验收。

<a id="approval-activity"></a>
## 4. 审批卡、通用资源和工作项：A-01 / D-01 / E-01

**现状：**[`TaskApprovalMcpApp`](<../../../../web/portal/src/components/TaskApprovalMcpApp.tsx>) 已将内置审批视图放入沙箱 iframe，并仅桥接 `respond_to_task_approval`；它尚不是任意外部 MCP UI 资源的通用宿主。现有审批响应入口为 `POST /api/tasks/{id}/approvals/{approval_id}/responses`；对话和审核区应读同一持久决定。

**拟定设计：**

1. 先完成内置卡闭环：两处都绑定相同 approval ID/version、Task/调用和授权范围；任一处决定后另一处重新读取服务端状态。提交超时或断线为“决定待确认”，先读取持久决定，再允许同身份安全重试；过期、参数变更或撤权的旧卡不可派发。允许只表示批准，不等于工具执行或验证成功。
2. R22 的通用资源能力按已授权 MCP 连接的**实际**工具与资源关联发现和读取；先核对锁定版本的 DSH MCP 插件能否复用 `resources/read`，不足时在现有边界做适配。不得让 iframe 直接取得凭据、任意访问本机/网络或调用全部工具；宿主按来源、当前卡/审批身份、协议和能力白名单桥接，未经授权的能力拒绝。外部资源未能安全装配时保留可见失败/重载，不能自动批准；不要把资源读取能力当作已有 MCP Apps renderer。
3. 任务动态是授权事实的只读投影，按 Agent/时间线显示真实搜索词、来源、打开对象、文件、命令、目录、耗时和结果的适用项；字段缺失或截断如实标明，失败项保留。审批、澄清、停止和任务验证动作仍在对话/审核区，不新增任务动态操作。
4. GitHub 源码分析得到的流程图应在原对话可读，或可在 Morde PC 客户端内打开；原对话保留结论、代码版本及来源。E 已在 `ChatMarkdownContent.tsx` 接入 Mermaid 渲染，并在实际 PC 用本地合成消息观察了图形和源码展开；真实模型生成与源码分析结果仍待验收。未经可信处理的图表内容不能执行脚本或改变宿主 CSP；渲染失败须提示，纯源码不算图形交付。

**交接与验收：**A 负责既有审批 API、授权事实与需要的新资源接口；E 负责 PC 宿主、双入口与动态；D 提供真实验证状态。T19–T21、T52–T54 先做并发双入口、版本/来源伪造、断线/重连与恶意 iframe 本地回归，再用实际 `morde-pc` 和真实 DSH 分层验收；界面显示必须与账本核对。

## 5. PC 单向文件夹同步：A-01 / C-02 / E-02

**现状：**[`morde-sync.ts`](<../../../../clients/desktop/harness/desktop/src/morde-sync.ts>) 保存项目同步 checkpoint/本机目录身份；服务端已有 [`createProjectUploadSession`](<../../../../server/internal/app/workspace_sync_project_upload.go>)、[`applyLiveProjectUpload`](<../../../../server/internal/app/workspace_sync_live_project_upload.go>) 及 [Host applied 回执](<../../../../server/internal/store/postgres/workspace_sync_project_upload.go>)。本机/API/数据库局部能力不等于真实 PC → 云电脑验收；非协作 Host 写入下多文件操作仍可能部分应用。

**拟定设计：**

1. E 在 PC 让用户确认本地目录、项目名、范围并点击；每次点击固化本机目录身份和该次快照/manifest、固定默认 Host 及授权身份。同步期间目录变更应由后续只读扫描显示“有待同步更改”，不自动发起第二次上传。
2. C 根据**上次得到 Host applied 回执的源基线**、当前源快照及云端现状计算新增/修改/删除。只允许删除基线中本次已删除且云端未独立变更的内容；云端新增、冲突路径、目录失联或不可读时保留并提示，根目录不可访问不能解释成空目录。规范化路径，拒绝越界或无法安全识别的链接/特殊条目。
3. 同一项目的活跃同步按已有身份/锁串行；云电脑、Workspace binding/generation、manifest 和用户授权在派发和回执时均复核，不切换目标。分块成功或服务端 session completed 不等于 Host 已应用；只在 Host 可信 applied 回执及目标核对成功后推进基线。
4. 中途断线、Host 回执 unknown 或云端独立写入导致部分应用时，保留原基线、记录具体已确认/未知/冲突范围，先对账，不假定整批原子回滚或盲目重放删除。云端变更不回写 PC；用户确认后再次点击才处理新快照。

**交接与验收：**C 提供 session、源基线、应用回执和冲突字段；A 处理共享接口/持久化；E 独占 PC 操作与状态。T16–T18/T44 覆盖同步中本机变化、首次目标非空、单文件和目录删除、云端独立修改、部分应用、断线、重复点击、撤权及默认 Host 不可用；实际云端合成目录按任务授权执行，不用本地 fixture 冒充云端。

## 6. 多 Agent、工具选择和共享资源：A-01 / B-02 / C-01

**现状：**[`AgentChildSessionService`](<../../../../server/internal/app/agent_sessions.go>) 与 [`createCloudDSHChildSession`](<../../../../server/internal/worker/cloud_dsh_session_tree.go>) 已有父子身份及授权/深度检查；Runtime [`validTools`](<../../../../runtime/morde-cloud-runtime/src/engine.mjs>) 限制每轮最多 64 个定义。子 Agent 已创建不代表工作成功，实际外部工具是否并发仍须核对。

**拟定设计：**

1. B 负责子任务目标、依赖与结果汇总；C 负责 Runtime、checkpoint 和会话树；A 负责共享预算、授权与 Broker。延用现有 `spawn_key`、父子 session、Task/修订及调用身份；子 Agent 权限/工具为父级可用集合的子集，创建和恢复复核当前授权。
2. 独立无冲突工作可以并行；同一 GUI 电脑的交互、同一路径或有重叠风险的写入不能同时无序执行。先复用现有 Host/Workspace 授权与操作栅栏；若不足，由 A 定义受影响资源的最小串行/互斥合同。无法确认资源关系时等待或说明，不把全部工作强制串行；租约过期不等于底层副作用已停止。
3. 子任务结算保留成功、失败、取消及 unknown 与证据引用，逐级交回主 Agent；某个子任务失败不自动抹除已完成工作。取消作用于明确目标，已派发 unknown 不重放。
4. 工具发现和每轮有界选择先经过用户/Task 授权和预算过滤；保留当前消息读取、必要控制和执行所需工具。选择摘要绑定版本、工具名/schema 摘要和 checkpoint；恢复时复核，不把模型选择当授权。无法装入或恢复一致时说明缺失能力，不静默替换工具。
5. **L4 监视与交接（M03-05，待核实/实施）：**按[最终设计](<../Morde 复刻 Muse 最终流程与开发设计.md>)复用现有子 Session、结算、handoff 和 checkpoint；普通进度仅更新工作项，必要的终态/阻塞按 Task 修订、父子 Session 及稳定来源事件身份交直接父级。交接须有可恢复的持久事实和可对账的父级处理回执；重复、重启、撤权或旧修订时先复核与对账，不重复副作用。B 核对事实/会话，A 在既有能力不足时定公共合同及原子边界，C 接 Runtime/checkpoint，D 承接 R20 原对话终态，E 负责实际 PC 验收；不把每个进度事件变成一次模型调用或新增第二个 Runtime。

**交接与验收：**B 将选择/协作合同交 C，公共权限/资源栅栏交 A。T09–T12/T42/T43 与 M03-05/06 记录独立 worker 的真实重叠时间、相同资源的互斥、混合结果、必要交接、重复/重启、超过 64 项时必要工具保留及撤权；模型回合重叠不能证明外部操作并行。监视比例只作样本观察，不是通过门槛。

## 7. 记忆、受控 Skill 与例行规则：A-01 / B-02 / C-02

**现状：**[`personal_mutations.go`](<../../../../server/internal/store/postgres/personal_mutations.go>) 已对规则候选检查来源记忆修订及确认状态；[`cloud_dsh_skills.go`](<../../../../server/internal/app/cloud_dsh_skills.go>) 当前读取的是固定的内置 allowlist，技能不增加权限。来源变更后的动态 Skill 提供、授权撤销和例行执行链路不能据此视为已完成。

**拟定设计：**

1. C 先给 B 一份记忆读取合同：owner、来源及版本、授权范围和删除/纠正状态。读取、生成候选及执行时重新核对来源；纠正/遗忘后旧来源及其派生候选不再用于新决策。保留用户可查看的原始聊天记录，并按已有授权与遗忘规则限制召回，不把对话自动变成长期规则。
2. B 的 Skill 候选绑定 owner、内容摘要、来源版本、可用工具及版本；使用既有候选/审批机制记录验证和用户确认，只有确认的精确版本可被加载。候选内容或来源变化、撤权、归档/撤销后不可继续加载或作为新操作依据；已派发的副作用仍先对账。不要把候选写到全局目录，也不要让模型从任意本机路径加载。
3. 先评估当前 `nanomuse_skill_read` 和上游 [`dsh-skill`](<../../../../project/deepseek-harness/packages/skill/skill/src/index.ts>)、[`tool-skill`](<../../../../project/deepseek-harness/packages/skill/tool-skill/src/index.ts>) 能否支持受租户约束的提供方。上游源码有 provider registry，但当前 Runtime 的 `package.json` 未声明 `dsh-skill` / `tool-skill`；不能把上游存在当作本项目已接入。若接入先核对锁文件版本、MIT 许可证、会话恢复及授权，不能假定当前固定内置 catalog 已支持动态内容。A 决定公共身份/存储与版本变更，B 实现技能选择/读取，C 实现记忆与 Runtime 专属适配；Skill 指令不能扩大原 Task 的工具、目标、预算或审批权限。
4. 例行规则只在用户明确启用、来源及授权仍有效时触发；每次触发绑定稳定的规则版本与执行身份，重启/重复触发不得重复执行已确认的副作用。高风险操作仍按原审批和账本执行；用户撤销、来源变更或权限失效时停止后续触发。

**交接与验收：**先由 C 交记忆/授权合同，B 交 Skill 候选/启用合同后 C 再接例行规则，不互等整份任务关闭。一体化 A01/A02 及 T30–T33 覆盖候选未确认不可用、确认版本变化、来源修订/遗忘、撤权、不同账号隔离、重启重复触发及高风险操作审批；缺少实际客户端或真实执行证据时相应层保持待验。

## 8. 双端状态与最终验收：A-02 / E-02

PC 和原生 iOS 使用同一账号、会话、Task 与服务端事件/审批身份，客户端只投影当前授权结果；两端提交同一操作沿用各自既有幂等/版本合同。E 负责需要修改的 iOS 专属文件，以及将 PC、iOS 各自实际行为和服务端账本交 A 汇总。用户关闭客户端不取消云端已受理任务，恢复后不得重复创建或执行；旧会话/账号的缓存必须隔离。

T44 分别登记 PC 操作、iOS 接续、真实云电脑同步及两账号隔离。PC 的交互验收只使用实际 `morde-pc`；iOS 是独立验收项，不代测 PC。若现行交互限制或环境不允许 iOS/云端操作，保持该层阻塞，不能以 PC 或 fixture 推导通过。T43 的复杂任务还应覆盖已授权电脑的实际观察/操作和终端、搜索来源、两个独立子 Agent、审批、验证与原会话结果；缺一环就如实保留缺口。
