## A-01 T57 Task lease 与 CloudDSH recovery 本地源码审计（2026-11-25）

- **代码路径：**生产 `TaskWorker` 配置 lease 30 秒、poll 500 毫秒，并按 lease/3（10 秒）续租（`server/cmd/portal/main.go:1101`、`server/internal/worker/task_worker.go:107`、`:344`）。续租 SQL 只更新 lease/`updated_at`，不递增 `event_seq`；Task 被重新认领时，Store 把过期 `running` 纳入候选、递增 lease version 和 `event_seq`，并写入 `task.status`（`server/internal/store/postgres/task_execution.go:867`、`:1151`、`:1258`）。
- **可解释的恢复循环：**执行器返回错误后，TaskWorker 记录执行停止并继续轮询，本身不把 Task 改为终态（`server/internal/worker/task_worker.go:276`）。CloudDSH 在恢复态将 `errCloudDSHConnectionInterrupted` 排除于 `PauseRecovery` 之外（`server/internal/worker/cloud_dsh_executor.go:820`）。如果这类错误使单次 `ExecuteTask` 返回，Task 可以保持 `running`，等 lease 到期后再被认领并创建新 Runtime generation；因此约 30 秒一个 `task.status`/generation 的节奏更符合“快速失败后反复认领”，但不是对 qfbwyq4f 历史现场的证明。
- **另一种不同状态：**若执行器 goroutine 尚未返回，TaskWorker 会继续每 10 秒续租。`runAgentRequest` 在收到 Runtime frame 错误后会等待工具执行 goroutine 结果（`server/internal/worker/cloud_dsh_session_tree.go:2275`），所以长时间未完成的工具调用也能造成 lease 持续刷新；T57 账本没有工具调用证据，不能把现场归因于此路径。Guardian 确认 Runtime stop 时会清空 `failure_reason`（`server/internal/store/postgres/account_agent_runtimes.go:510`），故 stopped 且原因为空也不能反推此前未出错。
- **结论与后续：**本地源码允许“执行器快速返回连接中断 → Task 留在 running → lease 过期后循环认领”的模式，也允许执行中阻塞而持续续租；现有 T57 快照和日志不足以锁定 qfbwyq4f 实际路径或 `errors.Join` 子错误。本审计只读，没有改代码、运行测试或操作 PC/远端。需要在 D 的 CloudDSH 恢复策略边界评估无 checkpoint / 首次模型调用前连接中断的有界重试与安全 pause，并以短 lease 回归验证；A 不应仅凭 lease 到期改 Store 的通用认领语义。
