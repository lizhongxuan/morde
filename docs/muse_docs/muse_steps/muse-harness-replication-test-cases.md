## 第一章 收件入口（源文档 §1）

**TC-1.1 多端同一会话，同一份 transcript**【黑盒｜已证实】
- 目的：验证 web / iOS / Mac / Chrome 扩展进的是同一个一对一对话，不是每端一份记录
- 前置：同一账号已在 web 与 iOS 登录
- 操作：web 发一条消息，iOS 打开同一会话继续发一条
- 观察：两端看到同一会话、同一顺序、同一任务列表；没有出现重复任务或第二份 transcript
- 通过：两端历史完全一致；每会话只有一个 chat UUID

> 当前执行：分别用实际 PC 和原生 iOS 验证同账号接续，按 T44 记录；历史 Web 场景不是 Morde 普通用户客户端验收要求。

**TC-1.5 任务行五字段齐全**【代码｜已证实】
- 目的：验证任务记录形态与 Muse 的 `activity_monitor_threads` 对齐
- 前置：Morde 已有一条任务记录
- 操作：读任务表，对照字段 `name`（标题）、`subtitle`（一句话副标题）、`status`、`finish_status`、`created_at` / `finished_at`
- 观察：六个字段都存在且有值；终态只有 finished 一类
- 通过：任一任务点开都能看到标题、副标题、状态、起止时间；无缺失字段

**TC-1.6 副标题随进展改写**【黑盒｜已证实】
- 目的：验证副标题不是写死文案
- 前置：一个进行中的长任务
- 操作：任务进行中看一次副标题；任务完成后再看一次
- 观察：进行中副标题是当前进展；完成后副标题变成交付物描述
- 通过：两次副标题不同，且第二次准确描述交付物

**TC-1.7 幂等收件：重复提交不重复建任务**【代码｜Morde 自研】
- 目的：验证 Morde 的收件幂等（源文档注明：Muse 侧幂等机制未知，Morde 这套是自研，比 hermes 更严）
- 前置：Morde 服务端，`AcceptConversationMessage` + `client_message_id` 已实现
- 操作：用同一个 `client_message_id` 发两次同一条消息；再用同一 ID 发不同内容
- 观察：第二次提交的返回与任务数
- 通过：同一 ID 第二次提交不新建任务；同 ID 不同内容被拒绝；会话内服务端 `sequence` 单调递增

## 第二章 意图路由与任务拆分（源文档 §2）

**TC-2.1 一条消息多半开一个任务**【黑盒｜已证实】
- 目的：验证“消息 → 任务”的基本映射
- 前置：空会话
- 操作：发一条独立的消息（如“帮我查一下今天天气”）
- 观察：任务列表新增一个任务，标题与消息内容相关
- 通过：新增恰好一个任务；主对话只出最终结果

> 当前执行：按 T04–T06 判断是否需要任务；纯文字问答直接回复，实时天气按需查询，不应固定要求每条消息新建任务。

**TC-2.2 多消息归并是否存在、按什么规则**【黑盒｜未知·探查】
- 目的：探查原则③后半句——同话题多轮是否归成一个任务（源文档：829 链接 / 352 任务，31% 的任务链 ≥2 条消息，但归并规则未知）
- 前置：空会话
- 操作：连续发 3 条同一话题的消息（第二条补充第一条的细节），间隔 1 分钟；另起一组间隔 1 小时发 2 条同话题消息
- 观察：记录每组产生了几个任务、几次最终答案
- 通过：不预设结论——如实记录“1 分钟组几个任务、1 小时组几个任务”；该结果即为本用例的产出，用于后续定义合并窗口

**TC-2.4 Connector 只提供文档列出的命令**【黑盒｜已证实】
- 目的：验证 connector 的能力边界是文档，不是模型想象
- 前置：任选一个 connector，读其 CONNECTOR.md 命令清单
- 操作：请求一个清单里没有的命令
- 观察：agent 的答复
- 通过：明确答复“该 connector 不提供”，不伪造调用、不编造结果

**TC-2.5 请求分类字段存在**【代码｜已证实】
- 目的：验证路由留痕有分类字段（分类算法本身未知，不测算法）
- 前置：可读 `runtime.requests`
- 操作：发一条用户消息，查该请求行的 `request_origin`、`transcript_surface`、`root_work_class`
- 观察：三个字段是否写入
- 通过：三字段齐全；`root_work_class` 能区分 internal 与 user_facing

**TC-2.6 偏好文件路由**【黑盒｜已证实】
- 目的：验证购物/旅行等任务先读偏好文件
- 前置：`~/memory/shopping/PROFILE.md` 已写偏好（如“不买某品牌”）
- 操作：发一条购物请求
- 观察：agent 是否先读 PROFILE.md，回答是否遵守其中的偏好
- 通过：回答与 PROFILE.md 一致；偏好文件未被改写（长期偏好只在用户明确说“以后都这样”时才写入）

**TC-2.7 回答“记得什么”之前先搜记忆**【黑盒｜已证实】
- 目的：验证记忆路由
- 前置：记忆里有一条明确事实
- 操作：问“你还记得我上次说的 XX 吗”
- 观察：agent 是否先 `muse.memory_search` 再回答；回答是否逐字来自记忆
- 通过：回答与记忆原文一致；无记忆时明确说不知道，不编造

**TC-2.8 大文档审阅用 coordinator + extraction worker + checking worker**【黑盒｜已证实】
- 目的：验证文档级推荐模式
- 前置：一份 >10 页的多文件文档（如法律/财务/技术审阅材料）
- 操作：发“审阅这份文档，抽取关键发现并合成结论”
- 观察：任务详情里是否出现 1 个 coordinator（定页码/章节分工）+ 若干 extraction worker（每人唯一输出路径）+ 1 个 checking worker
- 通过：分工明确、无输出路径冲突；最终判断权在 coordinator；checking worker 标出无支撑断言/对不上的数字

**TC-2.9 Wide research 输出合同固定**【黑盒｜已证实】
- 目的：验证 wide research 的 manager 输出格式
- 前置：准备一份独立输入列表 + 输出 schema
- 操作：发 wide research 任务（一句话 operation_brief）
- 观察：manager 输出是否先去重归一化输入，再派 worker；最终输出是否含 `total / success_count / failure_count / results / failures / notes`
- 通过：六字段齐全；`failure_count` 与实际失败数一致；失败项保留、不谎报成功

**TC-2.10 待办拆分规则：只在可分别完成或可解阻塞时拆**【黑盒｜已证实】
- 目的：验证任务拆分不是见词就拆
- 前置：一个含多个子项的用户待办
- 操作：让 agent 把待办拆成任务
- 观察：拆分结果；拆前是否先搜索已有相同任务
- 通过：只有“可分别完成或可解阻塞”的项被拆开；已有相同任务时不重复建；标题写的是下一步具体动作

**TC-2.11 会议跟进三分**【黑盒｜已证实】
- 目的：验证会议跟进的拆分结构
- 前置：一份会议记录
- 操作：让 agent 跟进这次会议
- 观察：产出是否分为决定 / 行动（owner + 日期）/ 开放问题；发 recap、建任务、约下次会是否为三个独立动作
- 通过：三分齐全；只做用户点的动作，不多做

**TC-2.12 合并窗口与同话题判定（Morde 自研，无 Muse 对照）**【代码｜未知·探查】
- 目的：为 Morde 自研合并窗口留出探查基线（源文档：意图分类算法、拆分算法、合并窗口、同话题判定全部未知）
- 前置：Morde 路由 worker 代码（`server/internal/worker/conversation_route_worker.go`）
- 操作：读代码，确认是否存在时间窗口常量与话题相似度判断
- 观察：有无窗口常量、有无相似度兜底；`steer` / `update` / `join` 是否完全依赖分类器一次判对
- 通过：如实记录现状（源文档结论：无窗口、无相似度兜底）；该记录作为 P0-4 的立项依据，不谎称“已实现”

## 第三章 并发派发与协调员监视循环（源文档 §3）

**TC-3.1 主 agent 派发后自己继续工作，不排队**【黑盒｜已证实】
- 目的：验证原则②——主 agent 只做简单对话，复杂工作派后台
- 前置：一个需要两件并行子活的任务
- 操作：发任务；观察任务详情里的时间戳
- 观察：主 agent 派发两个子 agent 后，自己是否继续做另一件小事（如 git 检查），时间戳是否重叠
- 通过：子 agent 开始时间与主 agent 的工作时间重叠；不是先等子 agent 完事主 agent才动

**TC-3.2 第一个任务不堵住第二个**【黑盒｜合理推断·验证推断】
- 目的：验证“第一个任务未完成时能否立刻接第二个用户消息”（源文档：时间戳重叠 + 单日 63 个任务是强间接证据，但逐消息级证据未单独拉取）
- 前置：一个进行中的长任务
- 操作：长任务跑着时，再发一个完全独立的新任务
- 观察：新任务是否立即开始，还是等前一个完成
- 通过：新任务立即开始；两个任务各自有独立进度；如实记录是否有一方被阻塞

**TC-3.3 子 agent 嵌套到 2 层**【代码｜已证实】
- 目的：验证嵌套深度上限至少 2 层（纠正旧推断“子 agent 不再派子 agent”）
- 前置：可读派生记录
- 操作：发一个需要子 agent 再派子 agent 的任务；查 `agent.subagent_spawns` 的 `child_depth`
- 观察：depth=1 与 depth=2 的派生是否都出现
- 通过：depth=2 的派生真实存在（源文档实测：230 次派生中 depth=2 有 71 次，31%）；depth=2 的工作项可查

**TC-3.4 第 3 层是否存在**【黑盒｜未知·探查】
- 目的：探查嵌套上限（源文档：实测最大值 max_depth=2，3 层是否存在未知）
- 前置：同 TC-3.3
- 操作：构造需要三层嵌套的任务，观察派生行为
- 观察：是否出现 depth=3 的派生或明确拒绝
- 通过：不预设结论——记录“出现 depth=3”或“被限制在 2 层”，作为上限设计的输入

**TC-3.5 子 agent 类型分工：默认通用**【黑盒｜已证实】
- 目的：验证默认形态是“1 主 + 通用子 agent”，没有内置架构师/程序员/测试队伍
- 前置：发三类任务：普通研究、构建 artifact、浏览器操作
- 操作：分别观察派生的子 agent 类型
- 观察：普通任务是否派通用子 agent（`agent_type` 为空）；artifact 任务是否派 `artifact_builder`；浏览器任务是否派 `browser_task`
- 通过：类型与任务匹配；通用占多数（源文档实测 54%）；没有出现“架构师/测试 agent”这类固定角色

**TC-3.6 协调员每事件决策一次，但 61% 什么都不做**【代码｜已证实】
- 目的：验证协调员监视循环的决策分布
- 前置：可读 `agent.subagent_monitor_decisions`
- 操作：跑一个含多个子 agent 事件的任务，统计决策类型
- 观察：`nothing_to_do` / `worker_or_coordinator_completed` / `notify_main_agent` / `inference_error` 的比例
- 通过：每个子 agent 事件恰好触发一次决策；`notify_main_agent` 只占约 1%（源文档实测 241/20,787）；`inference_error` 接近 0

**TC-3.7 派生本身是一条工作项**【黑盒｜已证实】
- 目的：验证派发动作可追踪
- 前置：一个派发了子 agent 的任务
- 操作：打开任务详情，找派发记录
- 观察：`action_id` 前缀是否区分 `ga-root-tool-…`（主 agent 工具调用）、`ga-root-subagent-dispatch-…`（主 agent 派发）、`ga-subagent-start-…`、`ga-child-tool-…`、`ga-subagent-finish-…`
- 通过：派发、启动、完成各有一条独立记录，前缀可区分

**TC-3.8 UI 工作项唯一事实来源是 activity actions**【代码｜已证实】
- 目的：验证不把内部调度表当成 UI 事实
- 前置：读代码/数据库
- 操作：核对 `runtime.work_items`、`runtime.agent_todo_snapshots` 与 UI 展示的关系；查 `activity_monitor_thread_sections` 行数
- 观察：UI 列表是否只来自 activity actions；分组是否客户端按 `agent_depth` / `agent_id` 现算
- 通过：`activity_monitor_thread_sections` 为 0 行时 UI 仍能正确分组；不把 `work_items` 或 `agent_todo_snapshots` 当 UI 数据源

**TC-3.9 一个 coordinator per objective，不从 root 直接扇出多个平级 worker**【黑盒｜已证实】
- 目的：验证官方推荐的扇出模式
- 前置：一个需要多 worker 的大任务
- 操作：发任务，观察派发结构
- 观察：是否由一个 coordinator 定分工再派 worker，还是 root 直接扇出多个平级 worker
- 通过：只有一个 coordinator；worker 由 coordinator 派发

**TC-3.10 后台结果以 hidden handoff 交回，worker 不能要求主 agent 做更多工作**【黑盒｜已证实】
- 目的：验证后台与前台互不阻塞
- 前置：一个后台 worker 任务
- 操作：等 worker 做完，观察主 agent 如何处理其报告
- 观察：报告是否以 hidden handoff 交回；主 agent 是否自行决定用户看到什么
- 通过：用户只看到主 agent 决定展示的部分；worker 的报告不直接进主对话；worker 没有反向派活给主 agent 的记录

**TC-3.13 最大并发数、配额、排队策略**【黑盒｜未知·探查】
- 目的：探查并发上限（源文档：无证据；wide-research 只给“先跑一项再放量”的启发式）
- 前置：可连续发起多个任务
- 操作：同一时间发起 5 个、10 个、20 个独立任务，记录开始/排队/拒绝情况
- 观察：何时出现排队或拒绝；有无明确的配额提示
- 通过：不预设结论——记录实测的并发上限与排队行为，作为 Morde 并发设计的输入

## 第四章 工具执行工作项（源文档 §4）

**TC-4.1 钻取七要素齐全**【黑盒｜已证实】
- 目的：验证原则⑤——每条工作项点开都有完整证据
- 前置：任一已完成任务
- 操作：点开任意一条工作项的 report
- 观察：是否含执行位置、完整命令原文、退出码、耗时（毫秒）、工作目录、输出原文（长输出截断并注明截了多少行）、一句人话结论
- 通过：七要素齐全；例：`git fetch`，exit code 0，2275 ms，cwd `/home/hatch`

**TC-4.2 再小的动作也记**【黑盒｜已证实】
- 目的：验证没有“太小不记”的例外
- 前置：做一个一秒钟的动作（如点赞 👍）
- 操作：点赞后打开任务详情
- 观察：是否记了工具名、返回值和一句话结论
- 通过：有点赞的工作项记录；无遗漏

**TC-4.3 进行中先占位，跑完才换正式标题**【黑盒｜已证实】
- 目的：验证运行中状态的实时展示
- 前置：一个耗时几秒以上的工具调用
- 操作：调用进行中时打开任务详情
- 观察：是否先出现占位行（如“正在运行：正在检查保存的记录”，状态 `running`），跑完后是否换成正式标题和 `success`
- 通过：占位行先出现；完成后标题与状态都更新，无残留占位行

**TC-4.4 失败项留痕，任务不中断**【黑盒｜已证实】
- 目的：验证失败不删不改写、不停任务
- 前置：一个会先失败一次再成功的任务（如某步 `ls` 返回 exit code 2，后面构建成功）
