## 2. R19-A：结构化文件交付意图

### 2.1 当前事实

- `task.FileDeliveryIntent` 的稳定值为 `none`、`required`、`unclear`；任务表字段由迁移 `00071_task_file_delivery_intent.sql` 持久化。
- 会话路由结构化输出只允许 `new` / `update` 携带该字段。空字段在新任务上采用 `none`，在更新时继承当前任务值。字段表达预期交付物，不授予工作区访问或写入权限。
- `TaskService.Submit`、batch item 和 schedule create/update 接受独立的结构化意图；新 Task/schedule 缺省为 `none`，更新缺省继承当前值。迁移 `00243` 持久化 batch item 意图，`00245` 持久化 schedule 意图并在 occurrence 创建 Task 时沿用该值；个人 schedule snapshot 和 DSH schedule 工具也保留结构化字段。schedule 当前没有 Workspace 绑定，因此服务/API 仅接受 `none`，提前拒绝 `required` 和需澄清的 `unclear`，不根据 objective 文本推断。batch 意图更新/重放不可改写；`unclear` 可为 Task 或单个 batch item 建立版本化澄清，并由原澄清 API 原子回答和重排。通用 Store 新 Task 归一化只把空值设为 `none`，不再从 Objective 文本分类。个人会话 route receipt 在接收时捕获 owner-scoped ready Workspace 的 revision/manifest digest，Apply 事务重新校验后绑定到 `new/required` Task；有效快照也保留给 `new/unclear`，使用户可用同一快照回答 `required`。route `update/unclear` 已接入独立 call ID 与版本化澄清，并由 PostgreSQL 集成回归验证旧 Task 停止前不提前创建修订。项目会话尚无可绑定的 Workspace 版本时，`required` 保持 fail closed；真实 PC/DSH 端到端未验。

### 2.2 合同 v1

**输入：**路由/任务协调器为一个 Task 和每个 batch item 分别提供 `file_delivery_intent`，取值只能是上述三个枚举。一个 batch 的意图不由首条文本覆盖其余 item。更新可省略字段表示继承；新任务可省略字段表示 `none`。如果协调器无法给出可靠决定，发送 `unclear`，由现有版本化 clarification 提问，不再回退到关键词或正文分类。

**持久身份：**Task 字段绑定 `(owner_id, conversation_id, task_id, task_revision)`；batch 意图同时绑定 `batch_item_id` 与 `attempt`。澄清答案绑定既有 `(task_id, clarification_id, clarification_version, idempotency_key)`，答案只解决对应的意图版本；重放返回原决定，不重复推进 Task。

**输出与门禁：**`none` 表示完成不要求额外交付文件；`required` 表示完成条件包含已授权且可核实的文件/Workspace 产物；`unclear` 必须保持等待澄清。该字段不能放宽授权、审批、Broker、Workspace 目标或产物校验。文件交付被要求但没有可用 Workspace 时返回明确的 `workspace_id` 校验错误，不得假称已交付。

**权限与失败：**服务端仍校验 Task 所有者、会话、项目、Workspace、授权和修订；非法枚举为输入校验失败，旧版本澄清或幂等键冲突不得改变当前意图。模型/路由不可用或输出无效时采用现有安全澄清路径，不猜测为 `required`，也不猜测为 `none`。

**调用方：**B-01 负责路由与 DSH schedule 工具的结构化来源；A 已为直接 Task、batch、clarification、schedule 提供 app/Store/API/OpenAPI 与持久化切片。新 Task 缺省不再按 objective 关键词分类，个人 route `new/required` 已绑定 receipt Workspace input snapshot，route `update/unclear` 已有版本化持久澄清且 Portal/iOS 已接精确 answer call ID；Portal 自动化通过，iOS target 已编译但模拟器 UI 用例未到达认证后澄清界面。项目 Workspace 版本绑定与真实 PC/DSH 接续仍待验收；合同已定不等于所有调用方实现已完成。

## 3. M02-14：计划步骤和真实执行结算

### 3.1 当前事实

- `task.Plan` 具有 Task revision、plan revision、步骤 ID 和 `depends_on`；验证器会检查步骤身份、依赖存在和无环。
- `PlanStep.Status` 当前包含模型提交的 `completed`。成功保存计划只证明 `morde_task_plan_update` 调用被接受，不证明某个计划步骤的工具或子 Agent 已完成。
- `task_dependencies` 是跨 Task 依赖并绑定前置 Task 的 `required_revision`；它与同一 Task 内的 plan-step 依赖是不同关系。

### 3.2 合同 v1

**计划步骤身份：**任何依赖门禁使用完整键 `(owner_id, task_id, task_revision, plan_revision, plan_step_id)`。`plan_revision` 每次保存计划递增；步骤 ID 仅在该计划修订内有意义。计划状态字段只是呈现/意图，不是结算事实。

**执行绑定输入：**B 在派发依赖步骤前，将计划步骤绑定到一个或多个现有真实执行身份：工具调用使用 `(agent_session_id, call_id, operation_id)`；子 Agent 使用父 Task、父步骤、`child_session_id` 和现有 spawn/child ledger 身份。绑定同时携带 `authorization_version`、Task revision 与计划 revision。不得以另建的平行操作账本取代 `task_operations`、MCP connector operation 或 `task_agent_sessions`。

**放行输出：**Store 按完整计划键查询已绑定的执行账本。只有所有必需执行均有可核实的成功结算时才返回可放行；失败、取消、unknown、待审批、缺绑定、授权撤销、Task revision 或 plan revision 过期均返回不可放行及稳定原因。无依赖步骤不因其他步骤失败而被强制阻塞。

**修订和重放：**旧计划下已派发执行仍按原 operation/child 身份对账，计划更新不重放副作用。旧结算不能自动继承到新修订；仅当目标、参数、授权范围、执行对象和原结算完全一致且有持久证明时才允许显式重绑，否则新计划步骤保持未结算。

**事务/调用方：**绑定与派发准入必须处于同一 revision/授权栅栏。A 提供公共 Store 端口、迁移及事务性绑定/读取能力，并在 Hub command 的 prepared→dispatched 事务接入 gate/bind；B 接入 `cloud_dsh_task_plan.go` 的依赖执行路径；C 在 child spawn 事务接入 gate/bind。child settlement 已由现有账本持久化，readiness 可读取该结算。DSH 调用协议仍需携带并核实 plan-step 元数据；没有持久操作账本的直接工具步骤也需要明确可核实的成功事实。禁止使用跨 Task `dependency_task_ids` 替代本合同。

**子 Agent 调用协议：**`dsh_delegate` 可携带成对的 `morde_plan_step_id`（1–40 位，字母或数字开头，其余可含 `_`/`-`）和正整数 `morde_plan_revision`；无计划时可省略，有计划时服务端按当前计划、授权及依赖核验。Runtime、IPC 和账户 Runtime 保留字段原样交给服务端，不将其混入子任务业务参数。旧 checkpoint 的无字段定义继续可恢复；缺半对或无效字段拒绝，字段本身不授予权限。

**当前状态：**迁移 `00244_task_plan_step_execution_bindings.sql`、`00248_task_plan_read_tool_bindings.sql`、`00250_task_hub_plan_step_bindings.sql` 与 Postgres Store 接口已覆盖 Host operation、MCP operation、child session、内部 direct-read 和 Hub command。Host dispatch、MCP admission、child spawn 与 Hub command 从 prepared 转为 dispatched 均在对应事务中核验当前 selector、Task/plan revision、授权、依赖及执行身份并持久化 binding；Skill、附件、会话历史、Workspace/impact map、Hub screenshot/files/get/fetch、Goal/Schedule 只读工具在读取前 admission，并绑定精确成功 TaskStep 身份与 32-byte 结果 digest，readiness 仅凭这些持久证据解锁。`PlanStep.Status=completed` 不构成成功证明；direct-read 与 Hub command 的 App/隔离 PostgreSQL 定向回归通过。跨场景/重启和真实 DSH 计划执行仍待验；H07 仍须绑定适用检查、覆盖范围及不可变 Workspace 版本，Host 内部 `file_write` source-proof 不替代该验证。scheduled observation 无生产调用方并保持 fail-closed。

## 4. R21：原文身份、manifest 与 DSH 投递

### 4.1 当前事实

- 会话上传最多 8 MiB，按 16 KiB 分块；提交时校验 UTF-8 长度、整体 SHA-256 和每块完整性，再创建服务端 message ID 并保留原始正文。
- 当前消息读取器可对原始 message ID/sequence 生成有序分页 manifest（总字节数、rune 数、全文 SHA-256、分页范围与页 SHA-256），读取时校验原文身份、权限和页摘要，并按连续页记录读取进度。
- 迁移 `00241_task_agent_message_delivery_receipts.sql` 为 `task_agent_message_deliveries` 增加原文 SHA/字节数、manifest、附件摘要、inline/reference 表示指纹、Task revision、Agent generation 与 applied checkpoint 证据。Postgres Store 为每条 pending 消息生成有序分页 manifest；checkpoint 原子保存回执，并提供按当前 Task、授权、消息和来源 SHA 栅栏化的 reference/page 读取。
- 迁移 `00253_agent_message_attachment_only_sources.sql` 兼容附件-only 消息：正文可为空，但必须有非空附件身份摘要；无正文且无附件仍拒绝。空正文使用规范空分页列表，迁移保留既有回执的可读性。隔离 PostgreSQL 回归覆盖附件-only 首次投递、启动失败后的恢复及单次应用；这证明本地持久化/恢复合同，不代表真实 DSH 或模型完整理解附件。
- Worker 对超过 128 KiB inline 上限的初始消息、followup、steer 和恢复批次生成有界的版本化来源引用；Runtime 校验规范 envelope、摘要、conversation/revision 与外层消息 fence，并可从 checkpoint 恢复该引用。Store/Worker/Runtime 有定向测试。真实 DSH/模型语义、实际 PC 长消息操作及端到端读取覆盖仍未验收。
- `applied` 只证明对应 envelope 被 root checkpoint 接收；不证明模型完整阅读了正文。现有 `CurrentMessageSource` 仍是单消息历史来源；R21 新 source receipt 为每条消息分别绑定来源和分页，不复用前一条的读取进度。

### 4.2 合同 v1

每个用户 message 必须保留一个不可变来源身份：`owner_id`、`conversation_id`、服务端 `message_id`、`message_sequence`、Task/revision 关联、UTF-8 `content_bytes`、原文 `content_sha256`、有序附件 ID/摘要和授权版本。首条、每条 followup、steer 及恢复批次成员分别建立来源；一条消息的身份、manifest 或读取进度不能代替另一条。

大正文的有界投递表示为版本化引用，至少包含 `version`、`message_id`、`content_bytes`、原文 `content_sha256`、manifest 版本/摘要和规范页范围。原文身份与投递表示身份分开：`source_sha256` 始终指原始用户正文；`representation_sha256` 对本次传给 Runtime/checkpoint 的规范 envelope、模式、顺序及附件身份求摘要。短正文可以 inline，长正文可以引用；不得以短 prompt 取代原文后仍冒用原文 message ID/hash。

持久 delivery receipt 必须携带上述 source 与 representation 摘要，并绑定 Task revision、授权版本、Agent generation、root session、mode、enqueue checkpoint 和 claim/applied checkpoint。`applied` 只表示 root checkpoint 已按同一 receipt 接受该 message envelope；它不表示该消息全文已经被模型或 Agent 处理。完整阅读须由按来源页/顺序的实际读取覆盖事实另行证明。

多消息批次必须保留原始顺序和每条来源；在 Runtime/模型预算或批次大小限制下可切成有序子批次，但不能丢项或重新归属。哈希/页摘要不一致、缺页、权限撤销、generation 不匹配或 checkpoint 不一致时保持 unknown/blocked 并提示，先对账，不盲目追加或重放。

**调用方：**A 已定义并迁移 receipt/公共数据结构与受栅栏 source reader；C 已接入 Worker、Runtime、history reader 与 checkpoint 投递/恢复切片；B 仍负责正确选择目标 Task 并保持消息归属；E 负责实际 PC 长消息/恢复验收。端到端真实模型结果和 PC 验收仍未完成。

## 5. R20：终态、持久等待、晚到验证与原会话交付

### 5.1 当前事实

- `CommitTaskProgress` 在一个 PostgreSQL 事务内更新 Task、增加事件序号并写执行事件；`CompleteTaskStop` 在确认 stop lease、操作对账和 Agent 停止后写最终 pause/cancel 状态事件。
- `conversation_result_review` 只覆盖 completed Task 的结果整理；`task_validation_reviews` 是绑定 `task.result` 的内部验证队列，不是用户交付 outbox。D-01 在验证复核完成事务中为**已有首个结果回执**的 Task 写入独立 `late_validation` outbox source；首次回执尚未发布时，结果发布事务会读取当前验证结论并将 FAIL 并入首条回执。PostgreSQL 回归覆盖验证先完成和发布事务先持锁两种顺序；source consumer 已接入 terminal-delivery Worker。
- 迁移 `00240_task_terminal_delivery_outbox.sql` 新增独立终态交付 outbox。`CommitTaskProgress` 确定失败与 `CompleteTaskStop` 确认取消会在写入终态事件的同一事务内排入 source row，唯一身份为 `(task_id, source_event_sequence, source_event_type)`，并记录 owner/conversation/initiator、Task revision、授权版本和事件 payload SHA-256。只有 server 执行 Task 入队；pause、internal route Task 和非 server Task 不入队。
- A-01 已提供持久 source schema、失败/确认取消 writer、选定持久 waiting writer、claim/lease 和 current-source 校验。CloudDSH 启用时，Portal 注册并运行 terminal delivery Worker；Worker 经 ModelGateway 预留/结算预算和用量，使用稳定 `terminal_delivery_<delivery_id>` call ID，加密持久化 `reply_ready`，再于同一事务向原会话写入 assistant 消息并标记 published。D-01 已增加晚到验证 source writer、首次结果合并、受摘要校验的 source facts 和消费编排。审批/澄清已有卡片时不重复写 waiting source。Worker/Gateway/Store 定向回归覆盖 unknown 不重派、已结算响应恢复、原会话发布原子性和幂等。
- ModelGateway 持久化模型调用预留、派发、已结算/unknown、实际 token 用量和可恢复的加密响应。已派发但结果/用量 unknown 时不能释放占用或盲目重派。

### 5.2 合同 v1

**入队事实：**独立 outbox 只接收：(a) `CommitTaskProgress` 原子提交的确定失败事实；(b) `CompleteTaskStop` 确认 Agent 已停且操作已结算/unknown 对账后的取消事实；(c) 没有现存卡片承载、确需用户处理的持久 waiting/unknown 事实；(d) 已交付结果之后到达的、绑定当前 result 的验证结论。审批和 clarification 继续使用现有卡片，不重复生成普通对话通知；pause、合并、短暂自动恢复等待和 completed 成功不产生失败通知。

**事实身份：**每条 outbox row 由稳定数据库 `id` 标识。终态/等待来源键为 `(task_id, source_event_sequence, source_event_type)`；晚到验证键为 `(task_id, result_event_sequence, result_sha256, validation_claim_generation, verdict_digest)`，因此它是独立验证事实，不覆写原始 `task.result`。行同时绑定 owner、conversation、task revision、授权版本、来源摘要和最小脱敏事实引用。失败、确认取消、选定无卡片 waiting 及已发布结果的晚到验证 source writer 已接入唯一键。各 source 与其事实事件在同一事务写入；验证 writer 与 `CompleteTaskValidationReview` 事务一起提交。消费 Worker 已注册并处理这些 source，真实客户端验收仍待完成。

**领取与模型调用：**outbox 按 lease owner/expiry 和单调 claim generation 领取；同一 `delivery_id` 生成稳定模型 `call_id`，只走 ModelGateway，不提供工具。预算按所属 account/project 与 Task 的现行规则预留并实际结算；只在可证明未派发时释放。派发或用量 unknown 时保留原 call ID 和占用并先对账；不创建新 attempt 执行相同副作用。预算/模型不可用时可提交明确标注为“系统状态说明”的事实回退，不能伪称为 Agent 的自然语言解释；回退一旦发布，晚到模型响应不得再发布。

**发布与失效：**模型输入仅包含当前授权可见、已脱敏的事实摘要和可核验来源，不发送工具秘密或无关个人数据。发布事务重新核对 owner、conversation、授权、Task/current/desired revision、来源事件摘要及后续 steer。过期或撤权的 row 标记 invalidated，不覆盖新修订结果。

**首次结果与晚到 FAIL 竞态：**首次 completed 回执尚未发布时，当前验证结论并入该回执，不再另发同源通知。若首次回执已发布，验证事务生成具有独立来源键的晚到结论 outbox。两条路径对同一 Task/source result 使用同一事务锁和唯一约束裁决；重启、重复 claim、重复验证或重连不得重复发同一事实。

**状态机：**`pending -> claimed -> reply_ready -> published`，允许 `claimed -> unknown`（模型派发/用量未知）并在对账后恢复；任何未发布状态可在来源过期或授权变化时转为 `invalidated`。`reply_ready` 必须持久化响应密文及摘要，避免模型已结算但发布前崩溃后再次收费。`published`/`invalidated` 是终态。

**当前状态：**A-01 已提供独立 outbox、失败/确认取消/选定持久等待 source、claim/lease/状态转换、budgeted ModelGateway Worker 和原会话原子发布；D-01 已接入 source facts、晚到验证同事务 source 写入及首次回执复用当前验证结论。loopback PostgreSQL 覆盖 outbox writer、active lease/replay/expired reclaim、revision/auth/source 失效、reply-ready 重放、published 幂等、晚到验证 source、等待 eligibility 和首次结果竞态。ModelGateway 将 ambiguous dispatch 保持为 unknown 并保留 stable call ID/预算，按现有对账边界处理；它不自动取回尚未落库的 Provider 响应。实际 `make pc` 的合成失败恢复请求未显示回复，因此真实 PC/DSH 交付仍未通过验收。当前 `task_validation_reviews` 不得复用为本 outbox。

## 6. R07 / R25 / R26：验证、来源与审批证据

### 6.1 验证事实合同

现有验证结论由服务端决定，值为 `pending`、`PASS`、`FAIL`、`N/A`。每次复核至少绑定 `(owner_id, task_id, task_revision, result_event_sequence, result_sha256, claim_generation)`，并绑定实际检查及其来源/版本。模型报告本身不是 verdict。证据不足、来源不可读、执行事实 unknown、权限或授权失效时为 `pending`，不得推断 PASS；明确适用检查失败才为 FAIL。

代码修复计划的每个新步骤必须用 `PlanStep.verification_applicability` 声明 `check` 或 `not_applicable`；`check` 必须携带 typed `verification_check`，后者绑定检查种类、命令、声明覆盖路径及来源。旧计划缺少 applicability 时仍可读取，但适用性未知，H07 保持 `pending`。服务端 typed-check receipt 已绑定 Task/plan revision、调用和 operation 身份、命令/检查/覆盖清单摘要及 Runtime 提供的 Workspace view、manifest 与退出事实；Store 复核会重读这些账本事实并校验已声明的必需来源身份。该摘要证明的是计划声明的覆盖路径，不能单独证明测试实际覆盖了这些路径；必需来源的哈希也不能证明来源语义或计划清单完整。review worker 在模型 settled 后重新读取最终 Task Workspace manifest，并把 Runtime 发布围栏保持到 Store completion；Runtime export、shell receipt v2 与 final proof 共用 `morde-task-workspace-snapshot-v1` 摘要，Store 在同一 completion 事务将 proof 与当前 Task、Host fence 和 typed check receipts 对账。App/Worker/Runtime 与定向 PostgreSQL 的本地回归通过；真实 DSH Host→Portal 活链路仍未验。**H07 PASS 仍要求独立可信事实证明检查要求集完整。**当前没有权威事实证明计划覆盖了用户/项目的完整明确要求，因此即使所有已声明检查通过，`requirement_set_verified` 缺失/false 时 H07 仍为 `pending`；例如来源明确要求全量测试而计划只声明定向测试，不能据定向测试 PASS。计划名单、影响图、退出码或模型自述都不能单独扩大授权或证明完整覆盖。红测/全量测试按用户请求和项目要求执行；明确要求的检查不可省略，其他检查按风险选择。未运行或失败须如实交付，不能被状态名改写为 PASS。

新计划工具的 user-message 来源只接受 `locator=current_task_input`、`locator=current_task_turn_input` 或 `locator=history_search_result`，不要求模型计算 SHA 或猜测历史 `message_id`。初始输入定位固定指该 Task 最早已投递的用户消息；当前轮定位的 message ID 由受信 DSH 请求元数据提供。后续历史消息必须使用授权历史搜索返回的 `history_result_token`：服务端签名绑定当前 Task、owner/initiator、conversation/project、Task revision、授权版本、历史水位、消息 ID 与原文 SHA；App 验证后由 Store 按当前 Task、owner、conversation 和 user role 重新读取已投递正文、重算 SHA，并与签名来源摘要比较。持久化的 canonical source 只保留服务端解析出的 `message_id` 与摘要，不保存临时 token；新提交拒绝模型直接提交历史消息 ID 或任意 SHA。新的 required `project_file` 来源由服务端 App 从 Task 授权范围内的不可变 Workspace revision 读取 manifest 与真实 blocks，验证文件摘要并保存 canonical source receipt；模型提供的 SHA 不作为依据。live source、越权、缺失 revision、token/内容不匹配或文件字节不可读时 fail-closed；旧的已持久化规范来源仍保持可读取/可恢复。模型需从已授权 Workspace 读取结果取得 path/revision；用户无需提供内部 ID 或哈希。

### 6.2 审批与工作项现行接口

- `PendingRequest` 是不可变、版本化的准确工具调用审批，包含 Task/调用身份、`task_revision`（新记录必填）、`call_id`、tool、内部 request hash、Host runtime/control fence、状态/决定和到期时间。request hash 不出现在公开响应。
- 对话与审核页使用相同 approval `id` 与 `version`；两个入口统一调用 `POST /api/tasks/{id}/approvals/{approval_id}/responses`，提交 `version`、`approve|reject` 和 `Idempotency-Key`。重复提交按同一身份幂等；版本过期冲突、到期、拒绝、撤权均不得派发操作。批准只表示允许该次精确调用，不证明成功。
- `TaskStepDetail` 只通过 owner/Task 授权读取；公开响应包含步骤身份/事件序号、摘要和 `truncated`/证据摘要标记，不将数据库行或敏感 request hash 序列化给客户端。截断时不能把摘要呈现为完整输出。
- Portal 的 `TaskApprovalMcpApp.tsx` 在沙箱 iframe 内承载审批 UI，使用 `TaskApprovalCard.tsx` 提供的同一 approval snapshot 和 `onDecision`；该组件通过现有 Portal API 回调。当前不需要为它新增服务端 `ui://` MCP Resource；服务端只保留面向云桌面观察的只读 MCP Resource。若实现改成服务端托管资源，必须另行补授权、CSP、OpenAPI/注册和隔离测试。

### 6.3 尚未满足的证据

- H07 对修复任务仍要求不可变工作区/覆盖证据；缺少时应保持 pending。当前超过 4 KiB 的内容证据只提供有 `truncated` 标记的预览，不足以证明全文语义。
- 审批事实对 Hub、sandbox 等操作若无精确 ledger/approval 绑定，保持 unknown/pending；不得把“已批准”投射成“已执行成功”。
- 现有审批 HTTP/OpenAPI 与 Postgres 版本/幂等记录可复用，不新增第二个审批 ID、状态机或响应 API。

### 6.4 H07 要求清单与确认事实

Plan event 是唯一候选 `RequirementManifest` 来源。B 的 Plan 合同保存服务端解析后的义务/source identity、`requirement_ids` 映射及 typed-check `scope_mode`；A 的 App/Store 在确认前从当前持久 Plan event 重算 canonical manifest digest，不信任模型或客户端提供的 digest。该候选清单及其 digest 只说明计划声明了什么，不证明它覆盖了用户/项目全部明确要求。source identity、SHA、typed-check receipt、影响文件列表或模型自述均不能单独证明清单完整；全量要求若只声明/执行了定向检查，不得将全部要求判 PASS。

A 已增加 `POST /api/tasks/{id}/requirement-manifest/confirm` 和迁移 `00252_task_requirement_manifest_confirmations.sql`。请求 body 只携带预期 `task_revision`、`plan_revision`、`plan_event_sequence`；候选 manifest digest 只通过强 quoted `If-Match` 提交，幂等键通过 `Idempotency-Key` 提交，确认人从已认证 Principal 取得。服务端按 Workspace/project fence→Task row 的锁序，在同一事务重查 owner/当前 Task 授权、Task 修订、最新 Plan event 身份及序号、Plan fingerprint/摘要，并调用 `Plan.RequirementManifestDigest()` 重算 digest。只有精确当前版本匹配才插入不可变确认事实；同一 event 仅允许一个 idempotency key 的事实，精确重试返回原事实。确认记录绑定 `owner_id`、`task_id`、`task_revision`、`plan_revision`、`plan_event_sequence`、`manifest_digest`、`confirmed_by_user_id`、`confirmed_by_principal_kind`、`task_authorization_version`、`idempotency_key` 与 `confirmed_at`。Store 同事务消费者可按 owner/Task/revision/plan revision/event sequence/current auth version/digest 精确读取该事实；消费方仍须重新验证当前授权有效，不能只比较 auth version。已取消或陈旧计划、授权失效或摘要不匹配时拒绝，且不产生确认行。

这条 API 只记录用户对精确候选 manifest 的显式确认，不自行写 `RequirementSetVerified`，也不单独成为 PASS。D replay verifier 已在同事务调用 Store confirmation projection，并核对当前授权、source、manifest digest 与 Plan event sequence 后投影 `RequirementSetVerified`；对应 loopback PostgreSQL 读取/映射回归已通过。PC 确认 UI 尚未接入，当前没有生产确认事实，因此缺确认仍为 `pending`。`ActualCoverageVerified` 仍没有 Runtime producer，H07 继续 pending；runner 对完整清单的实际覆盖仍未验证，真实 PC/DSH Host→Portal 活链路也未验。

### 6.5 R26 来源位置与结论引用

Task step detail 可附结构化 `source_locations`。每个 locator 的稳定 `id` 由服务端绑定 Task owner、Task、step、Task revision、工具调用及定位内容生成。成功内置网页读取当前只记录去掉 query/fragment 的 HTTPS 请求 URI、`state=requested_uri_only` 和同一读取输出的摘要；它不证明重定向后的最终来源或不可变网页版本，凭据样式 URL 不返回。

成功的 Hostless Workspace 读取和搜索也会保留服务端验证过的位置元数据，不保存文件正文：文件读取包括 Workspace ID、请求 revision、相对路径、文件内容 SHA-256，搜索还包括一基行号；基于不可变 manifest 的读取标记 `immutable_workspace_revision` 并绑定 manifest SHA-256。live directory 读取标记 `live_workspace_directory`，保留当次内容摘要但明确没有不可变 manifest/version。敏感路径、失败读取、身份/revision/摘要不匹配不会产生 locator。Task detail API 再验证 locator ID 与 Task/step/tool-call 身份，并对 Workspace locator 执行 Workspace 访问检查。

该合同只提供可展示的 Task step 定位，**尚未**验证模型最终结论到 `source_locations.id` 的映射。网页请求 URI也不是已核实的最终来源；Workspace live 数据也不是不可变版本。claim 目前仍绑定 Task 修订、事件序号、step 与工具调用身份，但 D 尚未把每条重要结论精确映射到 locator 并对缺项保持 pending，E/PC 尚未完成实际展示验收。来源不能取得或定位时，报告应明确说明限制。T57/T59 的真实 DSH + PC 验收未完成。
