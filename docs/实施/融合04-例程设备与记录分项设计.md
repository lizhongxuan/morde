# 融合 04：例程、设备与记录分项设计

> 2026-11-01。对应[融合 04 TODO](融合04-nanoMuse功能及管理后台迁移实施任务todo清单文档.md)的 F04-T03、T04、T06～T09。本文区分已有规则、源码事实与拟实现方式；未验证部分不表示已完成。

## 1. Goal 与 Schedule：先复用，再扩展

**已有合同：**00 第 9.2 节、`server/internal/domain/schedule` 和迁移 `00017_schedules.sql` 已定义 once/daily/weekly、IANA 时区、DST、错过策略、授权及不重叠；数据库以 `(schedule_id, occurrence_key)` 唯一，`schedule_version` 是运行快照，不是允许同一时点再执行一次的钥匙。错过默认 `skip`，`run_once` 最多补一次，正常轮询容差 1 分钟；DST 缺口跳过、重复墙钟时间取较早时刻。不能把旧方案中的三元组去重理解为可以跨版本重复执行。

**原客户端事实：**iOS `NanoMuseScheduler.swift` 将工作日表示为周一至周五；每 N 小时用实际经过的秒数，首次检查约在创建后 1 分钟，之后按上次开始时间加 N 小时。Morde 现有 Schedule 类型尚无每 N 小时；PC 原代码还存在 `cron`/`every` 字符串，不能直接等同于当前服务端已支持。

**切片：**F04-T03.01～.06 先恢复 Goal 和已有 Schedule 的唯一业务入口、去重、撤权和已定错过/DST 规则。F04-T03.07 再将工作日映射到 weekly 的 1–5，并单独设计和测试每 N 小时规则；按真实原功能核对首次、启停、编辑、故障恢复和跨 DST 的时点。每次触发仍走同一 Task 与预算/授权事务；停用旧客户端执行器但保留旧计划，明确导入和启用前不自动执行。

N 的允许范围、旧计划重新启用时的首次触发等若无法由已有规则和实际原功能确定，只暂停该扩展并给用户展示具体场景与选项；不能阻塞 Goal 或已定义的日/周计划，也不能把默认 `skip` 擅自改成全部补跑。范围确定后，同步 OpenAPI、持久模型、客户端及同一时点去重测试。

## 2. Hub：设备连接不等于执行授权

当前原 iOS `NanoMuseHub.swift` 声明 `info/open/notify/task/stop`，其中 `task/stop` 会启动或停止手机本机 Agent；融合版必须去掉该执行链。原 `hub.py` 会转发 `call/event/result` 并在断线时清理待处理调用；presence 是提示，不是任务或同步事实。上述是旧代码事实，不能推断 Morde 已有同等服务。

原 PC `cloud.ts` 注册了 `actions.ts` 的 `screen/shell/files/file.get/file.put/open`，其中 shell 以当前登录用户身份运行；`coding.ts` 还提供本机编程 Agent 的查询和发送接口。原 iOS 对 `open` 只接受 HTTP(S)，`notify` 依赖系统通知许可，而 `screen` 不支持；平台能力不能混为一谈。旧 PC `info` 返回用户名、home 和 cwd，这些路径不应未经新权限核对就原样暴露。旧 PC 的遥控总开关和可信设备可绕过逐次询问，旧 iOS 的 remoteControl 默认开启；既有决策禁止旧常驻授权自动升级为 Morde 授权，不能直接沿用这些默认值。

**用户于 2026-11-01 确认：**本期保留云端 Agent 请求 PC 截图、查看文件和执行命令的受控能力，分别拆任务；目标 PC 须授权，各能力未通过各自门禁前不可用。客户端不启动或委派本机 Agent；列表/presence 和基础调用可独立推进。原版 `file.put` 本期也保留，但只能写目标 PC 已选择的 Workspace，沿用同步限额及覆盖前安全副本，**F02-T10 通过后才能开放真实写入**；截图、文件查看和命令不因此等待。

**拟实现合同：**请求来源可以是 Morde 受权云端 Task，不伪装成另一台安装设备；服务端绑定账号、Task、授权版本、目标设备和 action，目标 PC 再按自身新授权及系统权限判断。旧的全局遥控开关或旧可信设备不能自动升级为新授权。PC 可在可信原生层实现必要的单次动作并复用原源码的行为，不能为此启动旧 dsh、本机 Agent 或工具循环。每个 action 的参数、结果和大小有界；截图与读取到的内容只进入获准的当前业务处理，不自动变成额外完整记录，日志和审计不包含截图、文件正文、命令输出或凭据。实施和验证仅在本地隔离环境使用合成内容，不对外发送文件。

| 独立切片 | 目标端处理及验收重点 |
|---|---|
| 截图 | 目标 PC 授权及系统屏幕权限均有效才执行；拒绝、超时、撤权或系统不可用有真实结果，测试只采集隔离的合成画面 |
| 文件查看 | 列目录/读取前明确目标和用户允许的范围，处理符号链接、路径替换及权限变化；未选择的本机内容不作为云端上下文，读取结果不可用摘要替代授权 |
| 文件写入 | 只写用户在目标 PC 选择且授权的 Workspace；先校验目录身份和路径、保护被覆盖文件，再按 02 合同同步；本机写入与云端确认分别报告 |
| 命令 | 在目标 PC 的受控执行边界内运行，显示命令及目标供授权；限制执行时间、输出和进程生命周期，取消或断线后未确认停止显示未知，不盲目重试 |

**文件写入拟实现顺序：**

1. 请求明确账号、Task、目标安装、`workspace_id`、相对路径及内容大小/摘要；目标 PC 依据当前映射、设备授权和用户选择定位目录，不接受远端指定的绝对本机路径。目录重绑、链接穿越、路径替换、撤权或无法核实身份时拒绝；执行前再次核验，不能只做一次字符串前缀检查。
2. 沿用 02 的单文件 300 MiB 和每 Workspace 5 GiB 同步准入、冲突及不可变检查点；涉及大文件时复用 F02-T10 最终确认的受限传输方式，不把 300 MiB 正文塞进旧 Hub 帧。原 `actions.ts` 的 `file.put` 使用 base64 且仅限 8 MiB，不能证明它满足新合同。真实写入与端到端功能须等待 F02-T10；此前仅可在本地隔离目录做路径、授权和保全验证。
3. 覆盖前复用 F03-T06.04/.05 的安全副本规则，副本在所有同步目录外、不自动上传、不计 Workspace 额度；保全失败、磁盘不足或无法保证旧打开句柄后续写入可恢复时暂停，保留原文件。同步与安全副本仍各自遵循 02/03 真实实现，不能仅依赖旧 `rename` 或 Syncthing 默认版本库。
4. 本机写入和云端确认分别报告：本机写入已持久但尚未通过服务端 5 GiB 准入/持久读回时显示待同步或拒绝，保留本机文件和安全副本，不伪报云端已保存。若 Task 要求文件交付，仍须通过 02 的检查点、摘要及必要 Host 确认，不能只凭目标 PC 返回成功完成 Task。
5. 写入在途断线或回执丢失时，持久记录操作 ID 与阶段并先对账；无法证明是否执行时显示未知，不盲目重放覆盖。重试和并发修改时重新核验目标及版本；同一内容的摘要不足以证明修改来源。

PC 目录同步到服务端后，若没有满足 02 Task 私有视图、受控发布及操作回执的完整来源证明，该变更按外部变更处理：相关旧输入 Task 暂停并要求按新版本重新提交。不能仅凭本次设备调用的 Task ID 或相同摘要推进 Task 自身检查点；若未来 F02-T10 提供了可验证的等效发布合同，按最终合同实现并补回归。

**不能互相等待的两阶段边界：**当前 `workspace_sync.go` 与 `workspace_sync_receive.go` 在 Workspace 存在 `prepared/dispatched/unknown` 的 Task 操作时拒绝变更提交；`task_operations` 又以 Host ID 为必填外键，不能把 PC 伪装成 Host。若新设备操作一直等“同步成功”才结算，而同步提交又等该操作结算，就会互相等待；若绕过这些检查直接提交，则可能让旧 Task 在文件漂移后继续产生副作用。

拟让 PC 写入有可审计、与 Workspace 同步/Task 停止共用围栏的持久操作状态；可以扩展现有模型或增加必要的设备操作记录，但不得伪造 Host，也不得只在 Hub 内存中记状态。目标 PC 已可靠确认本机操作结束后，在同一持久顺序点结算本机阶段并让 Task 停止派发后续操作，再允许 02 处理同步；云端确认后按前述来源规则处理检查点或暂停。若 PC 操作结果未知，保持相应 Workspace/Task 的安全阻断并对账，不能为解锁而把未知改成成功；不影响其他 Workspace 的独立任务。F04-T04.06f/.06g 先用本地真实数据库分别验证围栏参与和释放顺序，真实文件联验仍等待 F02-T10。

旧 `task/stop/approve` 本机 Agent 委派链以及启动/操纵本机编程 Agent 的路径不恢复。任意 shell 可能间接启动本机 Agent 或直接修改受保护文件，不能只靠 action 改名、命令字符串黑名单或来源端批准声称满足既有边界。实现前先在目标平台证明可执行的限制、停止和文件保护；证明不足时只关闭命令 action 并记录冲突，截图和文件查看不受影响。

本地 `project/nanoMuse/harness/desktop/package.json` 有 macOS、Windows 和 Linux 的 x64 构建入口，这只证明构建配置存在，不证明它们已在融合版交付或具备同等进程隔离能力。命令的共用协议先独立完成，再按本期实际声明支持的平台分别验证目标端授权、进程及后代停止和文件保护；缺少一个平台的环境只让该平台保持待验证，不阻止其他平台或截图/文件查看。不能因当前机器缺少环境就擅自排除原要求的平台。

按 F04-T04 分成设备登记/presence、双端授权的非 Agent 调用、PC 接入和 iOS 接入。先列出各端实际 `info/open/notify` 等非 Agent action 的用途、目标权限及参数，逐个决定保留或明确不支持；不可因为设备在线或客户端自报 action 就视为获准。`open` 等有副作用的请求必须由目标端自身配置和权限决定；重连只查询状态，不盲目重发已发出的调用。禁止 `task` 把 Agent 分派到 PC/iOS，也不能把云端 Task 的停止混成对设备的 `stop`。

来源与目标使用已验证的 Morde 账号、安装和设备归属；跨账号、未知 action、超限、已撤销或目标不在线应有明确结果。队列、超时、取消和断线有界；结果未知时不能显示已执行。可用本地测试端构造消息，不对外发送文件或通知。

设备调用要区分“尚未发送”“已发送但结果未知”和“目标明确返回结果”：超时或断线不能证明目标没有执行，也不能将取消显示为已撤销副作用。重连能查询到有权且可靠的结果时才展示该结果，否则保持未知并由用户决定后续操作；无需为基础 `open/notify` 擅自承诺已有持久调用账本。通知被系统接受也不等于用户已经看到。网页打开先只处理经过校验的 HTTP(S)，本地文件打开另按原功能映射及目标授权核对，不能把文件写入决定自动扩大为任意本机打开权限。

## 3. 完整记录：同意、异步写入与撤回

完整记录是额外副本，默认关闭，用户按用途和类别单独同意；普通会话、业务附件、用量账本和恢复检查点不是这份副本。训练贡献是另一用途。拟新增的同意、记录和管理接口见 04 清单第 2 节，必须同时落实权限、审计和调用方，不能先开放空接口。

关键顺序：① 请求入队前校验当前同意和可配置的期限/额度；② 异步消费者实际持久化前重新校验同意；③ 管理员读取/附件/导出时再检查当前同意及对应权限；④ 用户撤回后禁止新采集与新的内容访问；⑤ 是否删除已有记录由用户另行明确选择。客户端展示等待、成功和失败，不把队列已入队当持久完成。

排队项绑定**采集时的同意版本**，不只是检查“现在是否同意”：同意 v1 时入队 → 用户撤回 → 重新同意 v3 时，旧 v1 项不能借新同意落库。若队列本身持久化了正文或附件，它已经占用额外存储，入队时就须执行同意、容量预留和到期控制；撤回后清理尚未完成项及其临时附件，失败保留待清理状态，不计作已删除。队列满、额度满或记录存储故障只使额外记录失败，不应中断普通聊天、业务附件或已受理 Task。不得为排队悄悄复制一份无期限、无额度的正文。

**并发屏障：**撤回和异步落库必须有共同的持久顺序点，例如同事务锁定账号/用途同意版本再确认和写入：撤回先提交时，迟到的消费者不能写入；记录先提交时，其历史副本仍按用户选择保留或删除，但撤回后不能继续以管理员权限读取。暂存附件提交、删除与回收应互斥并重新检查引用；只靠模型进程内布尔值或排队时的一次校验不够。下载/导出按受权请求分块复核当前许可，已交付的数据无法撤回；失效后停止后续读取并记录未完成。

**用户于 2026-11-01 确认：**额外完整记录默认保留 **30 天**，每账号默认额度 **1 GiB（1,073,741,824 字节）**，管理员可调整；完整记录依旧默认关闭，必须由用户单独同意。普通会话和业务文件不计入该额度，不能因为记录过期或额度满而删除或禁用。

**拟实现口径：**额度计入已持久化的额外记录正文和记录专用附件的字节；不把普通业务正文或业务文件计入，重复引用及专用副本的计量规则在实现时固定并做并发测试。按记录写入时间及当时的已生效保留期限确定到期时间；管理员调整默认值用于之后创建的记录，不悄悄缩短已有记录期限。若调低额度后已有用量超过新上限，则保留未到期记录、拒绝新增额外记录并提示，不自动删除普通业务数据。到期清理和用户独立确认的提前删除须同步清理对应索引及专用附件引用；撤回同意先停止新采集和后续内容访问，历史记录按既定到期时间保留或由用户另行选择删除。过期清理失败显示待处理，不能伪报已删除。

按 F04-T07.01～.08 验证：排队后撤回、并发删除/写入、权限撤销和备份恢复均不能复活额外记录或授权；密钥/Vault 不落记录；已引用的普通业务附件不受记录清理影响。额度满、保留到期和清理失败需有可见结果，不静默删除其他业务数据。管理查询/正文/附件/导出/删除权限分开，敏感操作留审计。

## 4. 管理功能逐类交付

以 04 清单第 3 节为验收源，每一类后台独立完成“实际数据来源 → API/权限 → 页面 → 内置浏览器操作”，沿用现有用户、模型、账本、容量和审计来源。F04-T08/T09 的 11 类可以分别交付，不依赖所有 Console 页面完成后才验证第一类。历史决定（2026-11-01，后于 2026-11-03 覆盖）：当时默认不自动发放新用户免费额度。现行规则是新注册账号首次经管理员批准时按管理员配置发放默认模型额度；未配置则保持待审，既有预算及账本保留，重复批准或 disabled 恢复不重发。邀请与贡献奖励仍不自动发放；原管理功能验收记录保留。

现有 `server/migrations/00057_model_call_ledger.sql` 已规定模型预算不自动创建；`server/internal/store/postgres/model_usage.go` 在账号未配置模型预算时返回 `quota_exceeded`。因此新用户在管理员设置预算前不能调用平台模型；已有预算和账本不因本次决定被删除或重置。F04-T08.12 分别验证注册/审核、邀请及贡献事件不自动发放，并验证管理员显式配置预算及审计。模型预算与 Host 资源上限、Workspace 同步及完整记录的存储额度是不同限额；现有资源上限不因不自动发放奖励而改变。

**静态核对事实：**原 Console 在 `project/nanoMuse/cloud/console/src/pages/`；Morde 当前 OpenAPI 有管理员用户、Host、Workspace、容量、模型用量核对/预算及审计接口，不能据此推定原 Console 的全部统计或内容查询已实现。原 Console `lib/api.ts` 使用浏览器 `sessionStorage` 中的 `X-Admin-Token`，且 `X-Admin-Actor` 可由浏览器自填；迁入时使用 Morde 管理会话和服务端认证身份记录审计，不能照搬该 token 或把自填 actor 当操作者。
