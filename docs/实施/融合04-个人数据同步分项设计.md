# 融合 04：个人数据同步分项设计

> 2026-11-01。对应[融合 04 TODO](融合04-nanoMuse功能及管理后台迁移实施任务todo清单文档.md)的 F04-T01.02、T02、T05 和 T06。本文是可实现的设计方案，不代表服务或接口已经存在；具体字段在对应切片实现时与 OpenAPI、客户端及测试一并定稿。

## 1. 边界与先后顺序

当前 Morde 已有会话/消息、Task 和 Workspace，同步文件由 02 负责；本次只为账号资料、记忆、目标等建立个人数据同步。`server/openapi/portal.yaml` 当前没有本文拟新增的个人对象、账号变更流或附件上传接口。原 `nanoMuse/cloud/nanomuse_cloud/sync.py` 可作行为参考，但其“关同步即删除”、按设备时间覆盖及 30 天后删除墓碑等做法不符合现有融合规则，不能原样迁移。

原 iOS `Agent/Sync/CloudSyncEngine.swift` 会把 provider key 和环境变量值编码到 `secretsJson`/`envSecretsJson`，V2 hydrator 也调用这些导出方法。个人同步必须按类型和字段白名单构造，不可只替换原 CloudKit 的服务地址；旧备份/恢复路径也不能重新导入已定向删除的旧模型 key，其他凭据按原数据保护规则保留。

先做一个真实个人对象的写入、变更流和幂等闭环，再扩展资料/记忆、Feed/Ideas/Library 与非秘密配置；附件、历史导入、PC 和 iOS 各自独立验收。会话、Goal 和 Schedule 继续调用各自唯一业务用例，变更流只作为投递索引，不另建第二套可写正文。未接好的类型明确显示不可用；服务端不能因某类完成就宣称全部类型完成。

## 2. 一次修改怎样不丢、不重

拟新增个人对象和变更日志入口；对象 owner 从已认证请求取得，客户端不能指定其他 owner。每个设备在本地持久化 `mutation_id`、对象标识、原版本及请求摘要；先保存待发送项再发网络请求。相同账号、相同 `mutation_id` 和相同请求重试返回原结果；相同 ID 不同请求拒绝。实际数据库事务把对象变更、变更日志及幂等结果一起提交，失败时三者均不生效；用户可选择的本地历史不因登录自动上传。

**重试与删除的边界：**去重回执只需保存请求摘要、对象标识、结果版本和状态等最小信息，不保存可被后续重试取回的正文或凭据；查询回执仍须校验当前账号和安装授权。结果提交后响应丢失、随后对象被删除时，同键重试返回原操作已处理的最小回执，但不能让已删除正文重新可读。为支持长期离线 outbox，暂按现有 `idempotency_keys` 的不设过期字段方式保留必要回执；以后若要清理，须先证明旧请求不会再被接纳，或以可验证的同步代次使过期请求明确失败，不能把旧键当新请求执行。

**顺序陷阱：**事务 A 先取序号 1、事务 B 后取序号 2，但 B 先提交；设备读到 2 并保存游标后，A 才提交，就可能永远漏掉 1。不能单靠 PostgreSQL sequence 宣称按提交顺序递增。

**拟采用的最小屏障：**同一账号的写入在同一事务持有账号变更序号行锁，分配下一序号并写日志，直到提交/回滚才释放；不同账号仍可并行。F04-T02.02 先完成首个个人对象及基础设施；F04-T02.11 再把会话、Goal、Schedule 以及 Agent/客户端相关写入口接入同一屏障。接入前核对既有事务锁顺序，统一获取顺序，避免与 Task/授权锁形成死锁。用真实 PostgreSQL 控制上述 A/B 提交顺序、重试和失败回滚，验证客户端不会跳过已提交变更；不能只用单进程计数或模拟数据库。

**现有版本缺口：**`00017_schedules.sql` 的 Schedule 有 `version`；`00002_tasks.sql` 和 `00054_fused_task_conversations.sql` 中的会话及消息没有通用对象修订号，消息 `sequence` 只表示会话内顺序，不能拿来比较同一消息的后续修改。F04-T02.12a/.12b 分别处理会话消息和目标计划的可比较版本；可以复用已有业务版本或维护只含版本的同步索引，不复制第二份正文。快照返回的正文、删除状态和版本必须来自一致读取；一类写入口未接入前，该类型的同步能力不能开放。

## 3. 分页快照、断线和冲突

1. 首次同步或游标过期时，客户端先保留按账号隔离的本地 outbox 和设备私有资料；服务端返回账号当前已提交的变更水位 `H`。客户端按固定类型集合及不可变 `(对象类型, 对象 ID)` 分页读取当前云端对象到临时视图，每行携带与正文一致的对象版本；页令牌绑定账号、实例、类型范围和位置，不可跨账号或中途改变范围。分页期间的新增、修改和删除均写入大于 `H` 的变更流。
2. 分页结束后从 `H` 续读变更并按对象版本应用：较旧事件不能覆盖分页时已看到的新版本。先处理完一个服务端确认的水位，再将临时云端视图与已确认 cursor 一起提交到本机持久存储；未提交的本地 outbox 重新按原 `mutation_id` 对账。中途崩溃重来不能清空原本地数据。
3. 若 `H` 之后所需日志在分页期间被清理，服务端明确返回“重新拉取快照”，客户端保留 outbox 并重来；不得直接把 cursor 跳到最新。实现时明确日志保留与该过期错误的边界，避免长时间离线被误当已同步。
4. 同一对象并发编辑通过 `base_revision` 条件更新。冲突返回可定位的当前版本，保留用户本机未提交内容及可恢复冲突副本，由用户处理；不按设备时间或最后到达静默覆盖。
5. 删除使用带版本的墓碑，停止会复活该对象的旧 outbox；已有未发送编辑保留为可恢复的本地草稿并提示用户，不自动重建已删对象。即使正文及旧变更日志已清理，仍须保留不含正文的最小删除标记或等效证明，防止长期离线设备用旧 ID 复活对象；账号删除另按数据生命周期处理。旧 ID 不得被静默重新用于新对象。

增量追赶须先固定本轮结束水位 `K`，处理完 `(H, K]` 后提交临时视图及 cursor；持续写入不能让首轮永远等不到“最新”。若对象读取已包含 `K` 之后的版本，按对象版本去重且仍从 `K` 续读，不得把它当成已确认其他对象的变更。退出或切换账号后，旧同步任务不得把临时视图提交到新账号；分页、鉴权或版本校验失败时保留原视图和 outbox。

F04-T02.06、.09、.10 分别验证快照与增量交错、cursor 过期/崩溃恢复、删除与旧设备重连；必须覆盖两设备和不同账号。采用其他实现时须证明同样的无遗漏、保留 outbox 和不复活语义，不以“最后看到的 cursor”充当证据。

## 4. 附件与本地历史导入

附件先进入受限暂存，服务端核验认证账号、类型、大小、摘要和持久读回；实际业务对象的附件引用、版本变更和幂等回执在同一数据库事务提交。重复提交返回原结果；取消只清理未引用暂存，不能删已引用附件。回收暂存时须与提交互斥并重新核对引用；共享摘要不授予跨账号读取权限。记录专用附件和普通业务附件分别授权。

**请求大小缺口：**现有 `server/internal/api/api.go` 对普通 API 使用 `http.MaxBytesReader`，`deploy/single/portal.yaml` 的普通请求上限为 1 MiB；Workspace 块上传有单独的 4 MiB 路由上限。个人附件路径尚不存在，不能假设一个 300 MiB 请求能够通过现有链路。拟为个人附件增加有界分片上传，独立认证及个人额度，分片重试按序号和摘要幂等，最终核对完整大小/摘要再提交引用。只为该上传路由设置必要的有界请求限制，不全局放大普通 API 限制；网关、超时、重启和管理员调整上限都须联验。F04-T02.07a～.07c 分别交付会话、分片和提交回收，实际额度准入由 F04-T02.14c 完成。

历史导入只处理用户选定范围：先给本地预览，按 `(source, device/account, entity type, source ID)` 建立可重试映射；关联附件必须已获准且可读。写入会话历史不创建或重跑 Task，不自动启用旧例程。旧 nanoMuse Cloud 线上账号和历史已明确不迁移；与其不同的客户端本地数据仍须保护。

## 5. 普通个人数据容量

**用户于 2026-11-01 确认：**头像、资料、SOUL/记忆/日记、目标及例程、动态/点子/资源库等普通个人同步数据及其附件，默认每账号 **5 GiB（5,368,709,120 字节）**，单附件默认 **300 MiB（314,572,800 字节）**，管理员可调整。普通聊天不计入这一额度；Workspace 和额外完整记录分别使用各自额度。超限时保留已保存内容，不因这一额度拒绝普通聊天、Workspace 或额外记录。

**拟实现的计量口径：**按 `(server_instance_id, user_id)` 统计该账号的已确认个人对象内容和个人用途附件的逻辑字节数；在 OpenAPI 中固定被计数字段、编码及计算方法。附件按当前账号持有的附件对象计一次，同一对象的多个个人引用不重复计；不同账号各自计量，不能因摘要相同绕过权限或额度。只用于普通聊天的附件不计入；同一附件同时被个人对象引用时，按个人引用计一次，解除个人引用不能删除仍被聊天使用的内容。临时上传以预留单独显示，提交后转换为已用量，不能重复计算。

**拟实现的准入顺序：**写个人对象时在同一事务内核算变更前后的字节差、对象写入、变更日志及 mutation 回执；上传先校验声明大小并预留，流式读取过程中复核实际大小，提交引用时与额度账本及对象版本一起结算。并发写入、取消、过期回收和管理员调整须共享可核对的顺序点；不能只在前端检查，也不能以客户端自报大小确认用量。账号总量和单附件正好等于上限时允许；超过时拒绝新增或扩容并提示，保留本地待上传内容和既有云端内容。调低上限后允许删除或缩小以恢复，不自动清理用户内容。

计划触发时的运行状态、下一次触发时间、去重标记和同步游标不作为用户内容增长；已获准例程的触发、既有 Task 推进及必要状态落库不能因个人数据额度满而被误拒。管理员在上传预留期间调低限额时，提交阶段重新按生效配置核验；不能提交则保留客户端原件和已确认内容，并安全释放未用预留。

预留/文件写入失败和磁盘不足应可重试并释放未使用预留；未引用暂存的清理不能删除已有引用。物理磁盘和备份容量仍需单独检查，逻辑额度不是物理磁盘预留或对其他服务可用性的保证。F04-T02.14a～.14h 分别实现额度、各类个人对象、附件和目标计划准入；管理员调整归 F04-T08.13/F04-T09.12，最终联验归 F05-T05.28。
