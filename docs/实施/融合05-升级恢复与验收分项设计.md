## 2. 安装身份：先确定路线，再验证可行性

原工程恢复与正式身份是不同问题：原 iOS 工程可从已确认的本地 Git 历史取回并合并。**用户于 2026-11-01 选择先做本地可行性核对，再决定正式身份；尚未选择原身份或独立 Morde 身份。**两种路线都必须保护原数据：

- **原身份路线：**先验证应用标识、签名团队、AppGroup、Keychain 和扩展是否真的可用，再用隔离安装验证升级。缺少签名或权限时不承诺原位升级。
- **独立身份路线：**保留旧应用和数据；先核对旧版是否支持本地导出，以及文件、附件和扩展数据是否能完整导入。iOS 不可假设新 Bundle ID 能直接读取旧应用沙箱或旧 Keychain；原身份模型 key 的同步/非同步项能否按 D2 清理也须验证。导出或清理能力不存在时记录真实缺口并提问，不宣称数据已迁移或旧密钥已删除。

F05-T02.05a/.05b 分别调查 PC 和 iOS 的原签名/权限、原版导出、附件与旧 Keychain 清理能力，整理各路线的本地验证证据、数据影响及未完成项后，再请求用户选择。最终身份未定或某平台的签名问题只阻塞该正式升级路线，不阻塞 03 原工程、服务端、04 功能与本地隔离验收。

## 3. 服务端升级和回退的写入屏障

02 已记录：新 `workspace_sync_commit_receipts` 与旧 `idempotency_keys` 尚无跨版本原子键空间。新旧实例混写可能让同一幂等键在两张表各提交一次，且旧版不理解新版终态额度拒绝。**当前方案不是滚动混跑：**升级前先停止新写入并排空旧实例，再在可恢复副本完成迁移，确认新版读写路径后恢复；回滚也不能让不识别新回执的旧二进制继续接收写入。若将来需要混跑，必须另行实现共享终态合同并做双版本并发验证。

原有 revision/块、提交回执和当前目录的恢复关系以 F02-T06/T09 为准。当前目录物化及备份仍有待验证边界；正式切换文件权威前必须证明数据库、文件和目录从备份恢复后一致，不把现有只检查目录路径的备份参数当成已备份目录正文。

在本地副本执行：停写并记录未完成请求 → 备份并验证可读取 → 迁移 → 核对对象数量、引用、权限和文件摘要 → 写入一份新的合成消息/文件 → 演练兼容版本回退及恢复 → 再核对新旧数据。不能用旧数据库快照直接覆盖升级后新增数据；也不能同时启用旧/新两套可写 Workspace 权威。未知操作和不兼容检查点先对账或暂停，不从头重跑副作用。

### 3.1 旧备份之后的新增、删除和撤权

**现有工具的限制：**`deploy/single/backup/backup.py` 做离线本地备份和原路径恢复，归档 PostgreSQL、Workspace 块和 Site；恢复前另保留当前目录的回滚包。`deploy/single/README.md` 明确它不提供时间点恢复；旧备份自身不可能包含其创建之后的删除、撤权或新增消息。恢复操作的 `RESTORE-JOURNAL.json` 只是目录替换流程日志，不是后续业务删除/撤权清单。新增个人附件和额外记录的存储路径也须在实际实现后纳入备份范围核对，不能默认已有脚本已覆盖。

**拟定本地恢复步骤：**计划内回退先停写并保全可读的当前数据库与文件，再对照旧备份、当前状态和受影响的数据类型，确定能否完整取得备份之后已确认的新增/修改、删除、同意撤回、安装和资源撤权，以及关联附件、Workspace revision、幂等回执和未知操作。只有来源可信、范围与水位连续且依赖的正文/附件可核对时，才可在隔离恢复副本上按业务规则合并；先落实删除/撤权屏障，再允许对应访问或新写入。若不兼容旧二进制，保持受控只读/隔离，不能为声称“回退成功”而交给旧二进制继续写。

若当前库受损且没有可证明连续的后续记录或数据副本，无法自动知道哪些内容已删除、撤权或新增，也不能承诺完整恢复。受影响的内容访问、旧会话及写入保持阻断；列出备份时间、缺失范围、可用来源和可能丢失的数据，向用户呈现具体恢复选择。只恢复未受影响且可单独验证的功能，不以“待重放”掩盖缺失来源。是否采用 WAL、额外日志或其他恢复机制留待实现时基于实际要求选择；无论方式如何，都须验证来源的可信性、连续性和失败关闭，不引入未经验证的第二数据权威。

F05-T03.06a/.06b/.06c/.06d 分别验证有后续来源时的撤权、个人对象删除、缺少来源时的阻断和记录删除；F05-T03.08 单独检查个人附件、记录和其他实际持久路径是否被备份覆盖。恢复中的数据同步独立于普通退出和关闭同步的验收。
