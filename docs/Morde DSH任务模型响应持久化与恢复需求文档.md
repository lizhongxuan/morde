# Morde DSH 任务模型响应持久化与恢复需求

> 状态：目标需求，尚待实施。本文是对现有对话上下文压缩设计的补充，只覆盖 DSH Task 的模型响应恢复。

## 评估结论

DBOS 的做法对 Morde 有实际价值：将完整模型响应持久化后再向 Runtime 发出完成信号，使进程重启后可读取同一响应继续执行，避免已成功的模型调用因结果交付中断而无法恢复。Morde 不应接入 DBOS 或新增第二套 Agent Runtime；应在现有 DSH、模型网关、模型调用账本和检查点边界实现这一语义。

Morde 已为会话压缩摘要保存加密模型输出，并为消息路由保存可恢复的模型决策；DSH Task 的通用模型调用目前在账本中持久化用量与调用状态，模型响应随后通过 IPC 写入 DSH 检查点。检查点确认后才接受后续工具调用，因此已有工具授权和工具结果恢复围栏。但若模型已成功返回、账本已结算，而完整响应尚未写入检查点时进程中断，Task 账本没有可供恢复的响应正文，同一调用会进入对账/阻塞路径，不能仅凭现有账本继续。这是 DBOS 思路在 Morde 中最有价值的补齐点。

DBOS 会在工作流中重试中断的模型调用；外部提供商可能已经处理并计费，因此它不保证外部 API 只收费一次。Morde 也不得对用户或运维承诺模型调用恰好一次计费。

## 目标与范围

对 DSH Task 的每次模型调用，在响应完整、通过校验且仍符合当前交付授权后，先可靠保存完整响应与用量结算，再允许响应进入 DSH。进程恢复时，若相同调用身份和请求对应的成功响应已保存，则恢复该响应而不再次请求模型；DSH 再按现有检查点与工具账本继续。

本需求不改变压缩摘要或路由模型结果的专用恢复路径，不改变 DSH Agent 循环、工具执行、模型选择或消息会话模型。短期流式增量仍可按现有能力展示，但恢复完整响应时不得重复发布已经展示的增量。

## 功能与规则

1. **完整响应先持久化。** 对可交付的有效 Task 模型响应，持久化文本、推理内容、停止原因、完整工具调用（调用 ID、名称、参数）及已知用量。响应与对应的已结算账本状态须在同一持久化事务中提交；提交成功前不得向 DSH 发送 `finish`、`model_end` 或可触发后续工具处理的内容。模型网络请求不得放在数据库事务内。
2. **按原调用恢复。** DSH 以现有稳定调用 ID 重试/恢复时，Morde 先查找已保存响应；只有调用 ID、请求摘要、Task、Agent 会话、检查点序号、授权版本和模型连接版本均匹配，且当前租约与授权校验通过，才解密并返回原响应。原执行代次仍活动时必须匹配原 Agent 实例；合法后继代次仅能读取同一 session/checkpoint 前缀的结果，并须有旧 Agent 实例已停止的持久证明。恢复结果的工具调用和用量必须与首次保存完全一致，不重复预留或结算，也不再次调用提供商。请求或身份不匹配时拒绝恢复并记录冲突。
3. **保留 DSH 执行围栏。** DSH 收到完整结果后，仍须先将 assistant 响应及工具调用写入经确认的检查点，再允许 Worker 接受工具调用帧；工具执行继续通过现有 Broker、审批、授权和操作账本。恢复模型响应不得绕过任何一项检查，也不得跨账号、Task、会话或授权版本读取；代次变化只允许在旧执行者已确认停止且上述恢复围栏仍完全相同时恢复。
4. **未知结果不盲目重试。** 若账本表明提供商调用已派发，但没有可验证的完整响应，按现有未知用量与对账机制处理，不推断模型未执行，不自动换新调用 ID 重发，也不放行工具。若提供商已返回但本地持久化失败，保留可核对的用量/未知状态并阻止交付；无法确认响应是否已提交时，恢复逻辑先查询持久化结果。只有已确认完整响应成功落库，才可无外部调用地恢复。
5. **安全存储与保留。** 响应正文须加密存储并校验摘要；加密关联数据绑定调用和任务身份。限制响应大小，不把 prompt、响应正文、工具参数或密文写入普通日志。响应保留时间至少覆盖 Task 可恢复期间；终态清理沿用现有保留策略，清除正文时保留账本与必要审计元数据。旧版已结算但没有响应正文的调用不能伪装成可恢复结果。
6. **流式输出不重复。** 若首次调用期间已有文本增量对用户可见，恢复时不得生成第二份可见增量；沿用既有流消息标识/交付记录。完整 DSH 响应仍须进入检查点并成为任务最终结果的权威来源。无法安全续接已展示的流时，可以结束旧流并展示唯一的最终结果，但不能重复正文或声称旧流完整。
7. **已有能力保持不变。** 压缩摘要继续使用其加密响应与恢复实现；路由决策继续使用其专用持久化结果。新增 Task 响应持久化应复用 Morde 现有模型网关、账本、密钥管理及事务模式，不新增 DBOS 依赖、第二套计费账本或直连提供商的 DSH 路径。
8. **并发与隔离。** 不同用户、不同会话以及同一用户的多个会话须能在现有配额内并行启动和运行；一个会话的 Runtime 冷启动或续租不得通过管理器全局锁阻塞无关会话。单会话仍遵守现有 Runtime 租约与最大并发 Task 数。响应恢复以 owner、Task、session、call ID 和请求摘要隔离；同一调用并发请求最多一个 provider 派发，其他请求等待或安全失败；结果提交后同键重试复用该响应且只结算一次。不同调用之间不得串结果、串工具或串预算。

## 验收条件

- 合成提供商已成功返回完整文本及工具调用，随后在 DSH 收到完整响应或写入检查点前强制中断；重启后相同 Task 恢复出逐字段一致的响应，提供商调用数不增加、用量只结算一次，工具只在检查点确认后执行且不重复执行。
- 在模型响应已保存、Worker 尚未交付完成帧时中断；恢复从已保存响应继续，不能再次调用模型；请求摘要、Task、会话、检查点或授权不匹配，或前代 Agent 未确认停止时，响应不可读取或交付。前代已确认停止且当前围栏仍匹配时允许后继 generation 恢复。
- 提供商调用超时、响应格式错误、用量未知、保存事务失败及提交结果不确定时，不发送完成/工具信号，不伪报成功；状态按实际情况进入失败或未知/对账，且系统不宣称外部 API 仅计费一次。
- 含已展示文本增量的恢复不会在客户端重复显示同一段内容；最终 DSH 检查点、Task 输出及账本一致。
- 现有压缩摘要恢复、路由结果恢复、Task 检查点恢复、权限撤销、取消和工具操作账本行为无回归；使用合成模型与隔离 PostgreSQL 验证，不能以单元测试或“安装了插件”替代恢复链路验收。
- 至少两个用户、每个用户多个会话同时启动并执行；独立会话冷启动互不阻塞，单会话按配置并发 Task；同一调用并发恢复只有一个提供商派发/结算，结果与检查点仍各自隔离。
