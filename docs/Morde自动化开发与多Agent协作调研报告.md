# Morde 自动化开发与多 Agent 协作调研报告

调研日期：2026-11-11  
范围：本地 Morde 当前工作区代码和文档、仓库内 Muse 材料、DSH 上游及公开工程实践。Morde 工作区存在原有未提交改动，本报告反映读取时的工作区状态，不等同于某次发布的线上能力。

## 一、结论

**Morde 已具备运行开发型 Agent 的一部分底座，但离“输入一句话，自动交付经过验收的复杂项目”还有明确距离。**

1. 已有可恢复的 DSH 任务会话、子会话、后台作业、工具授权、工作区、操作账本、任务依赖和结果回传。它们证明了可以构造开发流程，但目前不等于已经有完整的自动开发产品。
2. 需要分清三个角色：**会话协调器**负责把用户消息分流为回复、新任务或任务控制；**任务 Agent**执行一个 Task；任务 Agent 可以调用 `dsh_delegate` 创建**子 Agent**。当前会话协调器本身没有工具，也不会直接担任能够编写和调度整个项目的开发总工。
3. 子 Agent 的后台模式允许并发，但不会自动获得完整父会话。父任务结束前会等待后台工作；子作业结算本身没有把结果自动投递给任务 Agent 再进行综合验收的完整闭环。独立 **Task** 完成后的会话级结果回传已经另有机制，不能与子作业回传混为一谈。
4. 复杂开发的主要缺口是：可恢复的项目级推进机制、开发沙箱与预览、分支和集成策略、绑定版本的测试证据、项目级交付校验，以及与这些能力匹配的预算。**增加 Agent 数量本身解决不了这些问题。**
5. 建议从一个受控的完整样例入手：先实现一条从需求到本地可运行交付的闭环；再增加按文件边界的并行，最后扩展长项目、预览与发布。继续使用 DSH 作为唯一云端 Agent Runtime，并优先评估 DSH 插件能否通过 Morde 的现有安全与恢复边界接入。

这里的“完全可用”应定义为：**约定范围内的用户场景可运行、可验证、可交接；无法完成的部分明确显示。** 不能保证所有未知环境、所有业务情形都没有缺陷，也不能把构建成功、子 Agent 说完成或页面能打开等同于验收通过。

## 二、Morde 现在怎么分发任务

### 2.1 三个层次

```text
用户消息
  │
  ▼
会话协调器：无工具的 DSH 轮次
  ├─ 直接回复 / 查询 / 修改 / 停止 / 澄清
  └─ 决策创建 Task（可关联已有活动 Task 的依赖）
          │
          ▼
      任务 Agent：DSH Agent Loop + Morde 模型网关 + 授权工具
          ├─ 自己调用工具
          └─ dsh_delegate(title, objective, tool_names, run_in_background)
                   ├─ 前台子会话：等待结果，父任务继续
                   └─ 后台子会话：返回 job_id，父任务可继续工作

Task 完成 → 结果记录 → 会话级 result_review → 协调器整理用户回复
```

会话协调器在自己的隔离 DSH 轮次中执行文本分类，工具列表为空；实际动作由服务端的路由和 Task 处理。任务 Agent 的工具由当前目标、Host 能力和用户授权决定，只有满足条件时才提供委派工具。参见 [会话协调器](/Users/zhongxuan_li/Desktop/morde/server/internal/worker/cloud_dsh_coordinator.go:109)、[路由决策](/Users/zhongxuan_li/Desktop/morde/server/internal/app/conversation_route_decision.go:92)、[Task 工具装配](/Users/zhongxuan_li/Desktop/morde/server/internal/worker/cloud_dsh_session_tree.go:668)。

`dsh_delegate` 要求提供标题、目标和工具名列表，可选 `run_in_background`。服务端检查工具必须属于父任务允许的集合；子级不能拿 `ask_user`、委派工具或后台作业管理工具，因此当前任务 Agent 的子级不能继续嵌套派发。子级的初始提示是标题与目标，运行在自己的 DSH Session 中，默认沿用任务模型，并非复制完整父会话。子级调用仍经过 Morde Broker、任务身份和授权围栏。参见 [委派工具定义与校验](/Users/zhongxuan_li/Desktop/morde/server/internal/worker/cloud_dsh_executor.go:280)、[子会话创建](/Users/zhongxuan_li/Desktop/morde/runtime/morde-cloud-runtime/src/engine.mjs:1064)、[子级工具限制](/Users/zhongxuan_li/Desktop/morde/server/internal/worker/cloud_dsh_jobs.go:34)。

**两种执行方式的区别：**

| 项目 | 前台委派 | 后台委派 |
| --- | --- | --- |
| 参数 | `run_in_background` 缺省或为 `false` | `run_in_background: true` |
| 父 Agent 何时继续 | 等子级结算后拿到摘要 | 子级启动后拿到 `job_id`，可继续其他工作 |
| 并发 | 当前 `delegateQueue` 包住整个前台执行，前台委派会排队 | 启动动作进入队列，启动后多个后台子级可同时运行 |
| 查结果 | 工具返回子级状态和摘要 | 使用 `dsh_job_list/get/output/cancel` 查询或取消 |
| 父任务结束 | 子级已结算 | 父任务进入最终完成前会等待后台作业；未知结果会阻止安全完成 |

代码见 [委派队列和后台作业](/Users/zhongxuan_li/Desktop/morde/runtime/morde-cloud-runtime/src/engine.mjs:1136) 与 [父任务结束](/Users/zhongxuan_li/Desktop/morde/runtime/morde-cloud-runtime/src/engine.mjs:1431)。后台子级结算时，服务端只对**前台**子级调用 `recordCloudDSHChildToolResult`；目前不能把“后台线程结束”说成“子结果已自动送给任务 Agent 并被其验收”。见 [结算处理](/Users/zhongxuan_li/Desktop/morde/server/internal/worker/cloud_dsh_session_tree.go:1355)。

子级和父级有持久化检查点，创建使用父子身份、spawn key 和请求摘要防止重放错配。恢复时先核对历史和工具回执，副作用结果未知则暂停处理；取消会请求停止并等待确认。子级成功意味着 DSH 轮次和历史满足当前结算规则，**不意味着独立的功能测试通过**。见 [子会话存储](/Users/zhongxuan_li/Desktop/morde/server/internal/store/postgres/agent_sessions.go:22) 和 [子级成功校验](/Users/zhongxuan_li/Desktop/morde/server/internal/worker/cloud_dsh_session_tree.go:1363)。

### 2.2 任务依赖和会话级回传已有哪些

Morde 已有 `task_dependencies`：当前会话路由可将用户明确提出的前后任务关系记录下来，最多选择 4 个活动任务依赖；前置任务对应修订完成后，后续任务才可认领，并收到该确切结果。当前这是**会话中独立 Task 的依赖**，不是已经完成的“把一个软件项目自动拆成任意开发 DAG 并逐项调度”的证据。见 [依赖选择](/Users/zhongxuan_li/Desktop/morde/server/internal/app/conversation_route_decision.go:29)、[依赖结果校验](/Users/zhongxuan_li/Desktop/morde/server/internal/store/postgres/task_dependencies.go:15)、[认领条件](/Users/zhongxuan_li/Desktop/morde/server/internal/store/postgres/task_execution.go:663)。

独立 Task 结束后，Morde 有持久化结果审阅与会话回复路径，带来源、修订和去重，旧修订不能冒充当前结果。这是**会话级 Task 回传**，与一个 Task 内的后台子 Agent 自动唤醒其父 Agent 是两件事。已有本地验收记录描述了同会话 A/B、修订、独立停止、结果回复和重启恢复；其中 iOS 联验使用本地 synthetic model proxy，不能当作真实模型完成项目的验收。见 [结果审阅实现](/Users/zhongxuan_li/Desktop/morde/server/internal/store/postgres/conversation_result_review.go:130)、[A21 验证记录](/Users/zhongxuan_li/Desktop/morde/docs/实施/Morde个人Muse三会话并行实施/A21-结果回传依赖与恢复实施任务todo清单文档.md:19)。

### 2.3 当前实现对复杂开发的实际约束

| 约束 | 当前代码和影响 |
| --- | --- |
| 单任务预算 | `Budget` 的上限为 1,800 秒活动时间、100 次工具调用、50,000 模型 token；复杂项目通常需要跨多个可恢复工作单元或调整设计，不能假定一个 Task 无限运行。见 [Budget](/Users/zhongxuan_li/Desktop/morde/server/internal/domain/task/types.go:83)。 |
| 子会话数量 | 数据库按一个 Task 的所有非根子会话计数，上限 16；这是**累计会话记录限制**，不是 16 个可用并发席位。见 [计数](/Users/zhongxuan_li/Desktop/morde/server/internal/store/postgres/agent_sessions.go:20)。 |
| 子级摘要长度 | Runtime 的子级摘要上限为 1 MiB，但服务端结算只接受 2,048 字节；静态对照显示超过服务端上限的摘要可能在结算时被拒绝。应统一合同并用定向测试确认，详细证据放受控产物中，避免简单截断造成事实丢失。见 [Runtime 摘要](/Users/zhongxuan_li/Desktop/morde/runtime/morde-cloud-runtime/src/engine.mjs:1116) 和 [服务端结算](/Users/zhongxuan_li/Desktop/morde/server/internal/worker/cloud_dsh_session_tree.go:1360)。 |
| Shell 审批 | `shell_exec` 落在敏感级别，每次调用要求与任务、参数和围栏匹配的审批；直接做多轮无人值守开发会反复停下。见 [风险分级](/Users/zhongxuan_li/Desktop/morde/server/internal/app/runtime_tool_executor.go:321)。 |
| Shell 运行边界 | 命令最多 5 分钟；Linux 实现每个 handler 最多 2 个并发 Shell、每次约 0.5 CPU 和 1 GiB 内存；使用独立网络命名空间，动作结束清空进程组。现有路径不能直接依赖联网安装依赖，也不能简单地让一个 Shell 调用启动长期服务供另一个浏览器会话访问。是否有其他适用的预览通道需专项验证。见 [Shell 限制](/Users/zhongxuan_li/Desktop/morde/runtime/morde-runtime/runtimeactions/shell.go:17)、[Linux 资源限制](/Users/zhongxuan_li/Desktop/morde/runtime/morde-runtime/runtimeactions/shell_linux.go:29)、[网络与清理](/Users/zhongxuan_li/Desktop/morde/runtime/morde-runtime/runtimeactions/shell_linux.go:318)。 |
| 并行文件修改 | 当前工作区私有视图按 Task 绑定；同一 Task 的子会话不等于每个子级已有独立分支或独立文件视图。未验证 Git worktree 与现有视图、发布和恢复合同兼容，不能直接把它当作已支持功能。见 [视图绑定](/Users/zhongxuan_li/Desktop/morde/server/internal/runtimeclient/client.go:363)。 |
| 项目交付证明 | Host 路径的候选文件证据来自成功 `file_write` 的调用/回执，并校验当前文件；单次收集上限 16 个文件、单文件 1 MiB、合计 8 MiB。仅通过 Shell 生成项目文件，或直接写入超过此数量，可能无法通过现有文件交付校验；项目清单/提交的独立验证需要补齐。见 [文件证据](/Users/zhongxuan_li/Desktop/morde/server/internal/app/agent_tools.go:142)、[完成校验](/Users/zhongxuan_li/Desktop/morde/server/internal/app/cloud_dsh_tool_broker.go:368)。 |
| 项目开发技能 | 当前云端固定技能目录有旅行、会议等技能，未见项目开发技能；已有 [技能读取机制](/Users/zhongxuan_li/Desktop/morde/server/internal/app/cloud_dsh_skills.go:39) 可供评估复用。技能是工作指引，不自动提供 Shell、预览、权限或验收机制。 |

这些边界是代码层面的观察；本次没有在生产环境跑完整项目，实际可用工具还取决于部署、Host 状态、权限和具体模型。

## 三、Muse 材料提供了什么启发

仓库中的 [Muse 子 Agent 材料](/Users/zhongxuan_li/Desktop/morde/docs/muse_docs/06-工具执行-子Agent-浏览器.md:19) 描述：主 Agent 把相互独立的长任务交给子 Agent，收到异步回传后继续工作；它强调任务书、异常恢复以及不要把排队当完成。该材料描述的上下文继承、两层委派和自动回传规则，**不能照搬为 Morde 当前已有行为**。

[Muse app-creation 技能材料](/Users/zhongxuan_li/Desktop/morde/docs/muse_docs/muse-all-materials/skills/app-creation/SKILL.md:3) 更值得借鉴的是产品闭环：

1. 先确认使用者、核心目标和运行形式，尽量复用已有项目，先做一条端到端可用的最小路径。
2. 区分静态页面、需要保存数据的应用和需要多人访问的托管应用；各自交付条件不同。Muse 自己的产品限制不是通用技术定律，Morde 应按自己的实际环境判断。
3. 用真实运行的页面测试主流程，以及空、加载、错误、不同屏幕尺寸和基本可访问性；构建成功不证明功能可用。
4. 交付时说明是本地运行、私有预览还是已发布版本，以及用户还需做什么。

仓库的 [Muse 自动化开发工作包](/Users/zhongxuan_li/Desktop/morde/docs/muse_docs/muse-dev-agent-package.md:1) 把构建日志总结为需求、判型、数据、后端、前端、探针、真实调用、一致性审计和交付；其中接口设计、主 Agent 模板和部分验收方法明确标为作者建议，不是 Muse 内部原版实现。材料还指出私有构建器、调度算法和资源限制等没有公开。见 [证据等级](/Users/zhongxuan_li/Desktop/morde/docs/muse_docs/muse-dev-agent-package.md:3)、[未知边界](/Users/zhongxuan_li/Desktop/morde/docs/muse_docs/muse-dev-agent-package.md:512)。

## 四、DSH 上游能复用什么

当前 Morde Runtime 的 `package.json` 和 lock 固定核心 DSH 包为 `0.2.2-rc.1`；Morde 自己持久化的检查点协议兼容标识是 `0.2.0-rc.2`，两者不能混为一谈。当前依赖清单没有 `dsh-subagent` 或 `dsh-jobs` 插件；Morde 已使用 DSH Agent、Session 等组件，通过自己的 IPC 和服务端逻辑接入子会话。见 [依赖](/Users/zhongxuan_li/Desktop/morde/runtime/morde-cloud-runtime/package.json:13) 和 [协议标识](/Users/zhongxuan_li/Desktop/morde/server/internal/worker/cloud_dsh_executor.go:29)。

上游同版本的 [subagent 工具](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/packages/subagent/tool-subagent/README.md) 提供受管理的异步委派、结果通知、部分子级消息与恢复能力；上游 spawn 从空会话开始，fork 使用父级**已完成**轮次的一次性快照，不包含正在执行的轮次，也不自动复制父级权限。二者应分别匹配场景，不能笼统地说“子 Agent 继承所有上下文”。参见 [spawn](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/packages/subagent/subagent-spawn-in-process/README.md) 和 [fork](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/packages/subagent/subagent-fork-in-process/README.md)。

仓库已有一次针对 `0.2.2-rc.1` 的评估：版本和 MIT 许可未构成阻碍，但上游当时的 provider 合同与 Morde 的每次工具授权、Task 身份、预算、进程重启重新附着和持久生命周期不完全匹配。上游 [jobs-local](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.1/packages/jobs/jobs-local/README.md) 的存活与 owner/service 生命周期绑定，进程退出后活跃作业不自动恢复。见 [A20 评估](/Users/zhongxuan_li/Desktop/morde/docs/实施/Morde个人Muse三会话并行实施/A20-主协调会话与消息分流实施任务todo清单文档.md:43)。

**建议**：以这次评估为起点，优先用现有版本插件做最小兼容验证；若适配能够保留工具子集授权、事件持久化、预算、取消和恢复，就通过受控 provider 复用；若不能，记录具体失败合同并先保留当前实现。不要引入第二套 Agent Runtime，也不要因为插件提供了通知就绕过 Morde 操作账本。

这些是来源方的经验和实验，不是 Morde 的实测性能承诺。

## 六、建议的自动开发流程

### 6.1 总体思路

保留 Morde 当前的会话协调器、Task 账本、DSH Runtime、Workspace 和 Broker。在此基础上增加一个**开发工作流**：由任务 Agent 使用开发技能形成项目计划；具备条件后，由同一种 DSH Runtime 执行有边界的子任务；由可恢复的编排和证据门禁推进阶段。

```text
用户目标与授权
    ↓
识别现有项目 / 运行目标 / 约束 / 成功场景
    ↓
准备环境与第一条可运行的端到端路径
    ↓
任务计划：依赖、边界、验收、预算
    ↓
并行处理独立工作 → 集成 → 真实测试 → 修复
    ↓
通过项目级门禁 → 交付可运行源码、证据和操作说明
```

核心职责归属建议：会话协调器继续处理对话；**项目开发负责人**作为有工具的 Task Agent 工作，负责需求澄清、拆分、集成和验收；子 Agent 只接有边界的任务。角色是任务职责和提示词，不必为每个角色新建运行时或常驻服务。

### 6.2 分阶段推进

**第一步：确定交付合同。** 读取现有项目、规范、构建和测试；确认目标用户、核心流程、运行位置、本地/预览/正式环境、数据与外部依赖。只在缺少关键决定且无法安全推断时提问。定义“用户可以从哪里打开、做什么、数据如何保存、如何重启、怎样判定成功”。

**第二步：建立项目基线。** 记录当前代码版本或工作区 revision、已知测试结果、运行方式及未完成项。优先复用现有框架、脚手架和项目约束。启动或环境准备脚本必须在实际环境中运行过；缺少依赖、凭据、网络、浏览器或执行权限时如实阻塞对应验收项。

**第三步：先跑通纵向切片。** 对有界产品，先做一条从用户操作到持久化再到页面反馈的核心路径。它可以暴露前后端契约、环境和权限问题，避免前后端分头完成后才发现无法集成。

**第四步：滚动拆解。** 不必一开始生成几十条任务。先列出必须达成的能力和依赖，再只细化下一批可做的工作。每个子任务应有：目标、输入和基线、可修改范围、接口约束、验收命令或用户操作、禁止事项、输出格式和预算；缺信息时由负责人补充到任务书。子 Agent 没有父对话全量上下文，必要事实和授权来源必须显式提供。

**第五步：实现、集成、验收。** 契约未稳定之前避免并行修改共享接口；只把独立的文件或模块分给不同执行者，尽早集成。子级返回后，负责人核对变更、测试输出和需求覆盖，失败则修复重测。独立验收者在集成后的真实版本上操作主路径。

**第六步：交付。** 交付本地项目位置或经过用户授权的预览、源代码和版本/修订、启动步骤、必要配置项、测试结果、已知限制与待用户提供的内容。生产发布、数据迁移、付费资源和向外发送等动作受现有授权边界约束；本次调研只在本地生成报告，不发送文件。

### 6.3 一个具体拆分示例

假设用户要求“做一个本地库存管理系统，能录入商品、入库、出库和查看库存”。交付目标是**本地可启动、数据可保存、重启后仍可查看**。没有要求时不默认加多租户、支付、线上发布或复杂消息系统。

| 顺序 | 工作 | 依赖/可并行条件 | 可观察的完成证据 |
| --- | --- | --- | --- |
| 0 | 项目负责人确认现有代码、数据规则、启动环境，写清用户操作与验收条件 | 无 | 需求清单、启动基线、具体示例数据 |
| 1 | 建立项目骨架和一条“新增商品 → 保存 → 展示”纵向路径 | 先于大规模并行 | 可启动；新增后刷新仍存在 |
| 2A | 后端：入库/出库、库存计算和数据校验 | 数据/API 契约稳定；有单独修改范围 | 接口与数据库测试；库存不足等错误路径 |
| 2B | 前端：商品列表、表单、操作状态 | 同一契约稳定；独立文件范围 | 界面可操作；空、错误和加载状态可见 |
| 2C | 验收准备：从需求写独立的核心流程与测试数据 | 可与 2A/2B 并行，先不依赖未集成页面 | 测试场景及预期结果，不把 mock 通过当实测 |
| 3 | 集成人员合并并解决接口、依赖和冲突 | 2A、2B 完成 | 集成版本标识、构建和相关测试结果 |
| 4 | 独立验证：新增商品 → 入库 → 出库 → 刷新/重启核对余额 | 依赖集成与可访问的运行环境 | 命令/浏览器证据、实际与预期结果、修复后复测 |
| 5 | 交付本地可运行项目 | 依赖门禁全部满足 | 源码位置、启动说明、测试记录和已知限制 |

该例中的角色是逻辑分工；任务规模小时由一个 Agent 串行完成可能更快。当前 Morde 的 Shell、后台回传和项目文件证据限制尚不足以保证此例可无人值守地跑通，表格是目标流程而非现有能力声明。

### 6.4 项目状态、依赖与恢复

建议先复用 Task、子会话、checkpoint、依赖、事件、工作区 revision 和操作回执作为权威事实。需求和计划可以在项目工作区存一份简明文档；不要让另一份自由编辑的 Markdown 状态与数据库执行状态形成两个彼此冲突的真相源。

对于每个待执行工作单元，最少要关联：目标和验收条件、依赖及其版本、输入工作区 revision、授权和预算、执行者/子会话、变更版本、检查结果和证据位置。状态至少能区分待执行、运行中、等待依赖、需要用户、待验证、通过、失败/未知；具体状态优先映射到现有 Task/Step，而非平行发明第二套权威状态机。

现有 Task 依赖只能覆盖一部分需求。跨多个预算单元持续推进时，应扩展或适配已有依赖与结果事件：依赖只消费被验证的指定 revision；输入发生变化时让后续证据失效并重验；中断后从 checkpoint 与操作账本对账，未知副作用先查实；子结果通知需要持久化和幂等消费，不能仅靠进程内 Promise。父 Agent 在所有必需结果到齐并验证后才能标记项目完成。

### 6.5 怎么并行才不会互相覆盖

建议先从 **1 个负责人 + 2 个执行者 + 按需 1 个验收者**作为实验配置，不把它当作已经验证的最佳并发数；项目简单则直接串行。可以并行：需求与代码只读调研、约定后的前后端模块、测试场景准备和文档核对。应串行或集中负责：公共 API/表结构、依赖锁文件、数据库迁移、最终合并、发布和同一文件的冲突修改。

初期若只能共享同一 Task 工作区，优先进行只读并行，写入按明确路径和单一集成负责人组织；这是一种操作约定，**不是隔离保证**。下一阶段评估每个执行单元基于同一版本建立隔离视图或 Git 分支/worktree，通过补丁/提交交给集成者；只有在验证现有 Workspace 快照、`.git` 处理、发布、恢复、用户权限和冲突保护兼容之后才能启用。冲突时重新读取最新基线、合并、再运行相关测试，不覆盖他人的未提交工作。

## 七、质量和速度怎么同时保证

### 7.1 验收门禁：从“有代码”走到“用户能用”

每项门禁都记录**执行命令或操作、环境、目标版本、时间、结果和证据**。证据与代码版本绑定；修改后受影响结果要失效并复测。

| 层级 | 最少检查 | 不通过时 |
| --- | --- | --- |
| 需求 | 核心场景、边界条件和未决定事项有明确记录 | 保持未完成，补充信息或合理假设 |
| 源码与构建 | 依赖可解析、构建成功、项目约定的静态检查通过 | 修复并重测 |
| 功能 | 核心业务规则、错误输入和权限边界有适当测试 | 不进入最终交付 |
| 系统集成 | 使用真实运行组件验证接口、存储与前后端联动；测试数据与生产数据分开 | 明确未接通项 |
| 用户体验 | 浏览器或适用客户端走核心操作，检查空/错误状态、相关屏幕尺寸及基本无障碍 | 截图或操作记录保留；按问题修复 |
| 交接 | 源码可取得，干净环境按说明启动；环境变量模板不含密钥；关键运行状态和限制可见 | 不声称完整交付 |

可用模拟服务验证离线链路，但要明确其范围；若需要第三方真实凭据或外部系统，只有授权且实际调用成功才称为已接通。对无前端的项目，用适合该产品的 CLI、API 或集成测试取代浏览器检查。

### 7.2 哪些措施能加速

- **先解决关键路径**：环境、核心契约、首条完整用户流程先跑通；并行工作围绕其余独立模块展开。
- **任务书简短但完整**：传目标、边界、基线、验收和必要事实；让子级按需读取仓库，不复制整段历史。
- **分层验证**：修改时先运行受影响的快速检查；合并后跑集成和用户流程；最后再运行必要的全量检查。避免每次小改动都跑整套重型测试，也不省掉最后的集成验收。
- **预算与资源可见**：分别记录模型用量、Shell 等待、构建、测试、冲突和重试；保留验收与修复预算。按瓶颈调并发，超额时排队或暂停，不能把安全门禁当成性能开关。
- **用反馈减少返工**：子级每次交付小而可检查的改动；负责人早集成。需求变更按受影响的依赖重算，而不是全部重来。
- **模型路由按证据决定**：当前子级默认与父级同模型；将来只有在网关授权和记录完善后，才按实际任务难度评估不同模型，不能假定小模型一定更快、更便宜或足够可靠。

## 八、Morde 落地优先级

### P0：跑通一个可验证的小项目

1. **开发任务技能**：基于现有受控技能读取机制增加项目开发指引，定义最小任务书、增量推进、集成和交付标准；检查技能是否实际被任务 Agent 调用，不能只放一个文件。
2. **可控开发环境**：在现有任务沙箱/Host 能力上验证并补齐工作目录、可用工具链、构建、测试、生命周期和恢复；提供与浏览器可达的受控预览。缓存依赖或经明确授权的受控网络解决安装问题。不能把 DSH 账号 Runtime 当用户 Shell，也不能绕过现有隔离与账本。
3. **审批体验**：现有 Shell 对每个调用单独审批。评估在独立、无凭据、受资源与网络控制的开发环境内，如何支持用户已授权范围内的连续构建和测试；任何放宽都必须由强制隔离、任务/版本绑定、操作记录和撤销机制支撑，不能只靠字符串白名单或提示词。外发、生产部署和不可逆动作继续遵守用户明确授权。
4. **项目交付证据**：扩展现有 Broker/Workspace 验证链，能够独立核验一组项目文件或版本化清单，以及构建/测试结果；处理仅 Shell 生成文件、多于 16 文件、并发修改和内容变化。不要仅通过伪造一次 `file_write` 绕过验证。

**P0 通过条件**：在本地隔离环境，用一个具有数据保存和实际用户交互的小应用，从自然语言需求到源码、重启后数据、真实测试、可复现启动和完整交付，连续完成 3 次；每次保留日志、版本和限制说明。3 次只是早期回归样例，不能证明所有项目可靠。

### P1：让多 Agent 并行后的结果可集成

1. 选择现有后台作业机制或兼容的 DSH 上游 provider 做最小接入，补齐子结果持久通知、空闲父任务唤醒、结果去重和显式汇合；统一子级摘要长度合同并验证超限行为；将后台作业完成与负责人验收分开。
2. 在现有 Task 依赖和 revision 上支持项目工作单元的依赖推进；记录基线、目标、边界、测试和结果，不让旧版本通过门禁。
3. 验证并接入独立工作视图/分支或等效隔离，明确集成顺序和冲突处理；基于现有权限、审计、停止和恢复执行。
4. 覆盖多子级真正重叠执行、相同文件冲突、依赖失败/取消、重复结果、用户修订、进程中断、权限撤销及未知副作用。测试应证明工作没有重复执行、没有互相覆盖、不能提前宣布完成。

### P2：支持长项目和可运营的交付

围绕多个受预算约束的 Task/阶段扩展持久项目推进、汇合与恢复；保留租约、修订、审批、取消、资源配额和用户隔离。按需要增加预览环境生命周期、失败诊断、项目级可观测性和授权后的发布连接。是否提高每任务预算、放宽固定上限或通过多工作单元推进，应依据真实资源与账本语义设计，不简单移除上限。

## 九、如何评估是否真的又快又好

选择同一组有明确验收条件的基准项目，包含新建小应用、现有项目修改、前后端集成和至少一个故障恢复场景。对比单 Agent 基线与有界并行方案，尽量保持模型、机器、输入、预算和交付条件一致；记录每次实际差异。

| 指标 | 计算或观察方式 |
| --- | --- |
| 核心场景一次验收通过率 | 全部必需用户路径经过真实运行验证的次数 / 尝试次数 |
| 到首个可运行版本时间 | 从任务受理到首条端到端场景成功 |
| 到可交付时间 | 从受理到全部约定门禁通过，包括等待和修复 |
| 缺陷与返工 | 验收发现的有效缺陷、修复轮数及重开项；独立评估和用户体验问题分开记录 |
| 并行收益 | 同一项目下总时长、集成耗时、文件冲突数，与单 Agent 基线比较 |
| 成本和资源 | 模型调用/Token、工具调用、沙箱 CPU/内存、审批等待；包含失败和重试 |
| 可靠性 | 中断恢复成功率、重复副作用次数、旧版本误发布次数、取消隔离情况 |

不要用代码行数、任务完成数或 Agent 自评分数作为主要成功指标。只有在同一验收门槛下整体交付更快，才能说并行提高了效率。
