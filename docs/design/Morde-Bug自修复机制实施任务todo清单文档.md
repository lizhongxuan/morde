# Morde Bug 自修复机制实施 TODO 清单

> 需求依据：[Morde Bug 自修复机制需求](Morde-Bug自修复机制需求文档.md)。本文是新清单；所有任务尚未开始，完成实现和对应验收后再勾选。

## 范围与顺序

在现有对话和任务中增加“定位 → 修复 → 验证 → 失败后继续排查”的自修复规则，复用 DSH、项目上下文、授权工具、任务记录和结果投递。不改 PC/iOS 界面，不新建一套任务或 Agent Runtime，不要求更换模型或部署方式。只在授权范围内本地修改，不上传、发送文件或推送代码。

**顺序：** T01 识别请求 → T02 接入修复技能 → T03 复用工具执行修复 → T04 验证与纠错 → T05 结果、交互和恢复 → T06 PC/iOS 真实验收。

## 接口与复用边界

- 对外沿用 `POST /api/conversations/{id}/messages`、`GET /api/tasks/{id}` 和现有 Task 事件；不新增请求字段、任务状态或客户端界面。消息受理的 `202` 只代表消息已保存，`Idempotency-Key` 仍等于 `client_message_id`。
- 内部沿用 `nanomuse_skill_read`：在现有固定技能目录中新增 `morde-bug-repair` 标识；调用仍使用 `skill_id`，返回沿用现有技能内容、版本与来源。技能只提供行为规则，不增加文件、终端或审批权限。
- 当前 Morde 已有固定技能目录及授权、操作记录；本地上游 DSH 的 `dsh-tool-skill` 是通用技能发现和加载插件，不是 Morde 自修复技能，且未列为当前 Runtime 直接依赖。本次优先使用已有 `nanomuse_skill_read`，避免重复建设加载链；若实施时确需新增上游插件，先按项目约定核查版本、许可证及授权、检查点、取消和恢复。

## 实施任务

- [ ] **T01（未开始）复用现有对话路由识别修复请求**
  - 修改：优先复用 `server/internal/app/conversation_route_decision.go` 和现有路由 Worker；仅在验证发现缺口时调整。明确请求修复 Morde Bug 时创建或关联正确 Task；普通讨论、追问、补充和停止仍按现有语义处理。
  - 验收：使用“帮我修复 Morde 的 X Bug”和不同表述验证会进入修复任务；只问“X Bug 是什么”不改代码。同一消息重试不重复创建任务；缺少真正必要的上下文时才在原会话追问。

- [ ] **T02（未开始，依赖 T01）在现有 DSH 技能目录接入自修复机制**
  - 修改：拟新增 `server/internal/app/cloud_dsh_skills/morde-bug-repair.md`，并在 `server/internal/app/cloud_dsh_skills.go` 注册及描述触发条件。参考仓库 `.agents/skills/correct/SKILL.md` 的定位、最小修复和验证原则，改写为当前 Task 实际可用的工具规则；该本地技能不能假定已被 Morde Agent 自动加载。必要时在现有 DSH 任务提示中引导明确的修复请求加载该技能；仍将普通文件和工具输出视为不可信资料，不由技能授予权限。
  - 验收：真实任务能通过 `nanomuse_skill_read` 加载该技能，并在现有 DSH 指令边界内实际遵循其修复规则；目录、工具参数和加载记录对应正确版本。普通对话不触发修复；未授权或技能不可用时不绕过现有工具和权限。

- [ ] **T03（未开始，依赖 T02）复用授权工具定位并直接修复**
  - 修改：通过 `server/internal/app/cloud_dsh_tool_broker.go` 已有项目、文件和终端工具检查目标、已有改动与问题；在当前授权的 Morde 工作区直接修改相关内容，沿用已有冲突检查、权限、审批和操作记录。实时目录的 `expected_revision` 是任务检查点，不能单独视为当前文件未变；使用现有文件基线及发布冲突校验，无法证明安全时停止相关写入。用户明确要求修复且授权足够时直接开展，不增加选目录、开始或应用确认；现有规则要求的敏感操作审批继续生效。
  - 验收：在本机授权的 Morde 测试副本中完成一次实际代码修改，保留已有未提交及无关改动；模拟目标文件在处理期间被并发修改，不覆盖已有内容。权限不足、目标不可用或存在无法安全处理的冲突时说明原因，不切换其他项目/电脑，不外发文件。只修改云端副本时不得声称已自动更新 PC 文件。

- [ ] **T04（未开始，依赖 T03）验证修复并根据失败结果继续调整**
  - 修改：在修复技能中规定使用当前 Task 可用的测试与验证工具，按现有任务预算继续排查失败，必要时新增或复用回归检查；将本次修改、环境和实际测试结果关联到现有 Task 步骤/证据，不复用旧任务的测试结论。
  - 验收：构造一次验证失败后修正并通过的案例，能追溯两次真实结果；测试不可用或无法复现时说明未验证，不凭模型自述报成功。实际测试通过与独立复核状态分别报告；现有 `validation.state` 未获可信复核时保持 `pending`，不把它写成已通过，也不以缺少第二个模型阻止修复开始。

- [ ] **T05（未开始，依赖 T03、T04）复用结果投递、记录与任务恢复**
  - 修改：沿用 `server/internal/app/cloud_dsh_tool_broker.go`、`server/internal/store/postgres/conversation_result_review.go` 和现有检查点/消息处理；在原会话说明原因、修改、测试、未完成项及实际生效环境。有用记录保留在已有 Task 或授权的项目记录中，不新增独立记忆系统。
  - 验收：同一会话能看到真实进度和结果；追问、补充或停止关联正确任务，断线恢复不重复执行已确认操作，结果未知时先对账。其他任务不被停止；同类任务仅在获得授权时参考已有记录，并使用本次新证据。

- [ ] **T06（未开始，依赖 T01–T05）完成真实 PC/iOS 闭环验收**
  - 修改：准备本机 Morde 测试副本、可复现的真实 Bug 和验收记录；使用现有 DSH、模型及已授权工具，不上传文件或部署外部环境。
  - 验收：从实际 `morde-pc` 现有对话发出修复请求，观察真实任务加载修复技能、修改目标源码、执行验证并回到原会话；没有新增页面、选目录或开始/应用确认。同账号从原生 iOS 查看同一任务，再对重建的隔离测试副本发起修复请求，观察任务实际执行并反馈结果；覆盖失败、撤权、停止和重连。任一客户端、模型或环境不可用时标记阻塞/待验证，不用替身或独立浏览器冒充端到端通过。

## 完成标准

每项只在对应实现和验收通过后勾选，并记录实际环境与未覆盖范围。涉及服务端代码时遵循 [server 开发规范](../../server/AGENTS.md)执行要求的检查；涉及 Runtime 或 DSH 插件时验证相关测试、任务隔离、取消和恢复。PC 验收必须操作真实 `morde-pc`，iOS 验收使用原生客户端并记录设备或模拟器。
