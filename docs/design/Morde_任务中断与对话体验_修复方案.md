# Morde 任务中断与对话体验修复方案

**适用代码：** `lizhongxuan/morde` 的 `release@936389c`。这是实施规格，不是已上线的修复。用「你看看今天有什么新闻」做回归案例，设计同样适用于其他个人 Agent 任务。不修改正在并行实施的模型生成预算方案。

## 1. 问题与证据

| 现象 | 代码能确认的事实 | 仍待核实 |
|---|---|---|
| PC 用户消息没有 👌🏻 | 服务端已有 `agent_acknowledged`，PC 的聊天气泡没有用这个字段渲染标记。 | 截图中的那条消息，后端是否真的确认过。 |
| 主对话像日志 | 终态交付的模型输入含步骤计数和通用下一步；无模型的兜底也会直接输出计数和「对账」。 | 截图这条是模型改写还是其他版本的兜底，不能只凭文案认定。 |
| 「等待你处理」却没有入口 | 恢复失败可写入 `waiting_user / dsh_recovery_unresolved`。PC 把 `waiting_user` 统一翻译为「等待你处理」；现有 PC 测试明确预期这一恢复场景无操作按钮。 | 具体是上游调用失败、返回校验拒绝、工具权限、还是恢复异常。截图只显示合并后的提示。 |

截图里的「1 步成功」也不是新闻已经查到的证据：开始处理本身就是一条标记为成功的进度步骤。要定位这一次事故，按 Task ID 打开任务事件和相关模型调用记录，找**第一条异常**，核对 `failure_category / failure_stage / failure_reason / tool_dispatched`（只使用实际存在的字段）、调用账本以及最后一次已确认 checkpoint；不要以面板中文提示去反推根因。没有生产记录，不把原因预填成超时、权限或预算。

## 2. 先修状态：标签必须回答「现在轮到谁？」

`waiting_user` 现在是后端的持久化状态，不是发给用户的一条操作指令。它可以表示真的在等用户，也可以表示系统不敢继续，所以**不能直接用于用户界面**。第一版保留原数据库状态和接口兼容性，由服务端提供结构化的对话展示信息（字段名建议为 `attention`）；PC 的任务详情、任务卡和对话使用同一套语义。

| 展示状态 | 进入条件 | 页面与行动 |
|---|---|---|
| **需要你操作** | 服务端确认当前用户有权限，且存在有效的审批或澄清请求 | 写清「允许执行什么」或「具体缺什么」。原对话提供允许/拒绝、填写/提交等现有控件。 |
| **正在恢复** | 同一任务确实有已持久化、尚未失效的恢复安排，或 Worker 已在执行该尝试 | 用户不用操作；如需发更新，只发一次，不承诺尚未安排的工作。 |
| **已暂停，可重试** | 没有自动恢复在跑，服务端对当前用户和当前任务版本确认可安全重试 | 在对话给「再试一次」；重试同一任务，不复制用户消息、不创建第二个任务。 |
| **已中断** | 无恢复安排，也无安全的用户动作 | 说明未交付、原因类别或原因暂未查明；只给「查看详情」，不暗示点击就能恢复。 |
| **结果待核对** | 外部副作用、模型账本或 checkpoint 状态无法确认 | 不自动重试，不提供普通重试按钮。有受支持的核对入口才显示；否则明确当前无法继续。 |

**实现约束：**

- 建议服务端提供 `kind`、经过归类的 `reason`、`action`（可为空）、状态事件序号；不得返回供应商原始错误。审批、澄清、重试的处理接口仍要重新鉴权并校验版本；界面上的按钮不是授权。
- 旧服务端未提供新字段时，前端按实际存在且有效的审批/澄清请求显示「需要你操作」；其余 `waiting_user` 保守显示「已暂停」或「结果待核对」，不能自行推断可重试。
- 用同一纯函数生成侧栏、任务卡和气泡的状态文案；旧事件晚到或刷新不得把已完成覆盖成暂停。重试按钮过期或被另一端使用时，刷新任务状态，不返回虚假的「已恢复」。

## 3. 修复续跑：只自动恢复能证明安全的失败

首版只覆盖**已由服务端确认是纯只读的公开信息查询任务**，例如仅具备已知的公开网页搜索与读取能力的新闻任务。不要按标题含「新闻」或模型自述只读判定。若暂时无法从能力和账本可靠证明只读，首版不自动续跑该任务；仍要修复状态和通知。

~~~mermaid
flowchart TD
    A["模型或运行返回异常"] --> B["读取已提交的 checkpoint、模型与工具账本"]
    B --> C{"同一调用已有已结算结果？"}
    C -- "有" --> D["回放记录，继续同一任务"]
    C -- "没有" --> E{"失败已确认且可重试<br/>任务只读、权限和账本有效？"}
    E -- "是，且尚未用过恢复额度" --> F["持久化一次恢复申请"]
    F --> G["Worker 认领，从已验证的 checkpoint 续跑"]
    G -- "完成并提交结果" --> H["主动回到原对话交付"]
    G -- "再次失败" --> I["结束自动恢复，通知原对话"]
    E -- "结果或用量不明" --> J["待核对，不重新派发"]
    E -- "其他" --> I
    I --> K["仅在确认安全且有权限时显示重试入口"]
    J --> L["说明未交付；只显示真实可用的核对入口"]
~~~

### 后端实施

1. **在 Worker 消费已分类的原因。** 入口从 `cloud_dsh_executor.go` 的模型结果不可用分支和 `CloudDSHToolBroker.pauseRecovery` 查起。在进入状态映射之前保留结构化诊断；优先复用现有分类、模型账本和 checkpoint 恢复能力。对模型或工具已结算的结果走回放，不为了重试重新做一遍。
2. **把自动恢复变成一次可持久化的调度。** 不做进程内 sleep 后递归重跑。若现有恢复存储不能表达，新增恢复记录，并在任务状态/事件事务中原子登记。建议按 Task ID、修订、失败事件/模型调用身份和已验证 checkpoint 锚点绑定；用唯一约束和条件更新防重复领取，同时用按 Task 修订累计的额度防止每次新失败都重新获得一次机会。重新提交正式的任务修订按明确规则管理新额度；Worker 重启不是新额度。
3. **恢复前再次校验。** 核对任务修订、授权版本、取消/暂停、Worker 租约、checkpoint 序号和摘要，以及未对账的工具和模型调用。已持久化的搜索结果直接用；只有上一尝试明确未派发或结算为可重试失败，才可用新的受控尝试身份调用模型，不能覆盖旧调用记录，也不能复用已结算失败身份发起第二次请求。重试仍走现有模型/用量限制，不隐式换模型或扩大额度。
4. **保守失败策略。** 明确可重试的临时故障且用量已知时进入有限重试（首版建议自动 1 次；如已有统一重试记录，计入总上限，不额外叠加一轮）。认证/授权、模型返回违反工具约束、模型输入过长、结果/用量不明、权限变化、checkpoint 对不齐，均不走这条通用自动重试。部署、发送、文件写入等外部副作用不纳入此首版；既有操作若结果不明，先走既有对账机制。
5. **手动动作必须真的能跑。** 先确认现有 Task 恢复接口能否复用，不能把「重试某个工具步骤」当成模型恢复接口。复用不了再给 Task 级恢复端点，服务端按当前版本和失败原因计算资格。双击、跨端竞争和 Worker 抢占最多产生一个恢复申请。若能力未实现，不显示重试按钮；「查看详情」可以保留。

## 4. 主对话怎么回

| 场景 | 界面预期 | 示例 |
|---|---|---|
| 能很快完成的小查询 | 不打 👌🏻，不发制式进度 | 直接给几条新闻，每条给报道来源和日期。 |
| 已确认接下耗时任务 | 原请求气泡 👌🏻；如有帮助，再发一条短计划 | 「我去核对今天的主要新闻和报道时间，整理成几条发给你。」 |
| 任务已排定安全恢复 | 对话只更新一次，或仅显示内联状态 | 「刚才没能拿到已核实的结果，我会再查一次。」 |
| 重试失败，且有可用入口 | 一句话讲结果和下一步 | 「没能整理出已核实的新闻。可以点『再试一次』继续查。」 |
| 中断且没有用户动作 | 直接说明中断，不把排查交给用户 | 「这次没有拿到已核实的新闻，任务已中断。原因可以在任务详情查看。」如详情也没有原因，应明确「原因暂未查明」。 |
| 真缺权限或必要信息 | 问一个具体问题，控件在同处 | 「我没有这个工作区的读取权限。请先授权读取，授权后我再继续。」 |

- **主对话显示事实和下一步；任务详情保留工程信息。** 从终态交付的面向用户输入和兜底文案中移走总步骤数、内部恢复词、原始代码及工具详情。不要只改提示词；失败、等待和取消优先使用服务端结构化事实渲染短状态。实际成功的结果仍走现有证据与交付流程；部分结果按已核实/未核实分开，不把「开始处理」写成任务产出。
- **通知不依赖模型恢复。** 终态交付文案模型自己的调用结果也可能是 unknown。保留原模型账本，不冒充它成功，不另发同一模型调用；同时从已经提交的任务状态事件向原对话展示确定性状态卡（可先复用客户端任务事件订阅）。若以后做持久化通知，用任务修订加来源事件作为去重键；同一事件不能同时出现一条通用消息和一张重复状态卡。失败默认优先送达原对话，不需要用户一直开着任务详情。
- **PC 气泡用服务端确认。** 保持现有 `agent_acknowledged` 的持久化和权限边界，补上 PC 渲染、无障碍标签「已接下后台任务」及事件后刷新逻辑。识别最初触发该后台任务的那条用户请求，不按 UI 的最后一条消息猜；绑定到正确的任务和消息，合并请求、后续修改和刷新时不能重复打标。先核验后端现有合并/修订路径的确认次数；若已能为同一逻辑任务写多个确认，先定义并持久化唯一的展示锚点，不用当前分页里碰巧最早的一条来去重。
- **排队不等于正在执行。** 先沿用服务端「确认开始后才打标」的语义；等待排队必要时显示独立「已排队」。短请求走现有路径，不为加标记强制开后台任务，也不把所有查新闻都改成未经核实的单次搜索。

## 5. 开发拆分和验收

| 顺序 | 开发项 | 合并前必须满足 |
|---|---|---|
| R1 | 状态契约、错误归类、PC 的保守映射 | 用截图形态的 fixture：没有审批或澄清时，聊天和面板都不出现「等待你处理」；真实审批和澄清各有可操作入口。 |
| R2 | 有界恢复和真实重试 | 用模拟模型 + PostgreSQL 在同一 Task/修订下跑「搜索已完成 → 下一次模型临时失败 → Worker 重启 → 恢复 → 结果交付」，断言搜索不重跑、只产生一次真正的自动恢复。 |
| R3 | 短回复和可靠回告 | 恢复耗尽、终态文案模型不可用、终态文案模型调用 unknown 三例，都能在原对话展示准确状态；已暂停不说「还在查」，详情仍能查诊断。 |
| R4 | PC 👌🏻、无障碍和多端一致 | 慢任务开始后只标正确原消息一次；快答、排队、另一个人的消息不误标；覆盖合并、刷新、分页以及重复事件。 |
| R5 | 实机回归与灰度 | 在实际 PC 打包版本重跑新闻查询成功、失败后恢复、失败后可操作三条路径。自动恢复可单独关闭，状态修复和通知仍保留。 |

**必须加反例。** 账本结果/用量未知、工具没有权限、外部写操作结果不明、checkpoint 摘要不符、用户取消或授权撤销、两个 Worker 竞争、两端同时点重试。不满足安全、权限或账本条件的状态拒绝续跑；竞争测试断言同一任务最多只有一个有效恢复申请和一次派发。失败原因与用户权限不得泄漏到其他账号或项目。

**上线看什么。** 先记基线，再对比灰度组：非用户阻塞误标「等待你处理」的次数、已接下任务在原对话有结果或明确中断的比例、恢复成功率、重复外部工具派发、额外模型调用/用量。重复派发有副作用操作或跨权展示属于立即停用条件。此次仅核对代码与既有用例，不宣称已经复现生产中断或完成回归。
