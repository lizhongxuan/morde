# Morde 可验收、可恢复的工程委托精简设计

> 本文仅讨论工程提交核查场景；跨场景的想法与开发说明见[可融合的任务能力与开发思路](Morde-可融合的任务能力与开发思路.md)。

> 状态：设计建议，尚未实现或验收。来源：本地 `Downloads/Morde_MVP_PRD.md`（2026-11-20，v1.3）。

## 1. 目标与范围

把 PRD 中最有价值的部分落成一个可验证的场景：用户在 Morde 会话中要求检查一次代码提交；Agent 只读核查改动和已有测试证据，任务中断后可恢复，并将带来源的结论交回原会话。下次同类任务可以复用用户确认过的核查规则。

这是 [Morde 第一里程碑](../../AGENTS.md)中的一个试点场景，不替代 PC/iOS 对话、长会话、指定云端电脑、常用工具或 PC 文件夹同步。PC 通过实际 `morde-pc` 发起和查看；iOS 原生客户端可接续同一会话、发送追问并查看同一任务和结果。已有必要信息和授权时，也可从 iOS 对话发起；首版不要求 iOS 完成仓库管理。

首版只核查**一个已授权仓库的一次固定提交**和已有证据，不修改代码、不运行未知代码、不提交或发布，也不外发文件。真实发布决定由用户负责。普通问答无需选择或启动云端电脑。

本方案补充已有的[工程任务闭环方案](../copy_lauren_engineering/Morde_工程任务闭环实施方案.md)中的只读取证场景；后者涉及代码修改和待审 PR，不能因本试点通过就认为其写入流程已验收。

## 2. 从 PRD 采纳的设计

| 有价值的做法 | 在 Morde 的落点 |
|---|---|
| 结果可验收 | 每项结论关联提交版本、文件位置或测试运行记录；没有证据就标“未验证”，推断单独标明。 |
| 离开后能继续 | 服务端保存任务、步骤和证据；断线或关闭客户端不取消任务，重连后继续查看。 |
| 主 Agent 协作 | 由 DSH 主 Agent 收回并检查子 Agent 的真实结果；委派成功不等于子任务完成。 |
| 下次少交代 | 只复用用户确认的关注点、证据标准和输出格式；新任务重新确认版本和权限。 |
| 评估真实价值 | 对照用户现有做法衡量人工时间、证据质量、等待和成本，不以 Agent 数量或演示效果判断价值。 |

## 3. 任务流程

1. **接单并固定范围。** 在原会话识别仓库、目标提交、比较基线、核查范围和验收口径；缺少必要信息时只追问缺项。服务端校验当前用户的仓库和证据源只读权限，将分支等可变引用解析为不可变 commit ID。普通提交可使用其父提交作基线；合并提交或用户指定对比范围时，以明确的基线为准，不猜测。
2. **并行收集证据。** 本试点使用两个独立 DSH 子会话：A 核查目标提交与基线的差异、受影响范围和风险；B 核查已有 CI、日志或验收记录。两路共享同一仓库和提交快照，各自记录子会话/运行标识、模型调用、状态与证据；不把它们创建成两份无关的用户任务。
3. **核对并汇总。** 主 Agent 逐项核对来源是否可访问、仓库与 commit 是否匹配、测试环境是否满足口径。两路都返回有效的核查结果后，生成完整汇总；一条核查结果可以是“未找到证据”，这不等于测试通过。来源冲突时列出冲突和出处，无法解决则标未验证。适用的独立复核沿用现有对话质量门禁，不能把两路取证自动当成独立复核通过。
4. **回到原会话。** 同一 Task 生成一条可去重的最终结果，列出提交与基线、改动、已验证项、失败项、未验证项、证据入口和下一步。PC/iOS 查看同一份结果；发布前再次检查原会话和证据访问权限，失权时停止投递，不改发到其他位置。

两路并行是本试点和第一里程碑的真实协作验收案例，不是所有请求的默认要求。普通问答或简单核查可由单 Agent 处理；其他任务是否并行取决于独立性、成本与收益。

## 4. 接入现有架构

```text
PC / iOS 原会话 → Morde 服务端：鉴权、任务、步骤、证据、恢复、结果去重
                                      ↓
                          DSH 主 Agent → 子 Agent A / B
                                      ↓
                        授权的只读仓库和测试证据源
```

- **复用现有路径：** 会话、Task、步骤/事件、授权与审批、预算、检查点和结果投递继续由 Morde 服务端管理；模型经现有网关，Agent Runtime 只用 DSH。不新增独立用户 Web 端、第二套任务状态机或通用工作流引擎。
- **固化最小任务信息：** 在现有 Task/步骤/证据中保存用户与原会话、仓库标识、目标和基线 commit、核查口径/规则版本、授权版本、预算、子会话/尝试标识、来源、结果及错误。使用现有字段和引用，缺少时再做必要扩展。用户只读取有权访问的任务详情和证据；日志按权限脱敏查看，凭据不得暴露。
- **核查来源：** 第一版先限定一类已授权仓库和可读取的测试记录来源，验证能取得指定版本的差异和 CI 运行身份、结果及所需环境。当前 [GitHub MCP 只读名单](../../server/internal/app/cloud_dsh_mcp_selected.go)包含文件、PR 和搜索等工具，但未列出专门的 Actions/CI 运行查询；需要补充最小只读接入或使用已有的授权证据源，不能假定 CI 已接通。来源不可用时显示缺口。
- **DSH 能力边界：** 当前 [Runtime](../../runtime/morde-cloud-runtime/src/engine.mjs)已有委派与后台子会话代码，可先复用；真实并行、隔离、取消及重启恢复仍需验证。上游 [DSH jobs 说明](../../project/deepseek-harness/packages/jobs/jobs/README.md)指出进程内作业不能单靠自身跨重启持久运行，因此恢复以 Morde 服务端持久状态和检查点为准。若实施时需新增或升级插件，先核对版本、许可证和授权隔离。

## 5. 恢复、权限与状态

- **只恢复安全的步骤。** 服务重启时读取原 Task、已保存证据、当前尝试和剩余预算；已完成的 A 不重跑。短暂超时或断线时，先确认旧执行已失效，再对未完成的只读步骤最多自动重试一次；无法确认旧执行状态、权限失效或预算耗尽时暂停并说明原因，不盲目重试。
- **拒绝迟到结果。** 子步骤和每次尝试有稳定标识及版本，服务端提交结果时校验当前租约/版本；旧尝试或重复回报不能覆盖当前结果。最终结果使用稳定标识与会话消息的原子写入或等价去重机制，重连和重复投递只显示一份。
- **权限持续有效。** 执行、恢复、查看证据和投递时重新核验当前权限；撤权后停止受影响步骤，保留已有记录但不向无权用户泄露，不沿用旧任务的授权或自动扩权。用户停止指定任务时，不影响其他任务。
- **明确区分状态。** 界面可展示待澄清/待授权、执行中、等待或失败、核查完成等信息，映射现有 Task 状态和步骤，不另造生命周期。“核查完成”仅表示该核查有结果；测试证据缺失、版本不符或复核未完成时不能显示验证通过。步骤失败或重试耗尽时显示未完成和已有部分证据。

## 6. 规则复用与价值验证

用户明确确认后，保存同一工作区内适用的核查关注点、证据标准和报告格式，记录仓库、验收环境等适用范围与版本，并允许修改或关闭。下一次重新绑定仓库和 commit、核验当前权限并重新收集证据；不复用旧结论、旧证据或旧授权。优先使用现有项目内容和存储，不先建设全局记忆库或知识图谱。

建议完成工程验收后进行两周小样本试用：3–5 位目标用户、至少 12 个真实任务，按难度对照现用方法，失败和重试也计入。记录人工投入、干预次数、可用结果等待时间 P50/P90、证据可核验率、未验证项比例和每单用量/可核计费用；费用无法核算时标未知。建议目标为：证据可核验率至少 90% 且不低于对照、不允许虚构证据；人工时间中位数降低至少 30%，且典型任务至少省 3 分钟或一次干预；至少 3 位用户次周主动复用。试用前确定等待与费用上限，样本不足不作通过结论；两轮调整后仍不省人工或无人复用，就收窄或暂停。另以同难度样本对照单 Agent，决定日常任务是否值得并行；这不取消第一里程碑的双子 Agent 验收。

## 7. 验收重点

1. 使用实际 `morde-pc` 发起本地测试仓库的只读核查，观察两路真实 DSH 子 Agent 的独立运行记录和并行时段；iOS 原生客户端打开同一会话，发送追问并看到相同进度与结果。关闭 PC 客户端后任务不因客户端退出而取消。
2. A 已保存、B 超时后重启服务：只在可安全重试时恢复 B；模拟旧尝试迟到和重复投递，A 不重跑，B 恢复成功后原会话恰好出现一份最终汇总。B 持续失败时保留 A 的证据并显示未完成。
3. 混入另一 commit 的 CI 结果、用模拟器结果冒充必需的真机记录，或引用不可访问来源，不能将对应项标为已验证；证据冲突、权限撤销和预算耗尽均显示真实状态，不泄露证据或误报成功。
4. 新任务复用已确认的同工作区规则，但使用新 commit、新证据和当前权限；关闭规则或切换到不适用的工作区后不自动套用。

开发与验收使用本地隔离数据和本地留存的证据，不上传或发送文件。真实模型、PC/iOS 或授权证据源不可用时将对应项记为阻塞，不用模拟数据或构建结果冒充端到端通过。现有历史 [PC-CHAT-008 验收记录](../验证记录/PC端AI对话测试用例-2026-11-12.md)中双子 Agent 场景曾失败；不能据设计或本地单测宣称当前已经通过。
