## 需要改动的合同

- **拟新增的路由字段：**`acceptance_plan` 是本轮路由模型可选的用户可见短计划，表达将要做什么及交付什么，只供首次需要后台接管的 `new` 使用；公开网页研究允许在 `tool` 标记被服务端验证并提升为 DSH Task 后携带该计划。当前解析器使用 `DisallowUnknownFields`，且 `tool` 输入的 `acknowledge` 必须为 `false`、提升后服务端才置为 `true`，因此提示、解析、校验、提升及持久传递都要一起改。[现有决策和解析](../../server/internal/app/conversation_route_decision.go)
- **短计划约束：**只接受非空、合法 UTF-8、无 NUL 且不超过 200 个 Unicode 字符的文本；计划仅描述未来打算，不能作为授权或执行证据。回传模型上下文时须保持其计划身份，不能将它当作工具结果、已核实事实或最终答复。字段缺失、空值、类型或内容无效时丢弃计划，保留原本有效的路由和真实确认；无效 JSON 或无效路由仍按现有规则处理。快答、状态、澄清、取消及未被提升的工具动作不显示计划；不为计划单独调用模型。
- **拟新增的消息区分：**在现有会话消息返回中为短计划提供可持久、可跨端识别的结构化类型或等价标记；如果复用现有字段无法表达，则新增可选 `message_kind: task_start_plan`，同步领域类型、存储、[消息 API](../../server/internal/api/conversations.go)、[OpenAPI](../../server/openapi/portal.yaml) 和 PC 生成类型。个人会话 `GET /api/conversations/{id}/messages` 与项目会话 `GET /api/projects/{id}/conversations/{conversation_id}/messages` 共用消息基类，都需核对；没有该标记的既有消息保持原语义。计划不能当成最终回复或终态解释：当前 PC 的 [Assistant.tsx](../../web/portal/src/routes/Assistant.tsx) 既用关联 Task 的助手消息判断终态补读是否结束，也用它抑制状态展示，两处都须区分计划与终态。iOS 的 [消息解码和合并](../../clients/nanoMuse/android/src/ios/Morde/MordeCredentialExpiry.swift)及[项目会话投影](../../clients/nanoMuse/android/src/ios/Morde/MordeApp.swift)也要核对并按需要保留此标记，不能把计划当成最终结果。
- **接管与投递：**路由阶段保存候选计划及原消息身份；实际接管时按既有 `task_revision_starts` 和 `agent_acknowledged` 锚点，校验账号、会话、任务、原请求、当前修订与授权，将确认和有效计划以原子方式落库，保证相同来源重复应用只产生一次计划。合并请求沿用已有唯一锚点，不给每条合并消息重复发计划；取消、授权失效、修订过期或任务已结束后不补发旧计划。计划先于最终消息进入会话顺序；无计划时不阻塞执行和交付。所需持久化字段或唯一约束若现有结构无法表达，新增迁移，不改已发布迁移。
- **现有消息/任务读取：**优先复用已实现的消息 API、终态 outbox 和更新通知；若现有通知不能可靠覆盖晚到回告，补上持久来源驱动的消息刷新或补读。读取失败、事件丢失、重连和会话切换后可重新查询；展示去重按消息 ID 和任务/修订/来源事件，不按文本去重。不得通过刷新来重派模型或工具。
- **跨版本发布：**先让服务端读取合同和新客户端识别计划，再启用计划写入。旧 PC 可能把任意 Task 助手消息误当终态；若无法保证旧客户端已更新，须为未识别该类型的客户端提供安全的读取投影，或保持计划写入关闭，不能仅因为新增字段是可选就认定兼容。项目会话分别按实际 owner、消息 actor 和成员授权处理，不能把会话 owner 当成操作发起人。

## P0 · 接活和原会话交付

- [ ] **01 接活说明｜未开始 · T08 · 路由、存储、PC。** 按上面的合同改 [路由决策](../../server/internal/app/conversation_route_decision.go)、[路由应用](../../server/internal/store/postgres/conversation_route_actions.go) 和 [Task 启动锚点](../../server/internal/store/postgres/task_revision_start.go)，将可选计划绑定实际首次接管；按需改消息 API 和 PC。计划是模型的打算，不表示工具已派发；如果没有有效计划，只展示服务端真实的 👌🏻 确认。
  **验收：**普通 `new` 和公开搜索 `tool → Task` 都能在真实接管后显示有效计划；排队时没有 👌🏻 和计划；无计划或非法计划不影响任务接管；重复消息、合并、重连和 Worker 重启不重复，已取消或过期修订不出现迟到计划。DNS 快答无任务、工具、👌🏻 或计划；有计划时它在最终结果之前。新旧服务端/客户端混用时旧端不会因计划隐藏终态或停掉补读。

- [ ] **02 原聊天真实交付｜未开始 · T07/T08 · Worker、存储、PC。** 先分别定位工具派发、DSH 综合、原会话落库和当前窗口显示；复用 [终态 Worker](../../server/internal/worker/task_terminal_delivery_worker.go) 及 [outbox 发布事务](../../server/internal/store/postgres/task_terminal_delivery_delivery.go)。若回复已落库而不可见，修 PC 补读；处理终态事件早于回复、超过现有有限补读时间才发布、重复/乱序事件、网络恢复和切换会话。计划消息不得让终态补读提前停止或隐藏等待/失败状态。用户停在底部时自动看到新消息，翻看历史时保持位置并可跳到最新。
  **验收：**① 新闻候选一新一旧，模型只交付有来源证据的一条并说明区别；② 隔离副本中对照两份在执行的文档和固定提交，仅修改指定精简版、保留原文。两例都在原会话自动显示一次最终交付，来源或文件可打开。另延迟终态写入至现有补读窗口之后，确认当前窗口仍能显示；关闭 PC 再重开后结果仍在，工具派发数不增加。

- [ ] **03 失败也要解释｜未开始 · T07/T08 · Worker、PC。** 复用白名单事实、来源事件及原会话回告；只说明已确认做了什么、哪一步停住、是否需要用户行动。只有服务端返回当前有效且本用户可操作的批准、澄清或安全重试才展示入口；原因或操作结果未知时如实说明，不自动重派。
  **验收：**隔离环境让搜索已结算、整理请求在派发前被预算拦下，断开 PC 再重连；搜索不重跑，同一来源只出现一条说明，表明没有摘要且无需用户操作。另测真实澄清可继续、过期或撤权入口不可用；计划气泡不能使失败说明消失。

## P1 · 对话能改、能停

- [ ] **04 中途纠正｜未开始 · T08 · 路由、Worker。** 复用 [补充与修订](../../server/internal/store/postgres/conversation_route_actions.go)：安全补充送入原任务；改变目标、交付物或范围使用同一任务的新修订。只有新要求被受理才确认，复用仍适用的已验证事实；在执行和交付前重验任务、修订和授权。用户未明确指代时先澄清，不影响其他任务。
  **验收：**执行中由「检查项目」改为「只看 Harness、跳过模型预算、再给一张图」，记录原 Task ID、新 revision 和实际输入；最终只交付新范围的审查与可打开的图。注入旧修订迟到结果，不能覆盖或作为新终态；另一独立任务继续运行，已发生的旧操作按事实说明。

- [ ] **05 询问和取消｜未开始 · T07 · 路由、Worker、PC。** 仅在缺必要决定或目标不明确时提出具体问题，使用现有澄清、审批与停止入口；关联任务及版本，在批准后和每次新派发前重验状态和授权。取消/修订与派发资格的状态检查和操作账本登记应有同一事务或等价的持久围栏，避免检查后才收到取消仍按旧状态发出新操作。取消阻止后续派发；已取得派发资格或已发出的操作按账本核对成功、失败或结果未知，不承诺撤销。
  **验收：**隔离环境下「部署 release」缺目标时允许只读准备，远端派发为 0；取消后过期确认和迟到 Worker 结果不能启动部署。再测取消与派发竞争、两个活动任务只停止指定任务，以及讨论「不搞了」这句文案时不触发取消。

## 联合验收和收口

- **顺序：**先在当前版本定位并修 02/03 的成功与失败交付，再完成 01；04 可在不与上述任务写入相同文件的条件下验证，05 验证取消与澄清。01 的消息标记必须与 02/03 的终态识别一并联调，不得单独宣称闭环。
- **真实语义：**五个场景各加两种未写进提示词的等义表达、一条同词异意反例；同一句追问配不同任务上下文，核对 DSH 决策、任务与修订、授权、工具实际派发数和最终消息来源。模型输出正确但实际没执行或交付，不算通过。
- **身份和持久性：**用同一账号的两个会话及第二个账号验证隔离；测试重复提交、重连、关窗、Worker 重启、旧事件晚到、撤权和消息分页，不重复执行、不跨会话显示。实际 iOS 用同账号打开同一会话核对已保存的确认、计划及最终结果；未能实测就记录未覆盖范围。
- **记录：**每例保存实际服务端提交、PC 构建来源、原会话及 Task/revision、接管/计划/终态的消息或事件身份、工具派发次数、来源和可打开的产物，以及失败或未覆盖原因。同步 [T07/T08](Morde_任务中断与对话体验_实施任务TODO.md)、总流程及相关验证记录；没有真实 PC 证据就保持未完成。
