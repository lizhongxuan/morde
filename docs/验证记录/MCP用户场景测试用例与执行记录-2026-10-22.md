## 已修复问题

`RuntimeComputerTools()` 曾将标记为 `internal` 的 `browser_observe_field` 一并导出给 MCP，导致普通 MCP 客户端看见不应公开的内部工具，并在调用时收到上游错误。现已在单一共享目录中跳过内部工具；Agent 的计划验证仍通过内部 executor 直接使用该映射，没有增加第二套工具定义。MCP 回归测试断言该工具既不在共享公共目录，也不注册到 MCP。

验证命令（工作区源码）：

```text
cd server
go test ./internal/app ./internal/mcp
```

结果：两个包均通过。此结果只证明本工作区源码；当前运行 Portal 进程仍来自其他 checkout，MCP-07 尚未在运行实例复验。

## 未解决项与后续验收条件

1. Codex 内置 `mcp__cloudhost` 连接器持续返回 HTTP 502；同机直连 Morde MCP 正常。需要查明连接器到 `portal.localhost` 的路由/凭证配置，才能恢复原生工具调用方式。
2. 当前 Host 的 Shell、窗口、桌面截图和浏览器点击均未成功；先核对该 Host 的运行端 capability 与版本，再在支持能力的 Host 上复测。当前结果不能证明所有主机都缺少这些能力。
3. 当前 API Key 不含 schedule scope。按最小权限原则未更换 Key，也未创建真实计划；需要经管理员批准的 schedule scope 才能验收计划与通知运行链路。
4. MCP 服务进程来自不同 checkout。要让 MCP-07 源码修复生效，需要把本机服务切换到本工作区构建后再通过 MCP `tools/list` 验证；本轮没有停止或重启正在运行的 Portal 服务。

结论：主机发现、空任务查询、工作目录清单幂等重放、同 session 的 AI 自有浏览器打开/读取通过；浏览器点击、运行端 Shell/桌面能力、计划权限与当前 MCP 服务源码对齐仍未完成。没有传输文件、没有改动 Host 数据、没有创建持久任务或计划。
