# Morde PC 端 AI 对话测试用例

> 版本：2026-11-12  
> 类型：手工功能验收用例  
> 原目标模型与强度：GPT-6 Luna，MAX；按用户指示，在 GPT 上游限流时改用 DeepSeek Flash 继续验收（DeepSeek 的等价 MAX 强度未验证）
> 范围：PC 客户端 AI 对话、任务进度与恢复、简单开发任务、复杂任务协作

## 1. 测试范围与数据边界

验证用户能否在 PC 端完成普通问答、简单任务、文本形式的开发任务，以及需要持续执行或协调子 Agent 的复杂任务；重点观察消息状态、任务状态、结果真实性、会话隔离和恢复行为。

本组用例使用人工编写的虚构文本和代码片段。不要附加、拖入或要求 Agent 读取仓库、真实项目、个人资料、凭据或其他本机文件；开发用例只要求 Agent 在对话中返回代码和测试建议。需要实际运行代码时，由测试人员在本地临时目录自行保存和运行。云端电脑用例只执行无保存、无外发的演示操作。

## 2. 执行前准备

- PC 客户端已安装并登录测试账号；记录客户端版本、操作系统、测试账号、实际模型标识和推理强度。
- 纯文字用例不选择或启动云端电脑。搜索、云端电脑和子 Agent 用例只在相应能力已配置且获得授权的测试环境执行。
- 任务恢复、关联和并发用例使用测试专用、可观察执行进度的任务；如环境支持，在发送中断/修改消息前确认任务仍处于处理中。
- 用例结果记录为“通过 / 失败 / 阻塞 / 未执行”。只有观察到实际消息、任务或操作结果才记为通过；等待、超时、授权缺失等如实记为阻塞或失败。

## 3. 基础与简单任务

### PC-CHAT-001 纯文字问答（P0）

**步骤**

1. 不选择云端电脑，在新对话发送：“用三句话解释 DNS 是什么，面向没有网络基础的人。”
2. 等待助手回复。

**预期**：消息受理状态与助手处理状态可区分；助手用通俗中文回答问题，不要求先启动或选择云端电脑，不伪造工具调用或执行任务。

### PC-CHAT-002 多轮上下文与用户修正（P0）

**步骤**

1. 发送：“接下来请用简短中文回答，不要用缩写。”
2. 发送：“解释一下缓存。”
3. 发送：“再举一个浏览器场景的例子。”

**预期**：助手沿用当前会话里的表达要求，后续问题能结合上一轮主题；每条用户消息和回复顺序正确，切换侧栏或页面后输入内容不丢失。

### PC-CHAT-003 缺少必要信息时先澄清（P1）

**步骤**

1. 发送：“帮我把这段话改短一点。”但不提供原文。
2. 观察助手是否请求补充文本；补充一段虚构文本后继续。

**预期**：助手先询问缺少的内容，不编造原文；补充后在原对话中继续完成，不另起无关任务。

### PC-CHAT-004 粘贴文本摘要（P1）

**步骤**

1. 在消息中粘贴以下虚构内容：“测试版周一开放。只支持桌面浏览器。用户反馈集中在登录流程。团队计划周五修复登录问题。”
2. 发送：“提炼成两条结论和一个待办，不要补充原文没有的信息。”

**预期**：总结忠实于粘贴文本，结论和待办清楚区分；不要求上传文件，也不把未提供的信息说成事实。

### PC-CHAT-005 搜索并给出可核查来源（P1）

**步骤**

1. 在已授权搜索能力的环境发送：“查阅 OpenAI 官方文档，说明 Structured Outputs 用来解决什么问题，并给出可打开的来源链接。”

**预期**：使用可用搜索能力后给出与结论对应的来源链接；搜索不可用时说明失败或等待状态，不编造搜索结果或来源。

### PC-CHAT-006 简单开发任务：生成小型代码补丁（P1）

**步骤**

1. 发送以下虚构代码和要求：

   ```python
   def clamp(value, lower, upper):
       return value
   ```

   “请实现 `clamp(value, lower, upper)`：返回不小于 `lower` 且不大于 `upper` 的值；若 `lower > upper` 则抛出 `ValueError`。只根据这段代码回答，给出最小修改和至少四个测试例（含边界和非法区间）；不要读取或修改本机文件，也不要声称已经运行测试。”

2. 检查助手给出的代码、测试例和执行说明。

**预期**：修改范围只涉及给定函数；覆盖正常值、上下边界、超界值和非法区间；没有本机文件访问或修改，也没有虚报测试已通过。

### PC-CHAT-007 指定云端电脑的安全操作（P1，可选）

**前置条件**：测试账号已获准使用一台专用测试云端电脑。

**步骤**

1. 发送：“在我指定的测试云端电脑上打开计算器并计算 2 + 3，不要保存文件。”
2. 查看对话进度及该电脑的实际画面。

**预期**：助手只操作指定电脑，反馈可观察的操作结果；电脑不可用或权限不足时显示真实失败/等待原因，不切换到其他电脑、不声称已完成。

## 4. 复杂任务与持续交互

### PC-CHAT-008 主 Agent 并行协调两个子 Agent（P0）

**步骤**

1. 在同一条消息中提供以下虚构需求：“商品页要显示含税价格并支持按分类筛选；服务端提供 `GET /items?category=`，返回商品 ID、名称和未税价格；税率由配置提供。”
2. 发送：“请并行委派两个互不重叠的只读子任务：一个分析客户端改动，另一个分析服务端/API 改动。收回两边实际结果后，整理一份不超过 8 条的联调清单；不要访问或修改任何文件。”
3. 查看任务进度与最终答复。

**预期**：实际启动两个边界清晰的子任务并行执行；主 Agent 等待并汇总各自真实结果，指出接口依赖或风险；子任务失败或未完成时如实标明，不把“已委派”当成完成；没有文件操作。

### PC-CHAT-009 执行中修订原任务（P1）

**前置条件**：准备一个仍显示“处理中”的只读分析任务 A。

**步骤**

1. 任务 A 处理中，在同一对话发送：“把报告改成最多三条，优先保留边界情况。”
2. 观察 A 的状态、修订后的结果和消息记录。

**预期**：新消息被关联为 A 的目标修订；系统停止或安全收束旧执行后按新要求继续，保留原消息和已完成结果；旧执行的迟到结果不能覆盖新版要求。若 A 已结束才收到消息，应按当前上下文继续，不能伪报中断。

### PC-CHAT-010 无关任务并行及定向停止（P1）

**前置条件**：测试环境能稳定运行两个可观察的文本任务；两项任务不读写文件、不产生外部副作用。

**步骤**

1. 启动一个较长的虚构需求分析任务 A，并确认其仍在处理。
2. 在同一会话发送一个独立且较长的任务 B，例如：“基于一段虚构的分类规则，逐项整理成分组说明和检查清单。”
3. 确认 B 已开始后，只停止 B。

**预期**：B 无需等待 A 结束即可作为独立任务处理；停止 B 只影响 B，A 继续运行；两个任务的状态和结果归属正确。如测试环境无法稳定控制任务时长，记为阻塞，不以连续发送消息代替并行证据。

### PC-CHAT-011 关联不明确时确认目标（P1）

**前置条件**：同一会话中有两个仍在处理、主题不同的任务 A 和 B。

**步骤**

1. 发送：“把它缩短一些。”
2. 在助手询问后，明确指定 A 或 B，再观察后续处理。

**预期**：在确认前，助手不擅自中断或修改 A、B；确认后只处理指定任务，并保留澄清前后的消息记录。

### PC-CHAT-012 关闭/刷新后恢复且不重复执行（P0）

**前置条件**：使用测试专用、处理中且可观察进度的任务，不包含文件写入、发送消息等副作用。

**步骤**

1. 发送任务并确认服务端已受理且任务开始。
2. 关闭 PC 客户端或刷新页面，稍后重新打开同一账号、同一会话。
3. 检查任务状态、进度、结果和任务记录。

**预期**：已受理任务不会因客户端关闭而被取消；重新打开后显示服务端的实际状态和已有进度；不会重复创建任务或重复执行已确认的操作。

### PC-CHAT-013 网络中断与消息重试（P1）

**步骤**

1. 在测试环境断开网络，发送一条文本消息，再连续发送第二条。
2. 查看消息状态后恢复网络，按界面提供的方式重试或恢复。

**预期**：消息内容和原会话归属保留，未获服务端确认时不显示“已发送”；恢复后同一消息重试不会重复生成消息或任务。发送状态与 Agent 处理失败状态分开展示。

## 5. 会话与长历史

### PC-CHAT-014 多会话任务归属（P1）

**步骤**

1. 创建会话 A 和 B，分别发送不同主题的消息；让 A、B 各自有一条可观察任务。
2. 来回切换会话并查看消息、任务进度和结果。

**预期**：每个会话只显示自己的消息、任务和结果；切换会话不会改变另一会话任务状态或丢失草稿。

### PC-CHAT-015 超过模型上下文窗口后的历史理解（P2）

**步骤**

1. 在测试模型的上下文容量之外构造多轮对话，早期放入一条虚构约束，例如“报告必须用中文且最多三点”。
2. 发送新的相关请求，检查助手是否依据早期约束回答；同时打开历史记录查看原始消息。

**预期**：必要历史仍可用时遵守早期约束，原始记录可查看；历史不可取得时明确说明，不编造此前约定。

### PC-CHAT-016 用户与账号数据隔离（P0）

**前置条件**：准备两个独立测试账号，使用不含真实个人信息的不同虚构标记。

**步骤**

1. 账号 A 在个人会话中发送：“本账号测试标记是 BLUE-731。”
2. 退出并以账号 B 登录，询问：“账号 A 的测试标记是什么？”并尝试打开 A 的会话链接。

**预期**：B 无法读取 A 的会话或标记；访问被拒绝或会话不可见，不返回 A 的内容。A、B 各自的任务和进度互不混淆。

### PC-CHAT-017 生成并下载设计方案文档（P0）

**前置条件**：使用本机隔离 Portal、合成模型和有写入权限的测试 Workspace；PC 客户端与 Web 浏览器登录同一测试账号，并确认两端指向同一 Portal 服务。下载文件只保存到本机临时测试目录。

**步骤**

1. 在新会话且未选择 Workspace 时发送：“为五子棋应用写一份设计方案，包含目标与范围、模块、数据结构、主要流程、风险和验收条件，保存为 Markdown 文件并提供下载。”
2. 按提示选择测试 Workspace 并继续原任务；等待任务完成，记录 Task ID、产物路径、固定版本和 SHA-256。
3. 分别从 PC 与 Web 的同一任务成果入口下载文件，保存到本机临时测试目录并核对文件内容和摘要。

**预期**：整个流程只创建一个 Task；设计方案包含要求的章节且可读；文件是可打开的 UTF-8 `.md`，任务产物记录的 Workspace 固定版本、文件大小和 SHA-256 均可核验。PC 与 Web 下载字节一致，摘要与产物记录一致。只看到聊天中的文件名/下载按钮或 HTTP 200 不算通过；权限撤销、产物未核验、文件版本不可用或摘要不匹配时必须明确失败，不能交付错误内容。不得上传或外发测试文件。

### PC-CHAT-018 同一工作的多条消息自动归并（P0）

**前置条件**：使用本机隔离服务、同一测试账号/会话/项目/Workspace 和相同授权范围；PC 客户端与 Web 浏览器连接同一个 Portal。记录每条消息、Task、修订和工具调用的 ID。

**步骤**

1. 发送：“为五子棋应用写一份设计方案并保存为 Markdown。”
2. 在首条消息仍在路由、Task 已排队、Task 正在运行三个时点，分别发送：“同一个方案增加 AI 难度和存档设计。”
3. 在 PC 与 Web 近同时发送一条范围相同的补充要求；等待完成后刷新页面并重启 PC 客户端，再核对数据库记录和最终文档。
4. 对照发送一条目标不同或明确要求“重新开始/重做”的请求，以及另一 Workspace 的同主题请求。

**预期**：同一工作范围内的补充消息保留各自记录并关联到同一逻辑 Task；新增要求进入该 Task 的修订和最终文档，不重复执行相同工作。服务端关联、Task ID、修订、操作账本与两端页面一致；任务开始后，同一 Task 只在一条对应用户消息显示一次 👌🏻，刷新和重启后不重复创建或执行。不同目标、明确重做、不同 Workspace/项目/账号或附件范围必须保持独立。

**范围说明**：“自动归并”指把同一工作的多条消息作为同一逻辑 Task 的补充/修订，不删除消息，也不把两个已经分别启动的独立 Task 伪装成一个 Task。已分别执行的任务保留原记录；需要汇总时保留各自来源。

- 将模型可用性和工具能力作为任务用例的前置检查：GPT-6 Luna MAX 需先确认能返回一次真实文本回复；并行委派和搜索需分别确认工具调用/搜索连接器可用。前置检查失败时停止该组用例，避免把服务故障误判为对话逻辑失败。
- 为 `usage_unknown` 增加可见的恢复状态和安全的结算流程；确认旧调用已结束或结果已协调前，不自动重放同一消息。当前 PC-CHAT-009 的修订正确地要求原文或用户确认，但缺少稳定任务结果，无法验收正常修订路径。
- 准备仅影响 Electron 客户端的可恢复网络故障注入、两个隔离测试账号，以及明确授权的测试云端电脑；这能解除 PC-CHAT-007、013、016 的环境阻塞，并避免改动共享 VM 网络或真实账户设置。
- 用小上下文的本地测试模型或受控测试配置验证长历史摘要：保留“早期约束 + 超窗后的新请求”验收点，同时避免向 1,000,000-token 上下文模型发送巨量文本和产生未核对用量。
